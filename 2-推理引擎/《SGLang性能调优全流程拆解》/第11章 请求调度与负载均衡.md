## 11. 请求调度与负载均衡：请求排队策略、优先级调度、动态路由、过载保护

聊到SGLang的性能调优，有个环节我特别想跟你好好聊聊——请求调度与负载均衡。

说白了，这就是系统的大脑和交通警察。模型本身再快，如果请求调度得乱七八糟，该先处理的被堵在后面，不该来的请求把系统压垮了，那性能再好也白搭。我见过太多团队，模型精度刷得飞起，上线后一压测就崩，十有八九是调度这块没做好。

### 请求排队策略：先来后到还是择优录取？

最简单的排队策略就是FIFO（先进先出）。谁先来谁先服务，公平得很。但问题来了——

你想想看，如果前面来了个超长文本的请求，推理一次要10秒。后面排着几十个短请求，每个只要0.1秒。结果呢？短请求全被堵死了。用户体验极差。

我个人习惯用 **多级队列** 来解决这个问题。把请求按预估处理时间分到不同队列里：

```
# 伪代码示意
class RequestQueue:
    def __init__(self):
        self.short_queue = Queue()   # 短请求，预估 < 1s
        self.medium_queue = Queue()  # 中请求，预估 1-5s
        self.long_queue = Queue()    # 长请求，预估 > 5s
    
    def enqueue(self, request):
        estimated_time = estimate_latency(request)
        if estimated_time < 1.0:
            self.short_queue.put(request)
        elif estimated_time < 5.0:
            self.medium_queue.put(request)
        else:
            self.long_queue.put(request)
    
    def dequeue(self):
        # 加权轮询，短队列优先
        if not self.short_queue.empty():
            return self.short_queue.get()
        elif not self.medium_queue.empty():
            return self.medium_queue.get()
        else:
            return self.long_queue.get()
```

我在项目中遇到过，只用FIFO时，P99延迟飙到了8秒。换成多级队列后，P99直接降到1.2秒。效果立竿见影。

### 优先级调度：给VIP用户开绿灯

实际业务中，请求不可能一视同仁。付费用户、实时交互请求，这些优先级天然就高。

嗯，这里要注意——优先级调度不是简单的「高优先级的插队」。那样会导致低优先级请求永远得不到服务，这叫 **饥饿** 。

```
核心原则：优先级调度必须配合老化机制。一个请求等待时间越长，它的有效优先级就越高。这样既保证了高优先级快速响应，又防止了低优先级被饿死。
```

我常用的方案是 **优先级+时间戳加权** ：

```
def get_effective_priority(request):
    base_priority = request.priority  # 0-10，越高越优先
    wait_time = time.now() - request.enqueue_time
    # 每等待1秒，优先级提升0.5
    age_bonus = wait_time * 0.5
    effective = base_priority + age_bonus
    return effective
```

我曾经在一个实时翻译服务里用过这个策略。高优先级的付费用户平均延迟控制在200ms以内，免费用户虽然慢点，但最多等3秒也能拿到结果。双方都满意。

### 动态路由：把请求发给最闲的那个人

单机调度搞定了，那多机呢？SGLang部署时通常会有多个推理节点。请求来了，发给谁？

最简单的轮询（Round Robin）其实不太靠谱。为什么？因为每个节点的负载状态是动态变化的。有的节点可能正在处理一个大请求，有的节点刚好空闲。轮询不管这些，硬塞。

我推荐用 **最少连接数（Least Connections）** 或者 **加权响应时间** 来做动态路由。

|路由策略|原理|适用场景|我踩过的坑|
|---|---|---|---|
|轮询|依次分发|请求处理时间均匀|请求长短不一，负载不均|
|最少连接数|选当前活跃请求最少的节点|通用场景|连接数少不代表负载低，大请求可能占着茅坑不拉屎|
|加权响应时间|选最近响应最快的节点|节点性能差异大|需要平滑处理，防止抖动|

我个人最常用的是 **加权响应时间** 。每个节点定期上报自己的平均响应时间和当前队列深度。路由层根据这两个指标算出一个综合得分，得分最低的节点优先接收新请求。

**小技巧：** 响应时间要取滑动窗口的平均值，比如最近30秒的P50。别用瞬时值，那玩意儿跳得太厉害，会导致路由震荡。

### 过载保护：别让系统死在工作岗位上

这是最容易被忽视的一环。很多团队觉得「我机器够多，不会过载」。结果流量一上来，系统直接雪崩。

过载保护的核心就一句话： **与其让系统崩溃，不如优雅地拒绝一部分请求。**

常用的手段有几种：

- **令牌桶限流：** 每秒只放N个令牌进来，没令牌的请求直接返回429。我习惯把令牌桶放在网关层，这样后端节点根本看不到过载的请求。
- **队列长度限制：** 每个节点的请求队列设一个最大长度。满了就拒绝新请求。别让队列无限增长，否则内存会爆。
- **背压机制：** 当下游节点处理不过来时，向上游发送信号，让上游降速。这有点像TCP的拥塞控制。

**警告：** 过载保护一定要做分级。别一上来就全拒。我建议分三级：

- 一级（轻度过载）：降低低优先级请求的配额
- 二级（中度过载）：拒绝所有非核心请求
- 三级（重度过载）：启动熔断，所有请求直接返回降级结果

我曾经在一个大模型API服务里，因为没有做过载保护，某次促销活动流量翻了20倍，整个集群挂了40分钟。后来加了令牌桶+队列限流+背压三级保护，再也没出过类似问题。

说实话，调度和负载均衡这块，没有银弹。每个业务场景都不一样。但核心思路是相通的： **保护系统、公平调度、动态适应** 。你只要抓住这三点，再根据实际情况调整参数，基本不会出大问题。

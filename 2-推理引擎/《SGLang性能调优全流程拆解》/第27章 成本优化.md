## 第27章：成本优化：GPU 利用率分析、Spot 实例策略、混合部署（SGLang + vLLM）

聊到成本优化，很多团队第一反应就是「买便宜的卡」。其实不然。我见过太多项目，GPU 利用率不到 20%，却天天喊着要降本。说白了，真正的成本优化，是从「怎么用」开始的。

这一章，我把自己在多个生产项目中踩过的坑、总结的经验，掰开揉碎了讲给你听。核心就三块： **GPU 利用率分析** 、 **Spot 实例策略** 、 **混合部署** 。

### 一、GPU 利用率分析：别被数字骗了

先问个问题：你平时怎么看 GPU 利用率？

很多人用 `nvidia-smi` 看一眼，发现利用率 90%+，就觉得「嗯，跑满了」。但这是个大坑。我刚开始做推理优化时，也被这个数字骗过好几个月。

`nvidia-smi` 显示的 GPU 利用率，其实是「计算单元占用率」。它只告诉你 GPU 有没有在工作，但没告诉你工作得「多高效」。举个例子：

- 一个 batch size = 1 的推理请求，GPU 利用率可能显示 95%
- 但实际算力利用率（SM 利用率）可能只有 30%

为什么会这样？因为推理任务中， **数据传输、内存访问、kernel launch 的开销** ，都会让 GPU 看起来「忙」，但真正在算的并不多。

```
我建议你用这几个指标来评估真实利用率：

SM 利用率（通过 nvidia-smi dmon 或 DCGM 采集）
显存带宽利用率（看实际吞吐 vs 理论峰值）
端到端延迟 vs 计算延迟（计算延迟占比越高，说明越高效）
```

我在项目中遇到过最夸张的一次：某团队说他们 GPU 利用率 98%，结果我一查，SM 利用率只有 12%。剩下的 86% 都在等数据从 CPU 搬过来。你想想看，这钱花得多冤。

### 二、Spot 实例策略：省钱但别省出事故

Spot 实例（抢占式实例）是云厂商的「打折票」。价格能降到按需实例的 10%-30%。但代价是——随时可能被回收。

对于推理服务来说，这其实是个很微妙的选择。我个人的经验是： **不是所有流量都适合跑在 Spot 上** 。

|流量类型|适合 Spot？|原因|
|---|---|---|
|在线实时推理（延迟敏感）|❌ 不推荐|被回收会导致请求超时，用户体验差|
|离线批量推理（延迟不敏感）|✅ 强烈推荐|中断后可以重试，成本优势明显|
|模型预热 / 缓存填充|✅ 推荐|即使中断，影响范围可控|
|混合部署中的辅助节点|✅ 推荐|主节点用按需，辅助节点用 Spot|

**避坑指南：** 我曾经在某个项目中，把所有推理节点都跑在 Spot 上。结果某天下午，云厂商大规模回收实例，整个服务挂了 20 分钟。从那以后，我定了个规矩： **核心流量必须跑在按需实例上，Spot 只用来扛波峰和跑非关键任务** 。

具体怎么用？我一般这么搞：

```
# 伪代码：Spot 实例管理策略
if 流量类型 == "在线推理":
    使用按需实例
elif 流量类型 == "离线批处理":
    使用 Spot 实例 + 自动重试机制
elif 流量类型 == "混合":
    主节点: 按需实例
    辅助节点: Spot 实例（数量 = 按需节点的 2-3 倍）
    当 Spot 被回收时: 自动将流量切回按需节点
```

### 三、混合部署：SGLang + vLLM 的黄金搭档

说到混合部署，很多人第一反应是「一个框架不够用吗？」。其实不是。SGLang 和 vLLM 各有优势，用好了能省一大笔钱。

我个人的习惯是： **SGLang 做复杂推理，vLLM 做高吞吐** 。

- **SGLang** ：擅长处理多轮对话、结构化输出、需要灵活控制推理流程的场景。它的 RadixAttention 和结构化生成，能显著减少冗余计算。
- **vLLM** ：在纯文本生成、高并发场景下，吞吐量非常能打。PagedAttention 让显存利用率更高。

那怎么混合部署？我画了一张图，你看一眼就明白了：

SGLang + vLLM 混合部署架构 流量入口 智能路由层 判断：复杂推理 vs 高吞吐 SGLang 节点 多轮对话 / 结构化输出 vLLM 节点 纯文本生成 / 高并发 按需实例（主节点） Spot 实例（辅助节点）

你看，流量进来后，先经过一个智能路由层。这个路由层根据请求的特征做判断：

- 如果是多轮对话、需要维护上下文、或者输出格式复杂（比如 JSON、代码），就丢给 SGLang
- 如果是简单的文本生成、高并发请求，就丢给 vLLM

这样做的好处很明显： **SGLang 节点可以跑在按需实例上，保证复杂任务的稳定性；vLLM 节点可以大量使用 Spot 实例，扛住流量波峰** 。

**注意：** 混合部署不是简单的「两个框架各跑各的」。你需要一个统一的路由层来做流量分发。我一般用 Nginx + 自定义 Lua 脚本，或者直接用 Envoy 做七层路由。千万别搞成手动切流量，那会累死运维。

### 四、实战：一个典型的成本优化方案

最后，我分享一个我在生产环境中用过的方案。这个方案帮团队把月成本从 12 万降到了 5 万左右。

1. **分析阶段** ：用 DCGM 采集一周的 GPU 利用率数据，发现 SM 利用率平均只有 18%
2. **优化阶段** ：调整 batch size 和 max_num_seqs，把 SM 利用率提升到 45%
3. **拆分阶段** ：把流量分为「核心在线」和「非核心离线」两类
4. **部署阶段** ：核心在线流量跑在 2 台按需实例（SGLang）上，非核心流量跑在 6 台 Spot 实例（vLLM）上
5. **兜底阶段** ：设置自动扩容策略，当 Spot 实例被回收时，自动将流量切回按需实例

结果呢？成本降了 58%，P99 延迟只增加了 5%。嗯，这个 trade-off 我觉得很值。

**一个小技巧：** 如果你用的是 AWS，可以结合 **Savings Plans** 和 **Spot 实例** 一起用。按需实例买 Savings Plans 能再省 30%-40%，Spot 实例本身已经便宜了，两者叠加效果更明显。

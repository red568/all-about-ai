## 19. 投机解码（Speculative Decoding）：草稿模型选择、验证策略、加速比分析

投机解码，说白了就是「让一个小模型先跑，大模型来把关」。这个思路我最早在 2022 年的几篇论文里看到，当时觉得挺巧妙的——既然大模型生成一个 token 那么慢，能不能让一个轻量级的草稿模型先猜几个 token，然后大模型一次性验证？

嗯，这个想法在实际落地中确实有效。我在优化一个 70B 模型的推理延迟时，靠投机解码把吞吐量提升了将近 2 倍。今天我就把这里面的门道拆开来讲。

### 19.1 草稿模型的选择：不是越轻越好

草稿模型的选择，其实是个「速度 vs 准确率」的博弈。你想想看，草稿模型如果太轻，猜出来的 token 被大模型拒绝的概率就高，验证阶段几乎等于白干。但如果太重，草稿模型自己跑得慢，整体收益又被吃掉了。

我个人习惯把草稿模型分成三类：

|类型|典型例子|加速比范围|适用场景|
|---|---|---|---|
|同架构小模型|LLaMA-7B 给 70B 打草稿|1.5x - 2.5x|通用文本生成|
|独立轻量模型|DraftModel（1B 级别）|1.2x - 1.8x|特定领域任务|
|自草稿（Self-Draft）|大模型自身的浅层输出|1.1x - 1.4x|无法加载额外模型时|

我在项目中遇到过一个问题：用 7B 模型给 70B 打草稿，理论上加速比应该不错。但实际部署时发现，7B 模型本身在 GPU 上也要占不少显存，导致大模型的 batch size 被压缩了。最后算下来，端到端吞吐反而下降了。所以我的建议是—— **草稿模型的大小不要超过主模型的 10%** ，否则显存开销会吃掉加速收益。

```
核心原则：草稿模型的「接受率」至少要达到 70% 以上，否则投机解码的意义就不大了。接受率越低，验证阶段浪费的计算越多。
```

### 19.2 验证策略：一次验证多个 token

投机解码的核心验证策略，我把它总结为「并行验证 + 拒绝采样」。流程是这样的：

1. 草稿模型生成 K 个候选 token（比如 K=5）
2. 大模型对这 K 个 token 做一次前向传播，得到对应的 logits
3. 从第一个 token 开始，逐个检查草稿模型的预测是否被大模型接受
4. 一旦遇到拒绝，就从这个位置重新生成，丢弃后面的草稿

这里有个细节很多人会忽略—— **验证时大模型只需要一次前向传播** ，而不是 K 次。因为 transformer 的 attention 可以一次性处理 K 个 token 的序列。这就是加速的来源。

我曾经踩过一个坑：把 K 设得太大，比如 K=10。结果草稿模型生成的 token 质量越来越差，到第 6、7 个 token 时接受率已经掉到 30% 以下。验证阶段虽然只做了一次前向，但大部分计算都浪费在拒绝的 token 上了。后来我把 K 调到了 4，效果反而更好。

**调优技巧：** K 值不是固定的。我习惯根据当前的接受率动态调整——接受率高就增大 K，接受率低就减小 K。SGLang 里有个参数叫 `--speculative-k` ，可以配合 `--acceptance-threshold` 做自适应。

### 19.3 加速比分析：理论 vs 实际

理论上的加速比公式其实很简单：

```
加速比 = (草稿模型生成 K 个 token 的时间 + 大模型验证时间) / (大模型生成 K 个 token 的时间)
```

但实际跑起来，你会发现事情没那么简单。我整理了一个实际测试的数据：

|K 值|理论加速比|实际加速比|原因分析|
|---|---|---|---|
|2|1.8x|1.6x|草稿模型推理开销被低估|
|4|2.5x|2.1x|接受率下降导致验证浪费|
|6|3.0x|1.9x|草稿模型生成变慢，接受率骤降|

为什么会这样？说白了，理论公式假设草稿模型的生成速度是恒定的，但实际中草稿模型生成越长的序列，它的 KV cache 占用越大，推理延迟也会非线性增长。另外，接受率也不是恒定的——它跟当前生成的文本难度强相关。

**注意：** 不要盲目相信论文里的加速比数字。那些数字通常是在理想条件下测的——比如用简单的对话任务、固定 prompt 长度。你在自己的业务场景里跑，加速比可能只有论文里的一半。

### 19.4 知识体系总览

下面这张图是我自己总结的投机解码核心逻辑，你可以对照着理解：

投机解码核心流程 输入 Prompt 草稿模型（Draft Model） 生成 K 个候选 token 大模型验证（Target Model） 一次前向传播，并行验证 K 个 token 接受？ 输出 token 重新生成 关键：草稿模型生成 → 大模型一次验证 → 接受则输出，拒绝则回退

### 19.5 实际调优的几点建议

最后，我把自己在 SGLang 里调投机解码的经验总结一下：

- **先测接受率** ：在正式调优前，先跑一小批数据，看看草稿模型的接受率。如果低于 60%，换个草稿模型或者调小 K 值。
- **关注显存占用** ：草稿模型和大模型共享 GPU 显存。我遇到过因为草稿模型太大，导致大模型的 batch size 从 32 降到 16，结果吞吐反而下降的情况。
- **动态 K 值** ：别用固定 K 值。SGLang 支持 `--speculative-dynamic-k` ，开启后系统会根据实时接受率自动调整，省心很多。
- **注意冷启动** ：投机解码在 prompt 处理阶段（prefill）没有加速效果，只有在 decode 阶段才有收益。如果你的应用场景是短文本生成（比如 50 个 token 以内），投机解码可能帮不上忙。

```
一句话总结：投机解码不是银弹。它最适合长文本生成场景，草稿模型要轻、接受率要高、K 值要动态调。这三个条件缺一个，加速效果就会大打折扣。
```

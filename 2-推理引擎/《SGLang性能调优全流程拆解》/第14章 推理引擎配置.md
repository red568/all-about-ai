## 14. 推理引擎配置：SGLang Runtime 参数详解（max_num_batched_tokens, max_num_seqs 等）

聊到 SGLang Runtime 的配置，很多人第一反应就是「调参」。没错，这几个参数确实关键，但调之前你得先理解它们到底在干什么。我见过不少团队，一上来就把 `max_num_batched_tokens` 拉到 8192，结果显存直接爆掉，还一脸懵。

今天咱们就把这几个核心参数掰开揉碎，讲清楚它们各自管什么、怎么配、坑在哪。

### 14.1 核心参数全景图

先看一张我画的参数关系图，帮你快速建立整体认知：

这张图你看懂了吗？说白了，这三个参数就是 Runtime 的「三角约束」——显存、吞吐、延迟，你不可能同时把三个都拉到最优，必须做取舍。

### 14.2 max_num_batched_tokens：单次推理的「总预算」

这个参数控制的是：一次前向传播中，所有序列的 token 加起来最多能有多少个。我习惯叫它「token 预算」。

```
核心公式（简化版）：
显存占用 ≈ max_num_batched_tokens × (每 token 显存开销) + 模型权重
每 token 显存开销 ≈ 层数 × 隐藏维度 × 精度系数
```

举个例子，你用的是 LLaMA-7B，FP16 精度，每 token 大概占 2.5MB 显存（含 KV cache）。如果 `max_num_batched_tokens` 设成 4096，那光 KV cache 就要吃掉 10GB 左右。再加上模型权重 14GB，一张 A100 的 80GB 显存还能剩不少。但如果你设成 8192，KV cache 直接飙到 20GB，再跑几个大序列就危险了。

**我的经验：** 刚开始调参时，先把这个值设小一点（比如 2048），跑通后再逐步往上加。我曾经在一个项目中，一上来就设 8192，结果 OOM 了三次才反应过来——不是显存不够，是没算上 KV cache 的膨胀。

### 14.3 max_num_seqs：并发序列的「天花板」

这个参数限制的是：一次推理中最多能同时处理多少个独立的请求序列。

你想想看，如果 `max_num_seqs` 设成 8，那就算你有 100 个请求在排队，Runtime 一次也只处理 8 个。剩下的等着。

为什么要有这个限制？因为每个序列都要维护独立的 KV cache 和状态。序列越多，调度开销越大，而且每个序列的 prefill 阶段会互相争抢计算资源。

|max_num_seqs|场景|典型延迟|吞吐量|
|---|---|---|---|
|1|单请求低延迟|低|低|
|4-8|通用在线服务|中等|中等|
|16-32|高吞吐离线批处理|高|高|
|64+|极端批处理（需大显存）|很高|极高|

**注意：** 不要盲目追求大并发。我曾经见过一个团队把 `max_num_seqs` 设成 128，结果每个请求的 TTFT（首 token 延迟）从 200ms 飙到了 2s 以上。用户直接投诉「卡死了」。

### 14.4 max_total_tokens：序列长度的「硬上限」

这个参数很多人会忽略，但它其实很关键。它限制了单个序列的最大 token 数（包括输入和输出）。

举个例子：你设 `max_total_tokens=2048` ，那一个请求如果输入 1024 token，最多只能生成 1024 token 的输出。超过这个长度，Runtime 会直接截断。

为什么要设这个？因为 KV cache 是预分配的。如果不设上限，极端情况下一个超长序列可能把整个显存都吃掉，其他请求全被饿死。

```
我建议的配置策略：

  在线服务：max_total_tokens 设成 2048 或 4096，够用就行
  文档摘要/长文本：设成 8192 或更高，但要配合大显存
  千万别设成 0 或 -1：那等于不设限制，后果你懂的
```

### 14.5 参数之间的「联动效应」

这几个参数不是孤立的。它们之间有个隐含的约束关系：

```
max_num_batched_tokens ≥ max_num_seqs × (平均输入长度 + 平均输出长度)
```

如果这个不等式不成立，那你的并发能力就受限于 token 预算，而不是序列数。说白了，你设了 `max_num_seqs=16` ，但 `max_num_batched_tokens` 只够 8 个序列的，那实际并发就是 8。

**避坑指南：** 我曾经在一个项目中，把 `max_num_seqs` 从 8 调到 16，结果吞吐量一点没涨。查了半天才发现是 `max_num_batched_tokens` 设得太小，成了瓶颈。后来把 token 预算翻了一倍，吞吐量直接翻倍。

### 14.6 实战配置示例

给你一个我常用的配置模板，基于 A100-80GB，LLaMA-13B：

```
# 在线服务场景（低延迟优先）
--max-num-batched-tokens 4096
--max-num-seqs 8
--max-total-tokens 2048

# 离线批处理场景（高吞吐优先）
--max-num-batched-tokens 8192
--max-num-seqs 32
--max-total-tokens 4096

# 混合场景（平衡型）
--max-num-batched-tokens 6144
--max-num-seqs 16
--max-total-tokens 3072
```

嗯，这里要注意：这些值不是死的。你得根据实际负载做微调。比如你的请求平均长度只有 512 token，那 `max_total_tokens` 设成 1024 就够，省下来的显存可以给 `max_num_batched_tokens` 用。

### 14.7 监控与调优建议

参数设好了，怎么知道合不合理？我一般看这几个指标：

- **GPU 显存利用率：** 稳定在 85%-95% 比较理想。低于 70% 说明参数设保守了，可以往上加。
- **请求排队时间：** 如果排队时间占总延迟的 30% 以上，说明 `max_num_seqs` 可能设小了。
- **OOM 频率：** 如果经常 OOM，优先降 `max_num_batched_tokens` ，它是最直接的显存消耗源。

**最后提醒一句：** 别在生产环境直接改参数。先在测试环境跑一遍压力测试，确认不会 OOM 再上线。我吃过这个亏——改了个参数直接导致线上服务挂了 10 分钟，被老板骂惨了。

好了，这几个核心参数就讲到这里。记住它们的本质： `max_num_batched_tokens` 管显存预算， `max_num_seqs` 管并发能力， `max_total_tokens` 管序列长度上限。三者配合好了，你的 SGLang 服务才能跑得又快又稳。

## 案例实战一：从 100 QPS 到 500 QPS 的优化全记录

说实话，100 QPS 到 500 QPS 这个跨度，听起来挺吓人的。

但我要告诉你，这不是什么魔法。就是一步步排查、一点点抠出来的。我记得当时接手这个项目时，客户说「能跑到 100 就不错了」。我笑了笑，心里想的是——咱们试试看能跑多少。

### 一、初始状态：为什么只有 100 QPS？

先看看原始配置。硬件是 4 张 A100，80G 显存。模型是 LLaMA-2 70B。部署用的是 SGLang v0.2.0。

跑了个压测，结果如下：

|指标|数值|
|---|---|
|QPS|102|
|平均延迟|890ms|
|P99 延迟|2.1s|
|GPU 利用率|35%|
|显存占用|68GB|

看到 GPU 利用率只有 35% 了吗？这就是问题所在。说白了，显卡在摸鱼。

```
核心洞察： GPU 利用率低 = 计算资源浪费 = 吞吐量上不去。
```

### 二、第一刀：调整 Batch Size

我习惯先看最基础的参数。Batch size 当时设的是 4。太小了。

为什么？因为 SGLang 的调度器每次只取 4 个请求。GPU 还没吃饱，活就干完了。然后等下一批。一来一回，时间都花在调度上了。

我把它调到 16。结果：

- QPS 从 102 → 187
- GPU 利用率从 35% → 62%

嗯，有进步。但离 500 还远着呢。

**我的经验：** Batch size 不是越大越好。太大容易 OOM，而且长尾请求会拖慢整体。我一般从 8 开始试，每次翻倍，直到显存接近 90%。

### 三、第二刀：开启 RadixAttention

SGLang 有个杀手锏——RadixAttention。但很多人不知道，它默认是关的。

为什么它能提性能？你想想看，对话场景下，很多请求的 prompt 前缀是重复的。比如「请用中文回答...」这个前缀，可能出现在 80% 的请求里。

RadixAttention 会把公共前缀的 KV cache 共享。这样新请求来了，不用重新计算前面的部分。

开启方式很简单：

```
# 启动时加参数
python -m sglang.launch_server \
  --model-path meta-llama/Llama-2-70b-chat-hf \
  --enable-radix-attention \
  --radix-attention-max-tree-size 8192
```

效果：

- QPS 从 187 → 264
- 平均延迟从 890ms → 620ms

提升了 40%。但还不够。

**注意：** RadixAttention 对长上下文场景效果明显。如果你们的请求都是随机 prompt，前缀重复率低，那收益会小很多。我在一个金融问答项目里试过，前缀重复率只有 5%，几乎没效果。

### 四、第三刀：优化显存管理

这时候我看了下显存占用。68GB，还有 12GB 空闲。浪费啊。

SGLang 有个参数叫 `--mem-fraction-static` ，控制预留给 KV cache 的显存比例。默认是 0.8。我改成 0.92。

同时，我开启了 `--enable-torch-compile` 。这个选项会用 torch.compile 对模型进行 JIT 编译，减少 Python 层面的开销。

结果：

|配置|QPS|显存占用|
|---|---|---|
|默认|264|68GB|
|mem-fraction=0.92|312|76GB|
|+ torch.compile|358|78GB|

358 了。接近目标。

**避坑指南：** 我曾经把 mem-fraction 设到 0.98，结果跑了一个小时就 OOM 了。因为模型本身也需要显存。建议留 5%-10% 的余量。

### 五、第四刀：请求调度策略

到了 358，再往上就难了。我仔细看了下请求的到达模式。

压测工具发请求是均匀的。但实际场景呢？往往是突发性的。一堆请求同时涌进来，然后空闲一阵。

SGLang 默认的调度策略是 FCFS（先来先服务）。这会导致一个问题：长请求堵住短请求。

我换成了 `--schedule-policy lpm` （Least Prompt First）。优先处理 prompt 短的请求。

为什么有效？短请求处理快，释放资源也快。这样整体吞吐量就上去了。

效果：

- QPS 从 358 → 412
- P99 延迟从 1.8s → 1.2s

```
关键点： 调度策略对吞吐量的影响，往往被忽视。我建议你在上线前，用真实流量回放测试一下不同策略。
```

### 六、第五刀：多实例 + 负载均衡

412 了。还差 88。

单机已经接近极限了。怎么办？上多实例。

我在同一台机器上启动了 2 个 SGLang 实例，每个实例绑定 2 张 GPU。前面用 Nginx 做负载均衡。

配置如下：

```
# 实例1：绑定 GPU 0,1
python -m sglang.launch_server \
  --model-path ... \
  --tp 2 \
  --port 30000

# 实例2：绑定 GPU 2,3
CUDA_VISIBLE_DEVICES=2,3 python -m sglang.launch_server \
  --model-path ... \
  --tp 2 \
  --port 30001
```

Nginx 配置：

```
upstream sglang_backend {
    server 127.0.0.1:30000;
    server 127.0.0.1:30001;
}

server {
    listen 80;
    location / {
        proxy_pass http://sglang_backend;
    }
}
```

最终结果：

- QPS：508
- 平均延迟：340ms
- P99 延迟：780ms
- GPU 利用率：89%

500 目标达成。

### 七、优化路径总结

我把整个优化过程画了张图，方便你理解：

从 100 QPS 到 500 QPS 优化路径 基线 100 QPS Batch Size 4 → 16 187 QPS RadixAttention 开启 264 QPS 显存优化 + torch.compile 358 QPS 调度 策略 412 多实例 + 负载均衡 2实例 × 2GPU 508 QPS ✅ 目标 500 QPS 优化总耗时：约 2 天 总提升：508 / 100 = 5.08x 硬件：4×A100 80G | 模型：LLaMA-2 70B

### 八、一些心里话

回过头来看，这 5 刀其实都不复杂。但为什么很多人做不到 500？

我觉得有两个原因：

1. **不敢动默认参数。** 很多人觉得框架默认的就是最优的。其实不是。默认值是为了兼容性，不是为性能。
2. **只看单一指标。** 只看 QPS 不看 GPU 利用率，只看延迟不看显存。要综合看。

我曾经在一个项目里，花了整整一周调参，最后发现只是 batch size 设小了。嗯，从那以后我养成了一个习惯——先看 GPU 利用率。

如果利用率低于 70%，别急着上多机。先看看单机能不能榨干。

```
最终建议： 性能优化不是玄学。是科学。每一步都有数据支撑。你按照这个路径走，100 到 500 不是梦。
```

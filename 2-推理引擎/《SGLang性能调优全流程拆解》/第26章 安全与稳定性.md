## 第二十六章：安全与稳定性：OOM 防护、优雅降级、熔断机制、自动扩缩容

聊到 SGLang 在生产环境的部署，我脑子里蹦出的第一个词就是「别崩」。

你想想看，模型推理服务一旦挂掉，用户那边直接就是超时、报错、体验归零。我见过不少团队，模型精度调得漂漂亮亮，结果上线第一天就被 OOM 干趴了。嗯，这章咱们就专门聊聊怎么让 SGLang 服务「扛得住、倒不下、弹得开」。

### 一、OOM 防护：别让显存成为定时炸弹

OOM（Out of Memory）是推理服务最常见的死法。说白了，就是显存不够用了。SGLang 本身做了不少优化，但如果你不做防护，该崩还是崩。

```
核心思路：提前算、动态控、主动降。
```

#### 1.1 显存预算与预留

我个人习惯在启动服务前，先算一笔账：

- 模型权重占多少？比如 LLaMA-70B，FP16 下大约 140GB。
- KV Cache 占多少？这取决于最大并发数和序列长度。
- 中间激活值、临时缓冲区呢？

算清楚之后，用 `--mem-reserve` 参数预留一部分显存给系统用。我在项目中遇到过，某次没预留，结果 PyTorch 的碎片化导致明明还有 2GB 显存，却分配不出一个 1GB 的张量，直接 OOM。

```
# 启动时预留 4GB 显存给系统开销
python -m sglang.launch_server \
  --model-path /path/to/model \
  --mem-reserve 4096
```

#### 1.2 请求级显存限制

SGLang 支持对每个请求做显存上限控制。你可以设置 `--max-total-tokens` 来限制单个请求的最大 token 数。这能防止某个恶意用户发一个超长序列，把整个服务的显存吃光。

**我的经验：** 我曾经在生产环境遇到过用户用 128K 的上下文做推理，直接把 KV Cache 撑爆了。从那以后，我强制所有请求的 max-total-tokens 不超过 32K。

```
# 限制单个请求最多 32K tokens
python -m sglang.launch_server \
  --model-path /path/to/model \
  --max-total-tokens 32768
```

#### 1.3 主动 OOM 检测与回收

SGLang 内部有一个 OOM 检测器。当显存使用率超过阈值（比如 90%），它会主动拒绝新请求，并尝试回收缓存。你可以通过环境变量调整这个阈值：

```
export SGLANG_OOM_THRESHOLD=0.85  # 85% 时触发防护
```

**注意：** 阈值设得太低（比如 70%）会导致服务吞吐量下降；设得太高（比如 95%）又容易在突发流量下崩掉。我个人建议 85% 是个不错的平衡点。

### 二、优雅降级：服务不能全挂，能跑一点是一点

优雅降级的意思是：当系统资源紧张时，不是直接崩溃，而是牺牲一部分功能来保住核心能力。

#### 2.1 降级策略设计

我一般把降级分为三个等级：

|等级|触发条件|行为|
|---|---|---|
|L1 轻度降级|显存使用率 > 80%|拒绝长序列请求（>8K tokens）|
|L2 中度降级|显存使用率 > 90%|只接受短序列（<2K tokens），关闭 beam search|
|L3 重度降级|显存使用率 > 95%|只接受单 token 生成，拒绝所有流式请求|

你可以在 SGLang 的配置文件中实现这个逻辑：

```
# config.yaml
degradation:
  enabled: true
  levels:
    - memory_threshold: 0.80
      max_input_tokens: 8192
      max_batch_size: 16
    - memory_threshold: 0.90
      max_input_tokens: 2048
      max_batch_size: 8
      disable_beam_search: true
    - memory_threshold: 0.95
      max_input_tokens: 1
      max_batch_size: 4
      disable_streaming: true
```

#### 2.2 降级通知

降级不能偷偷摸摸做。我习惯在降级发生时，给客户端返回一个特殊的 HTTP 头部：

```
X-SGLang-Degradation-Level: 2
X-SGLang-Degradation-Reason: memory_pressure
```

这样客户端可以根据这个信息，决定是否重试、降级自己的功能，或者通知运维人员。

### 三、熔断机制：别让故障蔓延

熔断这个概念来自电路设计——当电流过大时，保险丝熔断，保护整个电路。在 SGLang 服务里，熔断的作用是：当某个下游依赖（比如向量数据库、外部 API）出问题时，快速切断调用，避免雪崩。

#### 3.1 熔断器状态机

一个标准的熔断器有三个状态：

- **关闭（Closed）：** 正常调用，但统计失败率。
- **打开（Open）：** 失败率超过阈值，直接拒绝请求，快速失败。
- **半开（Half-Open）：** 过一段时间后，放少量请求试探，看下游是否恢复。

我曾在项目中用 `pybreaker` 库实现过这个逻辑：

```
import pybreaker

# 配置熔断器：5秒内失败3次就熔断，熔断后等待10秒再试探
breaker = pybreaker.CircuitBreaker(
    fail_max=3,
    reset_timeout=10,
    exclude=[requests.Timeout]  # 超时也算失败
)

@breaker
def call_external_api(prompt):
    # 调用外部知识库或向量数据库
    response = requests.post("http://knowledge-base/search", json={"query": prompt})
    return response.json()
```

**我的建议：** 熔断器的阈值要根据实际流量调整。我见过有人设 fail_max=1，结果网络抖动一下，服务就熔断了半天。建议先设 fail_max=5，观察一段时间再微调。

#### 3.2 与 SGLang 的集成

SGLang 本身没有内置熔断器，但你可以通过自定义中间件来实现。比如在请求进入模型推理前，先检查熔断器状态：

```
from sglang import middleware

class CircuitBreakerMiddleware:
    def __init__(self, breaker):
        self.breaker = breaker
    
    def before_request(self, request):
        if not self.breaker.allow_request():
            return {"error": "service unavailable", "retry_after": 10}
        return None
```

### 四、自动扩缩容：弹性才是王道

流量有高峰有低谷。白天用户多，晚上用户少。如果固定部署 10 个副本，白天可能不够用，晚上又浪费资源。自动扩缩容就是解决这个问题的。

#### 4.1 基于指标的扩缩容

我常用的指标有三个：

- **请求队列长度：** 队列越长，说明处理能力不足，需要扩容。
- **GPU 利用率：** 利用率持续 > 80%，考虑扩容；< 30%，考虑缩容。
- **P99 延迟：** 延迟飙升，说明负载过高。

在 Kubernetes 上，可以用 HPA（Horizontal Pod Autoscaler）实现：

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sglang-server
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sglang-deployment
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Pods
    pods:
      metric:
        name: sglang_queue_length
      target:
        type: AverageValue
        averageValue: 10  # 队列平均长度超过10就扩容
```

#### 4.2 冷启动优化

模型加载很慢，尤其是大模型。如果等流量来了再扩容，用户已经等崩溃了。我建议做两件事：

- **预热（Warm-up）：** 新 Pod 启动后，先发几个 dummy 请求把模型加载到显存里。
- **预留缓冲：** 保持 20% 的冗余容量，应对突发流量。

**踩坑提醒：** 我曾经以为自动扩缩容是万能的。结果有一次流量从 100 QPS 瞬间飙到 1000 QPS，K8s 还没来得及扩容，服务就挂了。后来我加了「提前扩容」策略——当请求队列长度超过 5 时就开始扩容，而不是等到 10。

#### 4.3 缩容保护

缩容时要注意，不能把正在处理请求的 Pod 直接干掉。K8s 的 `terminationGracePeriodSeconds` 可以设置优雅退出时间：

```
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60  # 给 Pod 60 秒处理完当前请求
```

同时，SGLang 支持 `SIGTERM` 信号处理，收到信号后会拒绝新请求，但继续处理已有的请求直到完成。

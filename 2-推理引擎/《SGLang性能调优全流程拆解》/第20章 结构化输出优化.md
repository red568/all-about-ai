## 20. 结构化输出优化：JSON Mode / Grammar 约束下的性能影响、正则表达式编译优化

聊到结构化输出，很多人的第一反应是：“不就是让模型输出个 JSON 嘛，加个 prompt 不就行了？”

嗯，我当年也是这么想的。直到有一次在生产环境里，模型输出的 JSON 格式偶尔会多一个逗号、少一个引号，下游解析直接崩了。那会儿我才意识到—— **靠“提示”约束模型，就像靠“劝说”让熊孩子别捣乱，效果全看运气。**

真正靠谱的方案，是用 **Grammar 约束** 或 **JSON Mode** ，在解码阶段就强制模型只能输出合法结构。但代价呢？性能会受影响。今天我们就来拆解这个 trade-off，以及怎么把损失降到最低。

### 20.1 JSON Mode 与 Grammar 约束：原理与代价

先说说这两者到底干了什么。

常规的 LLM 解码，每一步都是从整个词表里选一个 token。而 JSON Mode 或 Grammar 约束，相当于在每一步解码前，先根据当前已生成的内容，算出一个“合法 token 集合”。模型只能从这个集合里选。

举个例子：如果模型已经输出了 `{"name": "` ，那下一个 token 就不能是 `}` 或数字，只能是字符串内容或转义字符。

```
核心区别：

  JSON Mode：通常只约束顶层结构，保证输出是合法 JSON。内部字段的值类型（比如字符串、数字）可能不严格检查。
  Grammar 约束：用形式文法（如 CFG）定义完整的输出格式。可以精确到每个字段的类型、长度、枚举值。更灵活，但计算开销也更大。
```

性能影响主要来自两个方面：

1. **合法 token 集合的计算** ：每次解码都要跑一遍文法解析，生成当前可用的 token 列表。这个操作本身有 CPU 开销。
2. **采样效率下降** ：合法 token 集合通常远小于完整词表。如果集合太小，模型的选择空间被严重压缩，可能导致“被迫选一个概率很低的 token”，影响生成质量甚至导致死循环。

我在项目中遇到过最极端的情况：一个嵌套 5 层的 JSON Schema，加上枚举值约束，合法 token 集合平均只有 12 个。模型每一步都像在走钢丝，生成速度直接掉了 40%。

### 20.2 正则表达式编译优化：把“运行时”变成“编译时”

说到 Grammar 约束，很多人会想到用正则表达式来定义格式。但正则表达式在解码阶段的实时编译，是性能杀手。

为什么？因为每次解码都要把正则表达式编译成有限状态自动机（FSA），然后根据当前状态计算下一个合法 token。如果正则表达式很复杂（比如包含大量分支、回溯），编译时间可能比解码本身还长。

**我的优化思路：** 把正则表达式的编译提前到“加载模型时”或“第一次使用时”，而不是每次解码都编译。说白了，就是“一次编译，多次复用”。

具体做法：

- 使用 `re.compile()` 预编译正则对象，缓存起来。
- 对于 Grammar 约束，将 CFG 编译成确定有限状态自动机（DFA），并缓存状态转移表。
- 在 SGLang 中，可以利用 `@lru_cache` 或自定义缓存层，避免重复编译。

```
# 示例：预编译正则并缓存
import re
from functools import lru_cache

@lru_cache(maxsize=128)
def get_compiled_regex(pattern: str) -> re.Pattern:
    return re.compile(pattern)

# 在解码循环中使用
pattern = r'^\{[^}]*\}$'
compiled = get_compiled_regex(pattern)
# 用 compiled 来约束解码
```

我曾经在一个项目里，把正则编译从“每次解码”改成“首次缓存”，JSON 模式的解码速度提升了 3 倍。嗯，有时候优化就这么简单——只是把做重复劳动的时间省掉。

### 20.3 性能影响实测：JSON Mode vs Grammar 约束

为了让你有个直观感受，我放一组实测数据。测试环境：单张 A100，模型为 Llama-3-8B，输出长度固定为 512 tokens。

|约束方式|平均解码延迟 (ms/token)|相对无约束的延迟增加|合法 token 平均数量|
|---|---|---|---|
|无约束|12.3|-|32000 (完整词表)|
|JSON Mode (简单)|15.8|+28%|~800|
|JSON Mode (嵌套)|18.2|+48%|~150|
|Grammar 约束 (CFG)|22.7|+85%|~40|
|Grammar 约束 + 预编译 DFA|16.1|+31%|~40|

看到没？ **预编译 DFA 几乎把 Grammar 约束的额外开销砍掉了一半。** 从 +85% 降到 +31%，这个优化幅度，我觉得值得你花半小时改代码。

### 20.4 避坑指南：我踩过的几个坑

讲几个实战中容易翻车的地方：

- **不要用回溯型正则** ：像 `(.*?)` 这种带回溯的表达式，在解码阶段会频繁触发回溯，性能直接崩。尽量用确定性正则，或者转成 DFA。
- **注意 token 边界** ：Grammar 约束是基于 token 级别的，但 JSON 的合法字符是基于字节级别的。如果 tokenizer 把 `"` 和后面的字符合并成一个 token，约束可能失效。我建议用 `byte-level` 的约束，或者用 `character-level` 的 tokenizer。
- **枚举值太多时，考虑用 logit 偏置** ：如果约束只是“从 100 个固定值里选一个”，用 Grammar 约束反而慢。不如直接修改 logits，把非法选项的概率置为 -inf。SGLang 的 `logit_bias` 参数就是干这个的。

**我曾经踩过的一个大坑：** 在一个金融场景里，我用 Grammar 约束强制输出“金额必须为数字且保留两位小数”。结果模型在输出 `123.45` 时，因为 tokenizer 把 `.` 和 `45` 拆成了两个 token，Grammar 在 `.` 之后无法预测下一个 token 必须是数字，导致解码卡死。最后我改用 `byte-level` 约束才解决。

### 20.6 小结

结构化输出不是“加个 prompt 就完事”的活儿。JSON Mode 和 Grammar 约束各有适用场景，但都会带来性能开销。优化的核心思路就两条：

- **减少重复计算** ：把编译、合法集合计算等操作提前做，缓存起来。
- **选择合适的约束粒度** ：能用 logit bias 解决的，就别上 Grammar；能用简单 JSON Mode 的，就别写复杂 CFG。

我个人习惯是： **先跑一次 benchmark，看看无约束下的延迟基线，再逐步加约束，每一步都量化性能影响。** 这样你才知道，你为“格式正确”付出了多少代价，以及这笔买卖划不划算。

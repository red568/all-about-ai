## 第17章 离线批处理优化：大文件批量处理、数据流水线设计、结果聚合优化

离线批处理，说白了就是让SGLang一次性吃掉大量数据，然后乖乖吐出结果。我见过不少团队，在线推理跑得飞起，一到离线批处理就卡成PPT。为什么？因为大家习惯了一个请求一个请求地处理，突然面对成千上万条数据，内存和显存直接爆炸。

我个人习惯把离线批处理拆成三个核心环节： **数据加载** 、 **模型推理** 、 **结果回收** 。每个环节都有坑，咱们一个一个来填。

### 17.1 大文件批量处理：别让I/O卡住GPU

先说说数据加载。你想想看，GPU算得再快，如果数据喂不进去，那就是白搭。我在项目中遇到过最典型的情况：一个10GB的JSON文件，用 `json.load()` 直接读，内存直接飙到20GB+，然后OOM，进程被kill。

正确的做法是什么？ **流式读取** 。

```
import json
import ijson

# 错误示范：一次性加载
with open('huge_data.json', 'r') as f:
    data = json.load(f)  # 内存爆炸

# 正确示范：流式解析
def stream_json(file_path):
    with open(file_path, 'rb') as f:
        parser = ijson.parse(f)
        for prefix, event, value in parser:
            if event == 'map_key':
                # 按需处理
                pass
```

**我的经验：** 对于超大文件，别用标准json库。用ijson或者orjson的流式接口。我试过，内存占用能从20GB降到200MB。

还有一个容易被忽略的点： **文件格式选择** 。JSON虽然通用，但解析慢。如果数据是结构化的，我建议用Parquet格式。它天生支持列式存储和压缩，读取速度能快3-5倍。

|格式|读取速度|内存占用|压缩比|
|---|---|---|---|
|JSON|慢|高|低|
|Parquet|快|低|高|
|CSV|中等|中等|低|

### 17.2 数据流水线设计：让GPU永远不闲着

数据加载搞定了，接下来是流水线设计。核心思想就一句话： **不要让GPU等数据** 。

我刚开始做离线批处理时，用的是最简单的串行模式：读一批数据 -> 推理 -> 写结果 -> 再读下一批。结果GPU利用率只有30%左右，大部分时间在等I/O。

后来我改成了 **双缓冲流水线** 。说白了就是：CPU负责加载下一批数据，GPU同时处理当前批次。两者并行，互不干扰。

```
import threading
import queue

class Pipeline:
    def __init__(self, model, batch_size=32):
        self.model = model
        self.batch_size = batch_size
        self.input_queue = queue.Queue(maxsize=2)  # 双缓冲
        
    def data_loader(self, data_source):
        """CPU线程：持续加载数据"""
        batch = []
        for item in data_source:
            batch.append(item)
            if len(batch) == self.batch_size:
                self.input_queue.put(batch)
                batch = []
        if batch:
            self.input_queue.put(batch)
            
    def run(self, data_source):
        loader = threading.Thread(target=self.data_loader, args=(data_source,))
        loader.start()
        
        results = []
        while True:
            batch = self.input_queue.get()
            if batch is None:
                break
            # GPU推理，此时CPU已经在加载下一批了
            outputs = self.model.generate(batch)
            results.extend(outputs)
        return results
```

```
核心指标：流水线深度不是越深越好。我测试过，深度为2（双缓冲）效果最好。深度超过4，反而因为队列管理开销导致性能下降。
```

嗯，这里要注意一个细节： **批大小（batch size）的选择** 。不是越大越好。我见过有人把batch size设到256，结果显存爆了，反而比128还慢。为什么？因为显存不够，触发了内存交换。

我个人习惯的做法是：先设一个保守值（比如32），然后逐步增大，同时监控显存利用率。找到那个“刚好填满显存”的临界点，那就是最优batch size。

### 17.3 结果聚合优化：别让写结果拖后腿

推理完了，结果怎么存？很多人觉得这步无所谓，随便写个文件就行。但我在项目中遇到过：推理只用了10分钟，写结果用了40分钟。你说气不气人？

结果聚合的优化，核心是 **减少写操作次数** 和 **使用高效序列化** 。

```
import orjson
import numpy as np

# 错误示范：每条结果单独写
for result in results:
    with open('output.jsonl', 'a') as f:
        f.write(orjson.dumps(result).decode() + '\n')  # 频繁打开文件

# 正确示范：批量写入
def batch_write(results, file_path, batch_size=1000):
    with open(file_path, 'wb') as f:
        buffer = []
        for i, result in enumerate(results):
            buffer.append(orjson.dumps(result) + b'\n')
            if (i + 1) % batch_size == 0:
                f.writelines(buffer)
                buffer = []
        if buffer:
            f.writelines(buffer)
```

**我曾经踩过的坑：** 用Python自带的pickle序列化大tensor，速度慢且体积大。后来换成orjson + numpy的tobytes()，速度提升了10倍。记住，序列化选型直接影响I/O性能。

还有一个技巧： **结果去重与排序** 。离线批处理经常会有重复请求（比如用户重复提交了相同数据）。我建议在聚合阶段做一次去重，减少不必要的写操作。

```
from collections import OrderedDict

def dedup_and_sort(results, key_func):
    """去重并排序结果"""
    seen = OrderedDict()
    for r in results:
        key = key_func(r)
        if key not in seen:
            seen[key] = r
    return list(seen.values())
```

### 17.5 避坑指南

最后，分享几个我踩过的坑，希望能帮你少走弯路。

- **显存泄漏：** 每次推理后，记得显式释放中间tensor。我遇到过因为忘记 `del` ，导致显存越用越多，最后OOM。
- **文件句柄泄漏：** 流式读取时，一定要确保文件正确关闭。用 `with` 语句是最安全的。
- **数据倾斜：** 如果数据长度差异很大（比如有的文本100字，有的10万字），batch size要动态调整。我习惯按token数来分batch，而不是按条数。
- **结果乱序：** 多线程写入时，结果顺序可能被打乱。如果下游依赖顺序，记得加一个序号字段。

离线批处理优化，说白了就是 **让每一部分硬件都跑满** 。CPU负责加载，GPU负责推理，磁盘负责存储，三者并行，互不等待。做到这一点，你的离线批处理就能起飞了。

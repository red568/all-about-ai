## 16. 在线推理服务优化：API 接口优化、并发连接管理、超时设置、重试策略

在线推理服务，说白了就是让模型跑在线上，随时响应请求。这跟离线批量推理完全是两码事——离线你可以慢慢跑，在线不行，用户等着呢。

我接手过好几个在线推理项目，踩过的坑真不少。有一次线上服务突然超时飙升，查了半天发现是API接口设计不合理，一个请求卡住，后面全堵死了。嗯，今天就把这些经验掰开揉碎讲给你听。

```
核心要点：在线推理优化的本质，就是在延迟、吞吐、稳定性之间找平衡。API接口、并发连接、超时、重试，这四个点缺一不可。
```

### 16.1 API 接口优化

API接口是服务的门面。设计得好，后面省心；设计得烂，后面全是坑。

**我个人习惯用异步非阻塞接口。** 什么意思？就是请求进来后，不等着模型算完，而是立刻返回一个任务ID，让客户端轮询或者等回调。这样能有效避免连接被长时间占用。

```
# 异步接口示例（FastAPI）
from fastapi import FastAPI, BackgroundTasks
from pydantic import BaseModel

app = FastAPI()

class InferenceRequest(BaseModel):
    prompt: str
    max_tokens: int = 128

class TaskResponse(BaseModel):
    task_id: str
    status: str = "pending"

@app.post("/inference", response_model=TaskResponse)
async def inference(request: InferenceRequest, background_tasks: BackgroundTasks):
    task_id = generate_task_id()
    background_tasks.add_task(run_inference, task_id, request)
    return TaskResponse(task_id=task_id)

@app.get("/result/{task_id}")
async def get_result(task_id: str):
    result = cache.get(task_id)
    if result is None:
        return {"status": "pending"}
    return {"status": "done", "data": result}
```

这里有个细节： **请求体要尽量精简** 。我见过有人把整个对话历史都塞进请求体，一次请求几MB，网络传输就占了大部分时间。其实可以只传关键参数，历史记录放缓存里。

**小技巧：** API接口最好支持批量推理。一次请求传多条prompt，模型内部做batch处理，吞吐能翻好几倍。但要注意控制batch大小，太大反而会拖慢单条延迟。

### 16.2 并发连接管理

并发连接管理，说白了就是控制同时有多少请求在跑。这玩意儿搞不好，服务直接崩。

**我曾经遇到过一个案例：** 某次大促，流量突然暴涨，连接数冲到几千，结果数据库连接池先爆了，然后模型推理也卡死，整个服务雪崩。后来加了连接池限流才稳住。

常用的并发管理手段有这几种：

- **连接池：** 复用TCP连接，避免频繁创建销毁。我一般用 或 的异步连接池，设置最大连接数。
- **信号量限流：** 控制同时进行的推理任务数。比如GPU显存只够同时跑4个任务，那就用信号量卡住第5个。
- **队列缓冲：** 请求进来先放队列，worker从队列取任务。这样能平滑突发流量。

```
# 信号量限流示例
import asyncio

class InferenceServer:
    def __init__(self, max_concurrent=4):
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.model = load_model()
    
    async def handle_request(self, request):
        async with self.semaphore:
            # 只有拿到信号量才能执行推理
            result = await self.model.infer(request)
            return result
```

你想想看，如果没有这个信号量，同时进来10个请求，GPU显存直接爆掉，所有请求都失败。加了限流，最多4个在跑，剩下的排队，虽然慢点但至少不崩。

**注意：** 连接池大小不是越大越好。我见过有人把连接池设成1000，结果后端服务扛不住，反而更慢。一般根据后端处理能力来算，比如模型推理延迟100ms，那单线程每秒能处理10个请求，4个worker就是40个并发。

### 16.3 超时设置

超时设置，看起来简单，其实门道很多。设短了，正常请求被误杀；设长了，资源被僵尸请求占着不放。

**我一般分三层设置超时：**

|层级|超时时间|说明|
|---|---|---|
|网络连接超时|5秒|客户端到服务端的TCP连接建立|
|请求处理超时|30秒|模型推理+前后处理的总时间|
|整体响应超时|60秒|包含排队等待时间|

为什么分三层？因为不同阶段的超时原因不一样。连接超时可能是网络问题，处理超时可能是模型卡住了，整体超时可能是排队太久。分开设置，方便排查问题。

```
# 超时配置示例
import httpx

timeout = httpx.Timeout(
    connect=5.0,    # 连接超时
    read=30.0,      # 读取超时（对应推理时间）
    write=10.0,     # 写入超时
    pool=60.0       # 连接池等待超时
)

async with httpx.AsyncClient(timeout=timeout) as client:
    response = await client.post(url, json=data)
```

**这里有个坑：** 模型推理时间不是固定的。短prompt可能1秒就出结果，长prompt可能要30秒。如果统一设成5秒超时，长prompt全被杀了。我建议根据prompt长度动态调整超时，或者干脆用流式返回，边推理边输出。

### 16.4 重试策略

重试是保证服务可用性的最后一道防线。但重试策略设计不好，反而会加重服务负担。

**我曾经见过一个事故：** 某服务超时后立即重试，结果所有客户端同时重试，直接把后端打挂了。这就是所谓的「重试风暴」。

好的重试策略应该遵循这几个原则：

- **指数退避：** 第一次失败等1秒，第二次等2秒，第三次等4秒...这样能避免集中重试。
- **抖动（Jitter）：** 在退避时间上加随机偏移，防止多个客户端同时重试。
- **最大重试次数：** 一般3-5次就够了，再多也没意义。
- **只重试可恢复的错误：** 比如超时、503服务不可用。4xx的客户端错误不要重试，重试也没用。

```
# 带指数退避和抖动的重试策略
import random
import asyncio

async def retry_with_backoff(coro, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return await coro
        except (TimeoutError, httpx.HTTPStatusError) as e:
            if e.response.status_code in [429, 502, 503, 504]:
                # 只有服务端错误才重试
                delay = base_delay * (2 ** attempt) + random.uniform(0, 0.5)
                await asyncio.sleep(delay)
                continue
            else:
                raise
    raise Exception("Max retries exceeded")
```

**经验之谈：** 重试最好在客户端做，而不是在服务端。服务端重试会占用处理线程，影响其他请求。客户端重试的话，服务端可以专心处理当前请求。

### 16.5 整体架构图

下面这张图展示了在线推理服务的整体优化架构。从客户端请求进来，到最终返回结果，每个环节都有对应的优化手段。

在线推理服务优化架构 客户端 API网关 接口优化/限流 连接管理器 连接池/信号量 推理引擎 模型推理 超时控制（连接超时/处理超时/整体超时） 重试策略（指数退避/抖动/最大次数） 响应返回（含重试逻辑） 优化要点总结： 1. API接口：异步非阻塞、请求体精简、支持批量推理 2. 并发连接：连接池复用、信号量限流、队列缓冲 3. 超时设置：分层超时（连接/处理/整体）、动态调整 4. 重试策略：指数退避+抖动、只重试可恢复错误、客户端重试

这张图把整个优化链路串起来了。客户端请求先经过API网关做接口优化和限流，然后进入连接管理器控制并发，接着到推理引擎执行模型推理。整个过程受超时控制和重试策略保护。一旦某个环节出问题，重试机制会兜底。

**最后提醒一句：** 优化不是一蹴而就的。我建议先做监控，把每个环节的延迟、成功率、并发数都记录下来。然后针对瓶颈做优化，改完再看效果。别一上来就全改，出了问题都不知道是哪一步导致的。

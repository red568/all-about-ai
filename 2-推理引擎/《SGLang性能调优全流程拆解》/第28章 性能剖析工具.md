## 性能剖析工具：Nsight Systems / PyTorch Profiler 使用、火焰图分析、瓶颈定位

性能调优这件事，说白了就是「先找到瓶颈，再动手优化」。没有数据支撑的优化，都是瞎猜。我见过太多人上来就改代码，改完发现根本没跑对地方——GPU 利用率才 30%，你优化 CPU 预处理有啥用？

所以这一章，咱们就聊聊怎么用工具把 SGLang 的「底裤」扒干净。我会重点讲三个东西： **Nsight Systems** 、 **PyTorch Profiler** ，还有 **火焰图** 。这三板斧用好了，瓶颈基本无处可藏。

### Nsight Systems：GPU 层面的「全景相机」

Nsight Systems 是 NVIDIA 官方出的性能分析工具。我个人习惯叫它「全景相机」——因为它能把你整个推理过程里，CPU 和 GPU 各自在干什么、谁在等谁，全部拍下来。

安装很简单，去 NVIDIA 官网下载就行。命令行用法大概是这样：

```
nsys profile -o trace_output -t cuda,nvtx,osrt \
    python -m sglang.bench --model meta-llama/Llama-2-7b-chat-hf
```

跑完之后会生成一个 `.nsys-rep` 文件。用 Nsight Systems GUI 打开，你会看到一条时间轴。嗯，这里要注意： **别被花花绿绿的条条吓到** ，你只需要盯住三个东西：

- **GPU 活动条** ：看它是不是连续在跑，有没有大段空白
- **CPU 活动条** ：看 CPU 是不是在忙着做数据搬运或预处理
- **API 调用条** ：看 cuBLAS、cuDNN 这些库的调用频率

我在项目中遇到过最典型的情况：GPU 利用率只有 40%，但 CPU 那根条几乎拉满了。一查，原来是 tokenizer 预处理太慢，GPU 一直在等数据。这种问题，你光看代码是看不出来的。

```
关键指标：GPU 利用率低于 80% 时，大概率是 CPU 瓶颈或 I/O 瓶颈。别急着优化 kernel，先看看数据流水线。
```

### PyTorch Profiler：细粒度的「手术刀」

Nsight Systems 适合看宏观，但到了算子级别，就得用 PyTorch Profiler 了。它就像一把手术刀，能精确告诉你每个 torch 操作花了多少时间。

用法也很简单，在 SGLang 的推理代码里包一层就行：

```
import torch.profiler as profiler

with profiler.profile(
    activities=[profiler.ProfilerActivity.CUDA, profiler.ProfilerActivity.CPU],
    record_shapes=True,
    with_stack=True
) as prof:
    # 你的推理代码
    output = model.generate(input_ids, max_new_tokens=128)

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
```

输出会按 CUDA 耗时排序，把最耗时的算子列在最前面。我一般会重点关注前 5 个算子——它们往往占了 80% 以上的时间。

举个例子，有一次我发现 `torch.bmm` 占了 60% 的时间。点进去一看，shape 是 `[1, 32, 128] x [1, 128, 4096]` 。这明显是 batch size 太小，矩阵乘法没跑满。后来我把 batch size 从 1 提到 4，吞吐直接翻倍。

**小技巧** ：加上 `record_shapes=True` 参数，可以看到每个算子的输入 shape。很多性能问题，一看 shape 就明白了——比如 attention 的 QKV 投影 shape 不对，导致计算浪费。

### 火焰图：一眼看出「时间都去哪了」

火焰图这东西，最早是 Brendan Gregg 搞出来分析 CPU 性能的。后来被移植到了 GPU 领域。它的原理很简单： **横轴是时间占比，纵轴是调用栈** 。越宽的方块，说明那个函数占的时间越多。

在 SGLang 场景下，我一般用 PyTorch Profiler 导出火焰图数据：

```
prof.export_chrome_trace("trace.json")
```

然后丢到 `chrome://tracing` 或者用 `speedscope` 打开。你会看到类似这样的结构：

```
|-- forward()
    |-- transformer_block()
        |-- attention()
            |-- qkv_projection()   ← 很宽
            |-- scaled_dot_product() ← 很宽
            |-- output_projection()
        |-- mlp()
            |-- gate_proj()        ← 很宽
            |-- up_proj()
            |-- down_proj()
    |-- lm_head()
```

嗯，这里要注意： **火焰图不是越「高」越好** 。如果某个调用栈特别深，说明函数嵌套太多，可能有冗余调用。如果某个方块特别宽，说明那个函数是瓶颈。

我曾经在优化一个 MoE 模型时，发现火焰图上有个叫 `topk_router` 的方块特别宽。点进去一看，原来是用 PyTorch 原生 `topk` 实现的，每次都要排序。后来换成 `torch.argmax` + mask 的方式，直接省了 30% 的时间。

**避坑指南** ：我曾经被火焰图误导过一次。有个函数看起来特别宽，我以为是它慢，优化了半天没效果。后来才发现，是因为它被调用了 10 万次，单次其实很快。所以看火焰图时，记得结合调用次数一起分析。

### 瓶颈定位的「三步法」

工具再多，不会用也是白搭。我总结了一套自己的定位流程，分享给你：

1. **先看宏观** ：用 Nsight Systems 看 GPU 利用率、CPU 利用率、数据搬运时间。如果 GPU 利用率低，先解决流水线问题。
2. **再看算子** ：用 PyTorch Profiler 看 top 耗时算子。如果某个算子占比异常高，检查它的输入 shape 和实现方式。
3. **最后看调用栈** ：用火焰图看函数调用关系。如果某个调用路径特别深或特别宽，考虑重构或替换实现。

这套流程我用了两年，基本没失手过。你想想看，如果第一步就发现 GPU 利用率只有 30%，那你根本不需要去看算子细节——先把数据加载改成异步再说。

## 第15章：日志与监控：性能指标采集、日志级别控制、慢请求追踪

监控和日志，说白了就是系统的「眼睛」和「耳朵」。

我见过太多团队，模型推理跑得飞快，但一遇到线上问题就抓瞎——不知道瓶颈在哪，不知道哪个请求慢了，甚至不知道服务还活着没。嗯，这章我们就来解决这个问题。

### 15.1 性能指标采集：Prometheus + Grafana

我个人习惯，任何生产系统上线前，第一件事就是搭监控。SGLang 原生支持 Prometheus 指标暴露，你只需要打开一个开关。

#### 15.1.1 开启 Prometheus 指标

在启动 SGLang 服务时，加上 `--enable-metrics` 参数：

```
python -m sglang.launch_server \
  --model meta-llama/Llama-2-7b-chat-hf \
  --port 30000 \
  --enable-metrics \
  --metrics-port 30001
```

这样，SGLang 会在 `localhost:30001` 上暴露 `/metrics` 端点。你可以用 curl 验证：

```
curl http://localhost:30001/metrics | head -20
```

你会看到类似这样的输出：

```
# HELP sglang_request_duration_seconds Request duration in seconds
# TYPE sglang_request_duration_seconds histogram
sglang_request_duration_seconds_bucket{le="0.1"} 120
sglang_request_duration_seconds_bucket{le="0.5"} 450
...
```

#### 15.1.2 关键指标解读

我在项目中遇到过，指标太多反而不知道看哪个。这里我列出最核心的几个：

|指标名称|类型|含义|
|---|---|---|
|`sglang_request_duration_seconds`|Histogram|请求延迟分布，看 P50/P95/P99|
|`sglang_request_total`|Counter|总请求数，用于计算 QPS|
|`sglang_batch_size`|Gauge|当前 batch 大小，反映并发压力|
|`sglang_cache_hit_ratio`|Gauge|KV cache 命中率，低于 80% 要警惕|
|`sglang_gpu_memory_used_bytes`|Gauge|显存使用量，接近上限会 OOM|

**我的小技巧：** 重点关注 `sglang_request_duration_seconds` 的 P99 值。如果 P99 突然飙升，说明有长尾请求拖慢了整体性能。

#### 15.1.3 Grafana 仪表盘配置

Prometheus 采集数据，Grafana 负责可视化。我建议你至少建三个面板：

1. **请求延迟面板** ：展示 P50、P95、P99 延迟曲线
2. **吞吐量面板** ：展示 QPS 和并发请求数
3. **资源面板** ：展示显存使用率、GPU 利用率

一个简单的 PromQL 查询示例：

```
# P99 延迟
histogram_quantile(0.99, 
  rate(sglang_request_duration_seconds_bucket[5m])
)

# QPS
rate(sglang_request_total[1m])
```

### 15.2 日志级别控制

日志这东西，多了刷屏，少了查问题找不到。我见过有人把日志级别设成 DEBUG 上线，结果一天写了几百 GB 日志，磁盘直接爆了。

#### 15.2.1 SGLang 日志级别设置

SGLang 使用 Python 标准 logging 模块。你可以通过环境变量控制：

```
# 设置日志级别
export SGLANG_LOG_LEVEL=INFO

# 或者更细粒度
export SGLANG_LOG_LEVEL=WARNING  # 只输出警告和错误
```

支持的级别： `DEBUG` 、 `INFO` 、 `WARNING` 、 `ERROR` 、 `CRITICAL` 。

**避坑指南：** 我曾经在生产环境误开了 DEBUG 级别，结果日志里全是 token 级别的输出，每生成一个 token 就打印一行。QPS 直接掉了 30%。记住：生产环境用 INFO 或 WARNING，DEBUG 只用于本地调试。

#### 15.2.2 日志格式定制

我个人习惯把日志格式改成带时间戳和请求 ID 的，方便追踪：

```
export SGLANG_LOG_FORMAT="%(asctime)s [%(levelname)s] %(request_id)s %(message)s"
```

这样每条日志都带着请求 ID，排查问题时能串起来。

### 15.3 慢请求追踪

慢请求是性能优化的头号敌人。你想想看，99% 的请求都在 100ms 内完成，但总有那么 1% 的请求要花 5 秒。不抓出来，用户体验就是灾难。

#### 15.3.1 开启慢请求日志

SGLang 支持配置慢请求阈值，超过阈值的请求会被单独记录：

```
python -m sglang.launch_server \
  --model meta-llama/Llama-2-7b-chat-hf \
  --slow-request-threshold 2.0  # 超过 2 秒的请求视为慢请求
```

启动后，慢请求会输出到单独的日志文件 `slow_requests.log` ：

```
2025-01-15 10:23:45 [SLOW] request_id=abc123, duration=3.2s, 
  prompt_length=2048, output_length=512, 
  model=Llama-2-7b-chat-hf
```

#### 15.3.2 慢请求根因分析

拿到慢请求日志后，怎么分析？我一般按这个顺序排查：

1. **看 prompt 长度** ：如果 prompt 很长（比如 > 4K），可能是 prefill 阶段耗时
2. **看 output 长度** ：如果 output 很长（比如 > 1K），可能是 decode 阶段累积耗时
3. **看 batch 大小** ：如果当时 batch 很大，可能是排队等待时间长
4. **看显存使用率** ：如果显存接近 100%，可能是显存瓶颈导致 swap

```
核心思路： 慢请求不是随机出现的，它一定有规律。找到规律，就能找到优化方向。
```

#### 15.3.3 自定义慢请求告警

光记录还不够，你得在慢请求出现时立刻知道。我建议用 Prometheus 的 alerting rules：

```
groups:
- name: sglang_alerts
  rules:
  - alert: SlowRequestRateHigh
    expr: rate(sglang_request_duration_seconds_count{le="2.0"}[5m]) < 0.95
    for: 1m
    labels:
      severity: warning
    annotations:
      summary: "慢请求比例超过 5%"
```

这个规则的意思是：如果过去 5 分钟内，只有不到 95% 的请求在 2 秒内完成，就触发告警。

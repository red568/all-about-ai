## 案例实战二：长文本场景（128K Context）下的显存与延迟优化

128K 上下文，说白了就是一次能塞进模型 16 万 tokens 左右的内容。这个量级，我刚开始接触时也觉得夸张——相当于一本 200 页的书。但现实需求摆在那：法律合同审查、超长代码库分析、科研论文综述……用户就是要一口气读完。

问题来了。显存爆炸、延迟飙升，几乎是必然的。我踩过不少坑，今天就把实战中摸索出来的优化路径拆开揉碎讲给你听。

### 一、长文本场景的显存瓶颈在哪？

先看一个简单计算。假设我们用 LLaMA-13B，FP16 精度，单层 KV Cache 的大小是：

```
batch_size = 1
seq_len = 128K
num_heads = 40
head_dim = 128
dtype_size = 2 bytes (FP16)

单层 KV Cache = 2 × batch_size × seq_len × num_heads × head_dim × dtype_size
             = 2 × 1 × 131072 × 40 × 128 × 2
             ≈ 2.68 GB
```

模型有 40 层，所以总 KV Cache 是：

```
总 KV Cache ≈ 2.68 GB × 40 ≈ 107 GB
```

嗯，107 GB。一张 A100 80G 直接爆掉。这还没算模型权重和中间激活。所以， **长文本场景下，KV Cache 是显存的第一杀手** 。

```
核心结论：128K 上下文，不做优化，单张 A100 根本跑不起来。必须从「减少存储」和「减少计算」两个方向下手。
```

### 二、我的优化三板斧

我在实际项目中，针对 128K 长文本场景，总结了三套组合拳。每套都有适用场景，也有代价。

#### 1. 窗口注意力 + 滑动窗口

这个思路很直接：模型不需要记住所有历史 token，只关注最近 N 个 token 就够了。比如设置窗口大小为 4096，那么 KV Cache 就从 128K 降到 4K，显存直接减少 32 倍。

代码实现上，SGLang 支持通过配置参数开启：

```
# SGLang 启动参数示例
python -m sglang.launch_server \
  --model-path /path/to/llama-13b \
  --context-length 131072 \
  --sliding-window-size 4096 \
  --max-num-tokens 4096
```

但注意， **窗口注意力会丢失远距离依赖** 。我遇到过用户反馈「模型记不住文档开头的内容」，就是因为窗口太小。所以，如果你的任务需要全局理解（比如总结全文），这个方法要慎用。

**我的经验** ：窗口大小设为 8192 通常是个不错的折中。既能覆盖大部分局部依赖，又不会让显存爆炸。我曾经在代码补全场景中试过 4096，效果还行；但在法律合同审查中，必须开到 16384 才能准确识别前后条款的矛盾。

#### 2. 稀疏注意力 + 全局 token

这个方案更优雅。它保留少量「全局 token」来捕获长距离信息，其余 token 只做局部注意力。比如，每 128 个 token 中选 1 个作为全局 token，那么全局 token 数量就是 128K / 128 = 1024 个。

这样，KV Cache 的存储量变成：

```
全局 token 的 KV Cache: 1024 × 40 × 2.68 GB / 131072 ≈ 0.84 GB
局部窗口的 KV Cache: 4096 × 40 × 2.68 GB / 131072 ≈ 3.35 GB
总计 ≈ 4.19 GB
```

从 107 GB 降到 4.19 GB，这个优化幅度非常可观。而且，全局 token 的存在保证了模型仍然能「看到」远处的信息。

SGLang 中可以通过自定义 attention 模式实现：

```
# 伪代码示意
from sglang.srt.managers.router.model_runner import ModelRunner

runner = ModelRunner(
    model_path="...",
    attention_mode="sparse",
    sparse_config={
        "global_token_interval": 128,  # 每128个token选1个全局
        "local_window_size": 4096,     # 局部窗口大小
    }
)
```

**注意** ：稀疏注意力需要模型本身支持，或者你在微调阶段就加入这种 attention pattern。否则，直接推理时效果会打折扣。我曾经在未微调的模型上试过，结果生成质量下降了 15% 左右。

#### 3. KV Cache 量化 + 内存卸载

如果前两种方法都不适用（比如你必须保留完整的 128K 上下文），那就只能从「压缩存储」入手。

KV Cache 量化，就是把 FP16 的 key 和 value 压缩成 INT8 甚至 INT4。精度会损失一点，但显存直接减半或减到四分之一。

配合内存卸载（offloading），把部分 KV Cache 放到 CPU 内存中，GPU 只保留最近的热数据。推理时按需加载。

SGLang 支持通过环境变量控制：

```
# 启用 KV Cache 量化到 INT8
export SGLANG_KV_CACHE_DTYPE=int8

# 启用内存卸载，阈值设为 70% 显存占用
export SGLANG_OFFLOAD_THRESHOLD=0.7

python -m sglang.launch_server \
  --model-path /path/to/llama-13b \
  --context-length 131072 \
  --kv-cache-dtype int8 \
  --enable-offload
```

量化后的 KV Cache 大小：

```
INT8 量化后：107 GB / 2 ≈ 53.5 GB
配合卸载：GPU 只保留 70% ≈ 37.5 GB，其余卸载到 CPU
```

这样，单张 A100 80G 就能勉强跑起来了。但延迟会变高，因为 CPU 和 GPU 之间需要频繁传输数据。

**我的建议** ：如果对延迟不敏感（比如离线批量处理），量化+卸载是性价比最高的方案。如果是在线服务，我倾向于用窗口注意力或稀疏注意力，延迟更可控。

### 三、延迟优化：从 30 秒到 3 秒

显存问题解决后，延迟就是下一个拦路虎。128K 上下文，即使显存够，计算量也大得吓人。我分享一个真实案例。

某次线上服务，用户上传了一篇 10 万字的论文，要求模型生成摘要。原始实现，首 token 延迟高达 32 秒。用户直接投诉。

我做了三件事：

1. **预填充（prefill）阶段并行化** ：把 128K tokens 分成多个 chunk，每个 chunk 在单独的 CUDA stream 上并行计算 attention。SGLang 的 `--chunk-prefill-size` 参数可以控制 chunk 大小。
2. **使用 FlashAttention-2** ：这个 kernel 对长序列特别友好，能减少显存读写次数。实测在 128K 长度下，attention 计算快了 3 倍。
3. **动态 batch 调度** ：如果同时有多个请求，不要等所有请求都 prefill 完再 decode。SGLang 支持「prefill 一个，decode 一个」的流水线模式，能显著降低平均延迟。

优化后的启动命令：

```
python -m sglang.launch_server \
  --model-path /path/to/llama-13b \
  --context-length 131072 \
  --chunk-prefill-size 8192 \
  --enable-flash-attention \
  --enable-dynamic-batch
```

结果：首 token 延迟从 32 秒降到 2.8 秒。用户满意了。

### 四、实战避坑指南

最后，分享几个我踩过的坑：

- **不要盲目开大窗口** ：我曾经为了「保证效果」，把滑动窗口开到 65536，结果显存直接 OOM。后来发现，对于大多数任务，8192 窗口 + 全局 token 的效果已经足够。
- **量化后要验证精度** ：INT8 量化 KV Cache 后，生成结果和 FP16 版本对比，BLEU 分数下降不超过 2% 才算合格。我遇到过下降 8% 的情况，最后发现是量化参数没调好。
- **内存卸载的带宽瓶颈** ：CPU 和 GPU 之间的 PCIe 带宽有限。如果卸载太多，每次 decode 都要从 CPU 拉数据，延迟反而更高。我一般控制卸载比例在 30% 以内。
- **长文本的 prompt 工程也要改** ：128K 上下文里，关键信息可能分散在各处。我建议在 prompt 中明确告诉模型「请关注第 X 段和第 Y 段的内容」，而不是让它自己大海捞针。

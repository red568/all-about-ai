## 网络优化：gRPC vs HTTP 协议选择、连接池配置、数据压缩、RDMA 支持

聊到 SGLang 的网络优化，我其实挺有感触的。早期做推理服务时，大家总觉得「模型快就行了」，网络那点延迟算什么？结果呢？模型推理 50ms，网络传输 30ms，用户感知到的延迟直接翻倍。说白了，网络这块要是没优化好，GPU 再快也白搭。

今天咱们就掰开揉碎，聊聊 SGLang 里的网络优化四板斧：协议选择、连接池、数据压缩、还有 RDMA 支持。嗯，这四块搞定了，你的服务延迟至少能砍掉一半。

### gRPC vs HTTP：选谁？

先说说协议选择。SGLang 内部通信，我个人的习惯是： **节点间用 gRPC，对外暴露用 HTTP** 。为什么这么分？

**gRPC 的优势很明显：**

- **基于 HTTP/2** ：多路复用、头部压缩，连接复用率高。我在项目中遇到过，同样传输 1000 个请求，gRPC 的连接数只有 HTTP/1.1 的十分之一。
- **Protobuf 序列化** ：二进制格式，体积小、解析快。相比 JSON，体积能小 60% 以上。
- **流式传输** ：SGLang 的推理结果往往是流式返回的，gRPC 的 Server Streaming 天然支持，不用自己搞轮询。

**但 HTTP 也不是一无是处：**

- **调试方便** ：curl 直接测，不用装 grpcurl。
- **生态兼容** ：很多前端、网关只认 HTTP。
- **无状态** ：适合做负载均衡的入口。

```
我的建议：
内部微服务之间（比如 SGLang Router 到 Worker）用 gRPC。对外 API 用 HTTP + JSON，或者用 gRPC-Web 桥接。别混用，否则维护成本翻倍。
```

### 连接池配置：别让连接成为瓶颈

连接池这东西，很多人不重视。默认配置一用到底，结果高并发时连接不够用，低并发时连接又闲置。我踩过这个坑。

在 SGLang 里，gRPC 客户端默认使用 `grpc-go` 的连接池。关键参数就几个：

|参数|说明|推荐值|
|---|---|---|
|`MaxConcurrentStreams`|单个连接上的最大并发流数|100-200|
|`InitialConnWindowSize`|初始连接窗口大小（流量控制）|64KB - 1MB|
|`InitialWindowSize`|初始流窗口大小|64KB|
|`KeepaliveTime`|心跳间隔|30s|
|`KeepaliveTimeout`|心跳超时|10s|

我曾经遇到过一个场景：SGLang 集群 32 个 Worker，Router 到 Worker 的 gRPC 连接数只有 4 个。结果高并发时，单个连接上的流数飙到 500+，直接触发 gRPC 的流控限制，请求排队。后来我把连接数调到 16，每个连接限制 100 个流，问题就解决了。

**避坑指南：**

我曾经以为连接池越大越好，结果发现连接数太多会导致内存占用飙升。每个 gRPC 连接大约占用 1-2MB 内存，1000 个连接就是 1-2GB。所以， **连接数 = 预期并发 / 每个连接的最大流数** ，这个公式要记住。

### 数据压缩：小体积，大收益

数据压缩是性价比最高的优化手段。没有之一。

SGLang 传输的数据主要是：

- **请求数据** ：Prompt 文本、图像（多模态）
- **响应数据** ：生成的 Token 序列、概率分布
- **中间状态** ：KV Cache 的传输（分布式推理时）

对于文本类数据，gRPC 默认支持 **gzip 压缩** 。我测试过，压缩率能达到 5:1 到 10:1。但要注意，压缩和解压是有 CPU 开销的。

```
// gRPC 客户端启用压缩
import "google.golang.org/grpc/encoding/gzip"

conn, err := grpc.Dial(
    address,
    grpc.WithDefaultCallOptions(grpc.UseCompressor(gzip.Name)),
)

// 或者按请求级别控制
client.Call(ctx, request, grpc.UseCompressor(gzip.Name))
```

**什么时候该压缩？**

- Prompt 长度 > 1024 tokens：压缩收益明显
- 网络带宽受限：比如跨机房、跨地域部署
- 传输图像数据：用 JPEG/WebP 压缩，别用 PNG

**什么时候不该压缩？**

- 短 Prompt（< 128 tokens）：压缩后反而更大
- CPU 资源紧张：压缩会占用 CPU 时间片
- 内网高速互联：延迟优先于带宽

**注意：**

gRPC 的 gzip 压缩是全局的。如果你有的请求需要压缩，有的不需要，建议在应用层自己做判断。我见过有人把所有请求都压缩，结果小请求延迟反而增加了 20%。

### RDMA 支持：终极加速方案

RDMA（Remote Direct Memory Access）是网络优化的终极形态。说白了，就是让数据直接从一台机器的内存搬到另一台机器的内存， **不经过 CPU 和内核网络栈** 。

在 SGLang 里，RDMA 主要用于：

- **KV Cache 传输** ：分布式推理时，不同 GPU 之间需要共享 KV Cache
- **模型参数同步** ：多节点训练或推理时的参数广播
- **Tensor 传输** ：流水线并行时的中间结果传递

RDMA 的实现方式主要有两种：

|方式|延迟|带宽|CPU 占用|适用场景|
|---|---|---|---|---|
|InfiniBand|~1μs|200-400 Gbps|极低|高性能计算集群|
|RoCE v2|~3μs|100-200 Gbps|低|以太网环境|
|TCP (对比)|~50μs|10-100 Gbps|高|通用场景|

我参与过一个项目，SGLang 集群用 InfiniBand 互联。KV Cache 传输延迟从 200μs 降到了 5μs，推理吞吐提升了 3 倍。代价是什么？硬件成本翻倍。所以 RDMA 不是银弹，你得算账。

```
RDMA 在 SGLang 中的配置要点：

  网卡绑定：确保 GPU 和 RDMA 网卡在同一 NUMA 节点
  内存注册：提前注册 GPU 显存到 RDMA 区域
  QP 数量：每个 GPU 对之间至少 2 个 QP（一个发送，一个接收）
  中断合并：减少中断频率，提升吞吐
```

如果你没有 RDMA 硬件，也别灰心。用 **NVLink + NVSwitch** 也能达到类似效果。NVLink 的带宽是 PCIe 的 5-10 倍，延迟也更低。SGLang 对 NVLink 有原生支持，配置起来比 RDMA 简单多了。

## 编译优化：Torch Compile / XLA 集成、图捕获优化、JIT 编译预热

说到 SGLang 的性能调优，编译优化这块儿，我个人的经验是： **它决定了你的模型到底能跑多快** 。很多人觉得模型加载完就完事了，其实不然。你想想看，PyTorch 默认是 eager 模式，一条指令执行一次，中间有大量的 Python 解释器开销。而编译优化的核心，就是把这种「边解释边执行」变成「先编译再执行」。

说白了，就是让 GPU 少等你。

### Torch Compile 集成：动态图的「静态化」

Torch Compile 是 PyTorch 2.x 引入的重磅特性。我刚开始接触时也觉得它有点玄乎，不就是加了个 `@torch.compile` 装饰器吗？后来在项目中调优一个 LLM 推理服务，发现同样的模型，加上这个装饰器后，吞吐量提升了 30% 以上。

它的原理其实不复杂： **把 Python 级别的动态计算图，编译成静态的、可优化的计算图** 。SGLang 在集成 Torch Compile 时，主要做了两件事：

- **图捕获** ：把模型的前向传播过程，捕获成一个完整的计算图
- **图优化** ：对捕获到的图进行算子融合、内存优化等操作

嗯，这里要注意一个坑。Torch Compile 对动态 shape 的支持并不完美。我在项目中遇到过，输入序列长度变化太大时，Torch Compile 会频繁重新编译，反而拖慢速度。解决办法是： **限制输入长度到固定的几个 bucket** ，比如 512、1024、2048，让编译结果可以复用。

```
核心要点：Torch Compile 不是银弹。它最适合那些计算密集、且输入 shape 相对稳定的场景。如果你的服务输入长度变化极大，建议先做 padding 或 bucket 处理。
```

### XLA 集成：Google 的编译利器

XLA（Accelerated Linear Algebra）是 Google 推出的深度学习编译器。它和 Torch Compile 的思路类似，但实现方式不同。XLA 会把计算图编译成高效的、针对特定硬件的机器码。

SGLang 集成 XLA 时，我印象最深的是它对 TPU 的支持。如果你在 Google Cloud TPU 上部署 SGLang，XLA 几乎是必选项。它能把计算图中的冗余操作全部消除掉。

举个例子，一个简单的注意力计算，在 PyTorch eager 模式下可能包含 10 多个小算子。XLA 编译后，可能就变成了 3-4 个融合后的算子。GPU 执行起来，自然快得多。

**个人建议** ：如果你在 GPU 上跑，优先尝试 Torch Compile。如果你在 TPU 上跑，或者需要跨平台部署，XLA 是更好的选择。我在一个多平台部署的项目中，同时用了两者，效果都不错。

### 图捕获优化：让编译器「看」得更清楚

图捕获是编译优化的第一步，也是最关键的一步。你想想看，如果编译器连你的计算图都看不全，它怎么优化？

SGLang 的图捕获优化，主要解决两个问题：

- **控制流处理** ：模型中的 if-else、循环等控制流，在 eager 模式下很容易执行，但在图捕获时就成了难题。SGLang 通过 `torch.jit.script` 或 `torch.jit.trace` 来处理这些控制流。
- **动态 shape 处理** ：LLM 的输入长度是动态的，图捕获时不能假设固定 shape。SGLang 的做法是： **用 symbolic shape 替代具体数值** ，让编译器在编译时就知道哪些维度是可变的。

我曾经踩过一个坑：在捕获一个带有 `torch.where` 的模型时，图捕获失败了。排查了半天，发现是 `torch.where` 的 condition 依赖于输入数据，导致图捕获无法确定分支。解决办法是： **把 condition 计算移到图外** ，或者用 `torch.cond` 替代。

**避坑指南** ：图捕获时，尽量避免在模型内部使用 Python 原生的 if-else。改用 `torch.where` 、 `torch.cond` 等 PyTorch 内置的控制流操作。否则，编译器可能会「卡住」。

### JIT 编译预热：别让第一次请求「裸奔」

JIT（Just-In-Time）编译，说白了就是「用到的时候再编译」。但这里有个问题： **第一次编译很慢** 。如果你在线上服务中，第一个请求进来时才编译，那这个请求的延迟会非常高。

我遇到过最夸张的一次：一个模型在第一次推理时，JIT 编译花了 30 秒。用户直接超时了。从那以后，我养成了一个习惯： **服务启动时，先跑一次预热推理** 。

SGLang 的 JIT 编译预热，通常包含以下步骤：

1. **模拟输入** ：构造一批与真实请求 shape 相同的 dummy 数据
2. **触发编译** ：用 dummy 数据跑一次推理，触发 JIT 编译
3. **缓存结果** ：把编译后的结果缓存起来，后续请求直接复用

代码示例：

```
import torch
import sglang as sgl

# 加载模型
model = sgl.load_model("meta-llama/Llama-2-7b-chat-hf")

# 预热：构造 dummy 输入
dummy_input = torch.randint(0, 32000, (1, 512))
dummy_attention_mask = torch.ones(1, 512)

# 触发 JIT 编译
with torch.no_grad():
    _ = model(dummy_input, attention_mask=dummy_attention_mask)

print("JIT 编译预热完成，可以处理真实请求了")
```

**小技巧** ：预热时的输入 shape，最好覆盖你线上最常见的几种 shape。比如你的服务主要处理 512 和 1024 长度的输入，那就分别预热一次。这样编译缓存可以覆盖大部分请求。

### 总结

编译优化这块，说白了就是「用编译时间换运行时间」。Torch Compile 和 XLA 是两种主流方案，各有优劣。图捕获是基础，JIT 预热是保障。

我个人习惯是： **先做图捕获优化，再做 JIT 预热，最后根据硬件选择 Torch Compile 或 XLA** 。这个顺序，能让你在最短时间内看到效果。

嗯，最后提醒一句：编译优化不是万能的。如果你的模型本身就有严重的计算瓶颈，比如 attention 计算量过大，那编译优化能带来的提升有限。这时候，你可能需要先做模型层面的优化，比如量化、剪枝等。

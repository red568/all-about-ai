## 8. 显存优化：显存碎片整理、KV Cache 复用、Swap 策略（CPU Offloading）

显存优化，说白了就是跟 GPU 的「钱包」过不去。你想想看，一张 A100 80G 的卡，跑个大模型推理，动不动就 OOM。我刚开始做 SGLang 部署时，就吃过这个亏——明明显存还有 10 多个 G，结果报错说分配失败。后来一查，是显存碎片化太严重了。

这一章，我带你拆解三个核心手段： **显存碎片整理** 、 **KV Cache 复用** 、 **Swap 策略（CPU Offloading）** 。这三板斧用好了，显存利用率能提升 30% 以上。

### 8.1 显存碎片整理：别让显存变成「蜂窝煤」

显存碎片，就像你手机内存用久了会卡一样。频繁申请和释放不同大小的显存块，会导致空闲显存不连续。大块请求来了，明明总量够，但就是分配不出来。

```
核心思路：SGLang 使用 RadixTree 管理 KV Cache 的显存分配。每次分配时，优先从空闲链表中找大小最合适的块（Best-fit）。如果碎片太多，就触发一次「显存整理」——把已分配的块挪到一起，合并空闲区域。
```

我在项目中遇到过一个问题：连续跑 1000 次推理后，显存碎片率高达 40%。后来我加了个定时整理策略，每 200 次请求触发一次 `defrag()` ，碎片率直接降到 5% 以下。

**避坑指南** ：我曾经在整理时没暂停请求，结果出现数据竞争。后来我改用「双缓冲」——整理时用一块临时显存做中转，整理完再切回来。嗯，这个坑踩得值。

#### 8.1.1 碎片整理的触发时机

- **分配失败时** ：尝试整理后再分配，如果还失败，才报 OOM。
- **定时触发** ：比如每 N 次请求或每 T 秒整理一次。
- **空闲时整理** ：利用 GPU 空闲的间隙做后台整理。

### 8.2 KV Cache 复用：让显存「一鱼多吃」

KV Cache 复用，是 SGLang 最亮眼的设计之一。说白了，就是多个请求共享同一个前缀的 KV Cache，避免重复计算和重复存储。

举个例子：两个用户都问「如何用 Python 写一个 Web 服务器」，前半段「如何用 Python」的 KV Cache 完全可以复用。我见过一个场景，复用率高达 70%，显存占用直接砍半。

#### 8.2.1 复用的实现机制

SGLang 用 `RadixTree` 来索引所有 KV Cache 块。每个请求进来时，先查树，看有没有匹配的前缀。如果有，直接复用已有的 KV Cache，只计算新增的部分。

```
# 伪代码示意
def allocate_kv_cache(request_tokens):
    prefix_node = radix_tree.longest_prefix_match(request_tokens)
    if prefix_node:
        # 复用已有的 KV Cache
        reused_cache = prefix_node.kv_cache
        new_tokens = request_tokens[len(prefix_node.tokens):]
        new_cache = compute_kv_cache(new_tokens)
        return merge_cache(reused_cache, new_cache)
    else:
        return compute_kv_cache(request_tokens)
```

**注意** ：复用不是万能的。如果前缀匹配太短（比如只有 1-2 个 token），复用的收益很小，反而增加了查找开销。我一般建议设置一个最小复用长度，比如 8 个 token。

### 8.3 Swap 策略（CPU Offloading）：把显存「搬」到内存

当显存实在不够用时，就得把一部分 KV Cache 挪到 CPU 内存里。这就是 Swap 策略，也叫 CPU Offloading。

你想想看，CPU 内存便宜啊，DDR5 动辄 128G、256G。但代价是 PCIe 带宽有限，搬来搬去会拖慢推理速度。所以，Swap 策略的核心是： **什么时候搬？搬多少？搬哪些？**

#### 8.3.1 三种常见的 Swap 策略

|策略|原理|适用场景|我踩过的坑|
|---|---|---|---|
|LRU（最近最少使用）|把最久没被访问的 KV Cache 块换出|长序列推理，访问模式有局部性|曾经 LRU 换出了即将被复用的块，导致频繁换入换出|
|LFU（最不经常使用）|把访问频率最低的块换出|前缀复用率高的场景|频率统计有滞后性，新来的热点块容易被误换|
|Size-based（按大小）|优先换出最大的块，腾出连续空间|显存碎片严重时|大块换出后，小块依然碎片化，治标不治本|

我个人习惯用 **LRU + 大小混合策略** ：先按 LRU 选候选块，再从中挑最大的换出。这样既考虑了访问频率，又能快速腾出大块连续显存。

#### 8.3.2 Swap 的异步化

Swap 操作是 I/O 密集型的。如果同步做，推理线程会被卡住。SGLang 的做法是：用独立的 CPU 线程做异步 Swap，GPU 这边继续算，两边流水线并行。

```
# 异步 Swap 示意
async def swap_out(kv_cache_block):
    # 把 KV Cache 从 GPU 拷贝到 CPU
    await cuda_memcpy_async(kv_cache_block, cpu_buffer, direction="GPU2CPU")
    # 释放 GPU 显存
    gpu_memory.free(kv_cache_block)
```

**小技巧** ：我曾经把 Swap 的粒度设得太细（每个 token 单独搬），结果 PCIe 带宽被小包传输浪费了。后来改成按「页」搬（每页 256 个 token），吞吐量提升了 3 倍。

### 8.5 实战建议

最后，给你几个我压箱底的建议：

1. **先复用，再整理，最后 Swap** 。复用的收益最高，Swap 的代价最大。别一上来就开 Swap。
2. **监控碎片率** 。我习惯在日志里打印 `fragmentation_ratio` ，超过 20% 就触发整理。
3. **Swap 的带宽要算清楚** 。PCIe 4.0 x16 的理论带宽是 32GB/s，但实际只有 20GB/s 左右。搬 1GB 数据就要 50ms，别搬太多。
4. **测试时用不同序列长度** 。我见过一个案例，短序列时一切正常，长序列一来就 OOM。因为短序列的碎片问题不明显。

```
一句话总结：显存优化不是玄学，是工程。碎片整理保连续，KV 复用省空间，Swap 策略兜底。这三招练好了，80G 的卡能当 100G 用。
```

## 第24章：高并发场景调优：吞吐量 vs 延迟权衡、请求合并与自适应批处理

高并发场景下，SGLang 的性能调优其实就是在走钢丝。一边是吞吐量，一边是延迟，你压下去一头，另一头就翘起来。我做了这么多年推理优化，坦白讲，没有银弹。但有一些实战中摸出来的套路，今天跟你聊聊。

### 吞吐量 vs 延迟：这不是选择题，是平衡术

先搞清楚这两个指标到底在说什么。

- **吞吐量** ：单位时间内能处理多少请求。比如每秒处理 1000 个请求。
- **延迟** ：单个请求从发起到返回花了多久。比如 200 毫秒。

你想想看，如果我把批处理 size 拉到最大，GPU 利用率确实上去了，吞吐量也漂亮。但排在后面的请求就得等，延迟直接飙升。反过来，如果每个请求都单独处理，延迟是低了，但 GPU 空转严重，吞吐量惨不忍睹。

我在项目中遇到过一位客户，他们要求 P99 延迟必须低于 100ms，同时吞吐量要超过 500 req/s。一开始他们死磕延迟，把 batch size 压到 1，结果吞吐量只有 80 req/s。后来我帮他们调了自适应批处理，才把两边都稳住。

```
核心原则：不要追求单一指标的最优，而是找到业务容忍范围内的最佳平衡点。
```

### 请求合并（Request Merging）：把碎片拼起来

高并发下，请求是源源不断涌进来的。如果每个请求都独立走一遍推理流程，那效率太低了。请求合并，说白了就是把多个小请求拼成一个批次，一次性喂给模型。

但这里有个坑——请求不是同时到达的。你等不等？等多久？

我习惯用 **动态合并窗口** 来解决。举个例子：

```
# 伪代码：动态合并策略
class RequestMerger:
    def __init__(self, max_batch_size=32, max_wait_ms=50):
        self.max_batch_size = max_batch_size
        self.max_wait_ms = max_wait_ms
        self.pending = []
    
    def add_request(self, req):
        self.pending.append(req)
        # 条件1：批次满了，立即执行
        if len(self.pending) >= self.max_batch_size:
            return self.flush()
        # 条件2：等待超时，也得执行
        if self._wait_time() > self.max_wait_ms:
            return self.flush()
        # 否则继续等
        return None
    
    def flush(self):
        batch = self.pending[:]
        self.pending.clear()
        return self._infer(batch)
```

这里有两个参数很关键： `max_batch_size` 和 `max_wait_ms` 。前者控制最大合并量，后者控制最长等待时间。我曾经在一个实时翻译服务里，把 `max_wait_ms` 设成 30ms，结果 P99 延迟从 200ms 降到了 80ms，吞吐量还翻了一倍。

**小技巧** ：如果请求的 token 长度差异很大，合并前先按长度排序。这样可以减少 padding 浪费，GPU 利用率更高。

### 自适应批处理：让系统自己动脑子

固定 batch size 的问题在于——它不会变通。流量高峰时，你设的 batch size 可能太小，浪费算力；流量低谷时，又可能太大，让请求等太久。

自适应批处理，就是让系统根据实时负载动态调整 batch size。我常用的策略是 **PID 控制器** 的思路：

```
# 自适应批处理：基于延迟反馈调整
class AdaptiveBatcher:
    def __init__(self, target_latency_ms=100):
        self.target_latency = target_latency_ms
        self.current_batch_size = 1
        self.kp = 0.1  # 比例系数
    
    def adjust(self, actual_latency_ms):
        error = self.target_latency - actual_latency_ms
        # 如果实际延迟低于目标，可以增大 batch
        if error > 0:
            self.current_batch_size = min(
                self.current_batch_size + int(self.kp * error),
                self.max_batch_size
            )
        # 如果延迟超标，减小 batch
        else:
            self.current_batch_size = max(
                self.current_batch_size - int(self.kp * abs(error)),
                1
            )
        return self.current_batch_size
```

嗯，这里要注意：PID 的参数需要根据实际场景调。我刚开始用的时候， `kp` 设得太大，导致 batch size 来回震荡，系统很不稳定。后来改成小步快跑，每次只调 1-2 个，效果就好多了。

**避坑指南** ：我曾经在生产环境里遇到过一个问题——自适应批处理在流量突增时反应太慢，导致延迟瞬间飙升。后来我加了一个「紧急降级」逻辑：如果连续 3 个请求的延迟都超过阈值，直接强制把 batch size 砍半。这个机制救了我好几次。

### 三者如何协同工作？

请求合并、自适应批处理、吞吐量-延迟权衡，这三者不是孤立的。我画了一张图，帮你理清它们的关系：

高并发调优核心逻辑 请求流 请求合并 动态窗口 + 排序 自适应批处理 PID 动态调整 推理 延迟反馈 吞吐量 vs 延迟权衡引擎 根据业务 SLA 动态调整合并窗口和 batch size 关键参数调优建议： • 合并窗口：延迟敏感场景设 10-30ms，吞吐优先场景设 50-100ms • Batch size：从 1 开始，每次 +2 或 +4，观察延迟变化 • PID 系数：kp 建议 0.05-0.2，太大容易震荡

从图上你能看到，请求先进入合并模块，攒够一批后交给自适应批处理。自适应批处理根据推理延迟的反馈，动态调整 batch size。而整个系统的目标，就是满足你设定的吞吐量-延迟权衡策略。

### 实战中的调优步骤

如果你现在就要上手调优，我建议按这个顺序来：

1. **先定 SLA** ：明确你的业务能接受的最大延迟是多少，目标吞吐量是多少。
2. **从单请求开始** ：测出单请求的基线延迟，这是你的下限。
3. **逐步增大 batch** ：每次翻倍，观察延迟和吞吐量的变化曲线。
4. **找到拐点** ：当延迟开始非线性增长时，那个 batch size 就是你的上限。
5. **加入自适应** ：把拐点附近的 batch size 作为初始值，让 PID 控制器微调。
6. **压力测试** ：用真实流量模拟高并发，观察 P50、P95、P99 延迟。

```
我的经验：很多人在第 3 步就放弃了，觉得手动调太麻烦。但说实话，没有基线数据，自适应算法就是盲人摸象。我每次调优，都会先跑一遍全量测试，把数据记录下来。这些数据后面还能用来训练预测模型，实现更智能的调度。
```

### 总结一下

高并发场景下的调优，说白了就是三个字： **懂取舍** 。请求合并帮你攒批次，自适应批处理帮你动态调整，而吞吐量-延迟权衡是你的决策指南。这三者配合好了，你的 SGLang 服务才能在流量洪峰中稳如泰山。

记住，没有完美的配置，只有适合你业务的配置。多测、多调、多观察，慢慢你就能找到那个「甜点」。

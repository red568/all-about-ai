## 分布式推理：多节点部署的艺术

分布式推理，说白了就是把一个大模型拆开，让多台机器一起干活。我刚开始接触这个领域时，总觉得不就是把模型分一分嘛，有什么难的？结果第一次部署就踩了坑——通信延迟直接把推理速度拖成了龟速。今天咱们就来聊聊，怎么把分布式推理玩明白。

### 多节点部署：从单机到集群的跨越

单机部署就像一个人搬砖，力气再大也有限。多节点部署就是叫来一群人，分工协作。但问题来了——怎么分？

我个人习惯把部署策略分成两类：

- **数据并行** ：每个节点存一份完整模型，处理不同数据。适合高吞吐场景。
- **模型并行** ：每个节点存模型的一部分，共同处理一份数据。适合超大模型。

在实际项目中，我遇到过最头疼的问题就是节点间通信。你想想看，如果两个节点之间要频繁交换数据，网络带宽就成了瓶颈。我曾经在一个8节点集群上跑175B模型，结果发现60%的时间都花在了等待数据上。

```
核心原则：多节点部署时，计算时间要远大于通信时间，否则分布式就失去了意义。
```

### Tensor Parallelism 调优：切分张量的学问

Tensor Parallelism（TP）是把一个张量操作切分到多个设备上。比如矩阵乘法，可以按行切分，也可以按列切分。

我常用的切分策略是这样的：

|切分方式|适用场景|通信量|
|---|---|---|
|行切分|前向传播中的线性层|中等|
|列切分|注意力机制中的QKV投影|较大|
|混合切分|Transformer块整体|高|

调优TP时，我建议重点关注两个参数：

- **tp_size** ：TP的并行度。一般设为2的幂次，比如2、4、8。
- **通信后端** ：NCCL还是GLOO？NCCL在GPU间通信更快，但配置更复杂。

**我的经验** ：在A100集群上，tp_size=8时性能最佳。超过8后，通信开销开始反超计算收益。

### Pipeline Parallelism 调优：流水线里的平衡术

Pipeline Parallelism（PP）是把模型按层切分，每个节点负责连续几层。就像工厂流水线，每个工位只做一道工序。

调优PP的核心是解决两个问题：

1. **负载均衡** ：每个节点的计算量要差不多。我曾经见过一个案例，某节点负责的层数少但计算量大，结果成了瓶颈。
2. **气泡率** ：流水线启动和结束时的空闲时间。气泡率越低，效率越高。

我常用的调优手段：

- 使用1F1B（一个前向一个反向）调度策略，减少气泡
- 调整micro-batch大小，让流水线更饱满
- 对计算量大的层做二次切分

**注意** ：PP的调优不是线性的。我曾经把pp_size从4调到8，结果吞吐量只提升了10%，因为通信开销吃掉了大部分收益。

### 通信瓶颈分析：找到拖后腿的环节

分布式推理的瓶颈，十有八九出在通信上。怎么分析？我一般用三步法：

**第一步：打点测量**

在关键通信节点插入计时器，记录每次通信的耗时。SGLang自带的profiling工具就很好用。

```
# 伪代码示例
start = time.time()
all_reduce(tensor)
comm_time = time.time() - start
print(f"通信耗时: {comm_time:.3f}s")
```

**第二步：对比理论带宽**

比如你的节点间是100Gbps网络，理论传输1GB数据需要0.08秒。如果实际耗时0.2秒，说明有瓶颈。

**第三步：定位具体原因**

- 网络带宽不足？升级网卡或减少通信量
- 通信模式不合理？改用异步通信
- 拓扑结构问题？检查节点间物理连接

```
避坑指南：我曾经遇到一个案例，通信耗时忽高忽低。排查了半天，发现是某个节点的网卡驱动版本不对。升级驱动后，通信时间直接降了40%。
```

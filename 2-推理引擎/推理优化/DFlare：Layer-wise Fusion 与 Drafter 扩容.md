## 课程定位

本课把 DFlare：Layer-wise Fusion 与 Drafter 扩容放回真实请求链路中讨论，中心问题为“如何突破 DFlash 的共享条件瓶颈并判断更深 Drafter 是否值得？”。DFlare Drafter 扩容和 Layer-wise Fusion 提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 DFlare Drafter 扩容的局部理想收益直接当成端到端结果。

本课先用 CPU 模拟控制 DFlare Drafter 扩容和 Layer-wise Fusion，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界。这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 学习目标

1. 准确解释 DFlare Drafter 扩容、Layer-wise Fusion 和条件信息瓶颈之间的状态与资源关系。
2. 使用“NetGain(L) = SavedVerify(L) - DraftCompute(L) - FusionTraffic(L)”建立可计算的收益边界并解释全部变量。
3. 围绕分层特征读取量、Drafter 延迟、接受长度和净收益拐点设计可复现实验。
4. 识别融合层过多导致内存带宽饱和、Drafter 更准但净延迟上升和层间特征尺度不一致等典型失败模式。
5. 对“如何突破 DFlash 的共享条件瓶颈并判断更深 Drafter 是否值得？”给出包含适用条件、证据、风险和回滚的工程答案。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：不是所有 Draft Layer 都该吃同一份压缩信息

假设 Target 提供多层 feature：

$$
H=\{h^{(l_1)},h^{(l_2)},...,h^{(l_m)}\}
$$

一种简单做法先融合成：

$$
z=Fusion(H)
$$

然后所有 Draft Layer 都使用同一个 $z$ ：

```
Target layers → One Fused Feature
                   ↓
Draft L1 → Draft L2 → Draft L3 → Draft L4
```

当 Drafter 很浅时这可能足够。

当 Drafter 变深时，不同层可能需要不同层级信息。如果所有层看到同一个“窄瓶颈”，新增 capacity 未必能有效发挥。

### Layer-wise Fusion

更一般地，第 $j$ 个 Draft Layer 使用：

$$
z_j=\sum_i \alpha_{j,i}P_i(h^{(l_i)})
$$

其中：

- $P_i$ ：把不同 Target layer 投影到兼容空间；
- $\alpha_{j,i}$ ：第 $j$ 个 Draft layer 对不同 Target layer 的可学习权重。

于是：

```
Target L_a ─┬─→ Fusion_for_D1 → Draft1
Target L_b ─┼─→ Fusion_for_D2 → Draft2
Target L_c ─┼─→ Fusion_for_D3 → Draft3
Target L_d ─┴─→ Fusion_for_D4 → Draft4
```

不同 Draft 层不再被迫使用完全相同的 Target 条件。

### 为什么“更深”可能提高 Acceptance

Block parallel prediction 的难点是未来位置缺少逐 token 的真实条件。

增加 Drafter depth 可以提升：

- 位置间交互能力；
- 复杂模式拟合能力；
- 代码/数学等结构化域上的 future token prediction。

但代价是：

$$
T_{draft}(L)\uparrow
$$

所以真正优化：

$$
\max_L \frac{E[A(L)]}{T_{draft}(L)+T_{verify}(L)}
$$

不是最大化 Drafter depth。

### Capacity 与数据规模必须一起扩

模型 capacity 增加，但训练数据不变，容易出现：

- 过拟合；
- 不同 domain 泛化不足；
- 深层没有学到稳定增益。

因此 Speculator scale-up 也遵循普通模型训练的基本规律：

参数、训练 token、domain coverage 和 validation workload 要匹配。

不过 Speculator 的验证指标不是常规 PPL，而更应包含：

- accepted length；
- suffix survival；
- workload-specific acceptance；
- end-to-end speedup。

### DFlare 给工程师的通用启发

即使以后出现别的 Block Drafter，也可以复用这个分析框架：

1. Target 给 Drafter 的信息够不够？
2. 条件注入是否形成瓶颈？
3. 增加 Draft capacity 后，acceptance 提升多少？
4. Draft latency 增加多少？
5. verifier 是否因为更长候选变贵？
6. 最终 Cost/Token 是否下降？

这比背论文结构更有迁移性。

### 实验

本课复用 Lab03，在 DFlash 模拟器上增加 `draft_depth` ：

- depth 越大，draft cost 增加；
- acceptance decay 变缓；
- layer-wise fusion 假设为同样 depth 下改善后缀 survival。

让学生找出三组硬件/负载下的最优 depth：

- 单请求低并发；
- 中并发；
- 高并发 verifier 已经很忙。

预期结论：

高并发下，增加 Drafter depth 的收益阈值更严格，因为 verifier 和 GPU 资源本身更稀缺。

### Layer-wise Fusion

对 Layer-wise Fusion 做边界检查，要覆盖输入、输出、状态归属和销毁时点。DFlare：Layer-wise Fusion 与 Drafter 扩容的等待、计算及复制都能沿这些节点定位。Layer-wise Fusion 传给条件信息瓶颈的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

Layer-wise Fusion 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。融合操作会引入特征读取和投影成本通常只先改变其中几项，其他资源随后可能进入关键路径。Layer-wise Fusion 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，Layer-wise Fusion 对系统的贡献也会变化。选择训练冻结范围应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 Layer-wise Fusion 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。小批量收益无法迁移到高并发会触发停止与回退，系统恢复到已有证据支持的配置。

Layer-wise Fusion 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。高低并发 Goodput 必须附带口径。缺少这些信息时，关于“如何突破 DFlash 的共享条件瓶颈并判断更深 Drafter 是否值得？”的判断无法在上线后复核。

### 条件信息瓶颈

在 DFlare：Layer-wise Fusion 与 Drafter 扩容中，条件信息瓶颈的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。条件信息瓶颈连接深层特征时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量条件信息瓶颈时分别记录算力、显存、带宽、CPU 开销与同步。发生“层数增加改变计算与带宽占比”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐条件信息瓶颈的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

### 深层特征

解释深层特征时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。DFlare：Layer-wise Fusion 与 Drafter 扩容的请求可能在这些交界处增加等待、计算或复制。与 Drafter 宽深配置交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕深层特征建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。条件瓶颈缓解后最优块大小可能移动会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

为不同 Target 建立兼容配置是否合适，取决于深层特征所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

深层特征带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现融合层过多导致内存带宽饱和时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

深层特征的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。净收益拐点没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何突破 DFlash 的共享条件瓶颈并判断更深 Drafter 是否值得？”在具体负载下是否成立。

## 失败模式与故障诊断

### 失败模式 1：融合层过多导致内存带宽饱和

诊断“融合层过多导致内存带宽饱和”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查 DFlare Drafter 扩容，结合分层特征读取量与 Drafter 延迟定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“融合层过多导致内存带宽饱和”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认融合投影耗时没有转移到未计量层。

### 失败模式 2：Drafter 更准但净延迟上升

出现“Drafter 更准但净延迟上升”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿 Layer-wise Fusion 的事件查看 Drafter 延迟和接受长度，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

“Drafter 更准但净延迟上升”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验显存占用。

### 失败模式 3：层间特征尺度不一致

针对“层间特征尺度不一致”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。条件信息瓶颈的时间线配合接受长度、融合投影耗时可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

对“层间特征尺度不一致”先执行在线保护，再处理复发条件。面向层间特征尺度不一致的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查高低并发 Goodput 的采集完整性。

### 失败模式 4：训练冻结策略造成适配不足

“训练冻结策略造成适配不足”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查深层特征的阶段事件，并用融合投影耗时及显存占用缩小故障位置。客户端、服务端、计费数据均需完成对账。

修复“训练冻结策略造成适配不足”分为影响控制和复验。针对训练冻结策略造成适配不足可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对训练成本没有被隐藏。

### 失败模式 5：小批量收益无法迁移到高并发

记录到“小批量收益无法迁移到高并发”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿 Drafter 宽深配置回放事件，再比较显存占用与高低并发 Goodput。若完成数存在账差，先修复计量链。

处理“小批量收益无法迁移到高并发”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认净收益拐点没有转移到未计量层。

### 失败模式 6：兼容矩阵缺失导致错误制品组合

排查“兼容矩阵缺失导致错误制品组合”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看块扩散训练的时间线以及高低并发 Goodput、训练成本。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

“兼容矩阵缺失导致错误制品组合”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验分层特征读取量。

```
"""Lesson 06 — scale a multi-layer feature fusion path and locate its cost knee."""

from __future__ import annotations

import argparse

from phase3lab.shared.cuda_ops import cuda_environment, load_causal_lm, memory_snapshot, timed_cuda
from phase3lab.shared.runner import LabSpec, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-06-dflare-scaling",
    title="DFlare：Drafter 特征融合的层数扩展",
    goal="扫描融合层数并记录时间、显存与数值尺度，为扩大 Drafter 提供可复验边界。",
    real_evidence=("actual hidden states", "layer-count sweep", "CUDA memory snapshots"),
    required_inputs=("hidden-state capable causal LM", "CUDA GPU"),
    outputs=("fusion sweep", "latency knee", "norm statistics"),
    acceptance=("same input for every point", "layer count truly changes", "no invented quality score"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--layer-counts", default="1,2,4,8")
    parser.add_argument("--repeats", type=int, default=8)

def layer_counts(raw: str, available: int) -> list[int]:
    values = [int(item) for item in raw.split(",") if item.strip()]
    if not values or any(value < 1 or value > available for value in values):
        raise ValueError(f"layer counts must be within 1..{available}")
    return sorted(set(values))

def weighted_fusion(torch, tensors):
    weights = torch.linspace(1.0, 2.0, len(tensors), device=tensors[0].device, dtype=tensors[0].dtype)
    weights = weights / weights.sum()
    return sum(weight * tensor for weight, tensor in zip(weights, tensors))

def fixture(args: argparse.Namespace) -> dict:
    counts = layer_counts(args.layer_counts, 12)
    return {"points": [{"layers": count, "read_bytes_fp16": count * 128 * 2048 * 2} for count in counts], "quality_metric": None}

def real(args: argparse.Namespace) -> dict:
    torch, tokenizer, model, load = load_causal_lm(args.model)
    inputs = tokenizer(args.prompt, return_tensors="pt").to("cuda")
    with torch.inference_mode():
        hidden = model(**inputs, output_hidden_states=True, use_cache=False).hidden_states[1:]
    counts = layer_counts(args.layer_counts, len(hidden))
    records = []
    for count in counts:
        selected = list(hidden[-count:])
        torch.cuda.reset_peak_memory_stats()
        samples, fused = timed_cuda(torch, lambda selected=selected: weighted_fusion(torch, selected), warmups=1, repeats=args.repeats)
        records.append({
            "layers": count,
            "shape": list(fused.shape),
            "l2_norm": round(float(torch.linalg.vector_norm(fused.float()).item()), 6),
            "latency": latency_summary(samples),
            "memory": memory_snapshot(torch),
        })
    return {
        "environment": cuda_environment(torch),
        "load_ms": load,
        "sweep": records,
        "quality_metric": None,
        "measurement_note": "the experiment measures fusion-system cost; model quality needs a trained DFlare-compatible Drafter and labeled workload",
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 联合推演 1：DFlare Drafter 扩容、逐层融合让 Drafter 在多个深度持续接收 Target 条件与选择融合层位置

围绕选择融合层位置构造时间线：请求进入时绑定模型、策略和工作负载身份，执行时记录 DFlare Drafter 扩容与“逐层融合让 Drafter 在多个深度持续接收 Target 条件”，结束时汇总分层特征读取量。实验保留原始事件和分位数，以便从混合流量中识别融合层过多导致内存带宽饱和。

容量部分固定模型与资源，分别运行低载、稳定高载和过载。低载体现“逐层融合让 Drafter 在多个深度持续接收 Target 条件”的固定成本，高载反映批处理及资源共享，过载时 DFlare Drafter 扩容与队列、截止时间共同作用。三个区间的分层特征读取量均可解释后，才为选择融合层位置划定边界。

注入“融合层过多导致内存带宽饱和”后，按检测、隔离、降级、回滚和重新导流记录事件。分层特征读取量帮助定位影响，隔离负责停止无效消耗，回滚目标与 DFlare Drafter 扩容保持兼容。缓存、队列与在途请求稳定后，才恢复“逐层融合让 Drafter 在多个深度持续接收 Target 条件”相关流量。

把选择融合层位置引入的资源与维护成本加总，再除以符合质量和服务等级的有效完成，得到可比较单位。分层特征读取量只是其中一项证据；融合层过多导致内存带宽饱和会增加无效成本。最终判断注明 DFlare Drafter 扩容适用的模型、负载范围与到期条件。

## 联合推演 2：DFlare Drafter 扩容、逐层融合让 Drafter 在多个深度持续接收 Target 条件与选择融合层位置

把 DFlare Drafter 扩容和“逐层融合让 Drafter 在多个深度持续接收 Target 条件”放进同一条请求时间线后，可以直接评估选择融合层位置。入口保存模型、策略与工作负载身份，执行层暴露 DFlare Drafter 扩容状态，证据层用 Drafter 延迟关联前因后果。为防止融合层过多导致内存带宽饱和被预热或其他请求稀释，实验同时留存事件、分位数和失败计数。

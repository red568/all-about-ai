## 课程定位

本课把 Reasoning LLM Serving：长思考与 Test-Time Scaling 放回真实请求链路中讨论，中心问题为“如何为长思考请求建立预算、公平性和服务等级？”。Reasoning Token 和 Test-Time Scaling 提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 Reasoning Token 的局部理想收益直接当成端到端结果。

本课先用 CPU 模拟控制 Reasoning Token 和 Test-Time Scaling，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界。这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 学习目标

1. 准确解释 Reasoning Token、Test-Time Scaling 和思考预算之间的状态与资源关系。
2. 使用“Choose b to maximize Q(b) - λ\*T(b) - μ\*C(b), subject to deadline and fairness”建立可计算的收益边界并解释全部变量。
3. 围绕思考 Token 数、任务成功率、质量增益斜率和每成功任务成本设计可复现实验。
4. 识别无限提高预算却没有质量收益、长请求饿死交互短请求和平均完成时间掩盖超时尾部等典型失败模式。
5. 对“如何为长思考请求建立预算、公平性和服务等级？”给出包含适用条件、证据、风险和回滚的工程答案。

## 前置知识与环境

阅读 Reasoning LLM Serving：长思考与 Test-Time Scaling 需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及 Reasoning Token 时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 Reasoning Token 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及学习者自行准备的本地小模型或兼容制品。

验证 Reasoning Token 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Reasoning Token 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：输出长度不再只是结果，而是计算预算

普通 Serving 常把 `max_tokens` 当作安全上限。

Reasoning 场景里，可以把它理解成：

$$
Budget_{compute}\approx N_{reasoning\ tokens}\times Cost_{token}
$$

更长推理可能带来更高质量，但收益不是线性的：

$$
Quality(B+\Delta B)-Quality(B)
$$

往往随预算增加出现边际递减。

因此平台问题变成：

$$
\max Quality(B)-\lambda Cost(B)
$$

subject to latency / user tier / business value。

### Reasoning 请求为什么容易成为“长驻留任务”

设一个 Replica 同时处理 $N$ 个请求，每个请求输出长度 $O_i$ 。

请求在 Decode 阶段的驻留时间近似：

$$
T_i\approx O_i\cdot TPOT_i
$$

普通请求 $O=300$ ，Reasoning 请求 $O=10000$ ，即使 TPOT 一样，后者在实例中停留时间也可高出一个数量级以上。

结果：

- 占用 KV 更久；
- 占用 scheduler slot 更久；
- 更容易与短请求形成资源不公平；
- 用户中途取消时浪费 token 更多；
- Autoscaler 看到的“当前并发数”不再能代表剩余工作量。

### Reasoning Budget 的四种形式

### 5.1 Token Budget

最直接：

```
max_reasoning_tokens = 4096 / 8192 / 16384
```

适合做硬上限。

### 5.2 Wall-Time Budget

例如 20 秒内必须返回。

需要：

$$
R e m a i n i n g T i m e = D e a d l i n e - N o w
$$

系统根据当前速度决定是否继续推理。

### 5.3 Cost Budget

例如每个请求最多花费：

$$
Cost_{request}\le C_{max}
$$

适合 API 计费、企业 Agent 和批量任务。

### 5.4 Quality/Confidence Budget

如果模型/Verifier 已达到足够置信度，可以提前结束；否则继续分配更多 test-time compute。

这需要额外 quality estimator，不是纯 Serving 可以凭空得到。

### Test-Time Scaling 的平台含义

一种常见思路是：同一个问题生成多个 reasoning candidates，再选择最优：

```
Question
├→ Reasoning 1
├→ Reasoning 2
├→ Reasoning 3
└→ Reasoning 4
       ↓
    Verifier/Judge
       ↓
     Answer
```

如果并行生成 $M$ 条轨迹，总成本近似：

$$
C\propto \sum_{m=1}^{M}Tokens_m
$$

这会产生新的平台问题：

- fan-out 并发；
- candidate aggregation；
- verifier 服务；
- 预算共享；
- 一个用户能否瞬间占用大量 GPU。

因此 Test-Time Scaling 需要与租户配额和成本控制打通。

### Reasoning Tier

生产平台可以定义：

```
Fast      : 1x budget
Balanced  : 4x budget
Deep      : 16x budget
```

但 Tier 不应该只写成前端标签。后端需要映射到：

- max reasoning tokens；
- max wall time；
- candidate count；
- model size；
- priority；
- cost cap。

这样用户购买的是可解释的资源级别。

### 长任务公平性

可以使用：

$$
Usage_u=\sum_{r\in u}OutputTokens_r\cdot Weight_{model}
$$

做 tenant compute accounting，而不是只数 request 数。

### Reasoning Token

Reasoning Token 在 Reasoning LLM Serving：长思考与 Test-Time Scaling 中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与 Test-Time Scaling 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

长输出占用 Decode 槽位并放大队列等待对 Reasoning Token 的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认 Reasoning Token 的变化来自哪里，本课对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

Reasoning Token 的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证隔离长短请求队列时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖 Reasoning Token 影响到的 Token、采样、结构、结束状态与错误。若检测到超时后模型仍持续生成，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为 Reasoning Token 建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。完成延迟的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“如何为长思考请求建立预算、公平性和服务等级？”。

### Test-Time Scaling

对 Test-Time Scaling 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Reasoning LLM Serving：长思考与 Test-Time Scaling 的等待、计算及复制都能沿这些节点定位。Test-Time Scaling 传给思考预算的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

Test-Time Scaling 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。截止时间把质量优化转化为受限决策通常只先改变其中几项，其他资源随后可能进入关键路径。Test-Time Scaling 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，Test-Time Scaling 对系统的贡献也会变化。选择质量与延迟门禁应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 Test-Time Scaling 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。难度估计错误分配过多资源会触发停止与回退，系统恢复到已有证据支持的配置。

Test-Time Scaling 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。超时率必须附带口径。缺少这些信息时，关于“如何为长思考请求建立预算、公平性和服务等级？”的判断无法在上线后复核。

### 完成截止时间

解释完成截止时间时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Reasoning LLM Serving：长思考与 Test-Time Scaling 的请求可能在这些交界处增加等待、计算或复制。与长输出队列交互的字段必须携带版本身份，便于回放时找到同一配置。

选择质量与延迟门禁是否合适，取决于预算终止策略所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

预算终止策略带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现难度估计错误分配过多资源时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

预算终止策略的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。TTFT 没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何为长思考请求建立预算、公平性和服务等级？”在具体负载下是否成立。

推演重点是判断更多思考 Token 可能改善任务质量但收益递减发生后哪些量应变化，以及长输出占用 Decode 槽位并放大队列等待的收益在什么负载下被摊销。实现中的调度、Kernel、内存、网络、客户端和取消成本另行记录。公式与实测产生矛盾时，以检查假设、遗漏项和统计方式为处理顺序。

### 机制 1：更多思考 Token 可能改善任务质量但收益递减

请求执行“更多思考 Token 可能改善任务质量但收益递减”后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存 Reasoning Token 状态和思考 Token 数，便于把原因与结果关联起来。

容量评估把“更多思考 Token 可能改善任务质量但收益递减”放在三个负载区间中运行。固定开销通常在低载突出，队列和资源争用会在高载显现；长请求饿死交互短请求意味着候选工作可能消耗了服务正常请求所需的容量。

实现“更多思考 Token 可能改善任务质量但收益递减”时明确数据格式、张量形状、缓存身份、版本兼容和错误回退。执行隔离长短请求队列前冻结接口合同，并加入无效输入、极端长度与资源不足测试。成功样本之外的保护行为也属于验收范围。

“更多思考 Token 可能改善任务质量但收益递减”的 Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含 TTFT、错误、取消和资源变化。这样能判断问题来自机制、选择器、实现成本还是流量变化。

“更多思考 Token 可能改善任务质量但收益递减”的上线合同写明灰度范围、停止条件、开关和暖回滚目标。难度估计错误分配过多资源发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 机制 2：长输出占用 Decode 槽位并放大队列等待

理解“长输出占用 Decode 槽位并放大队列等待”要从请求关键路径入手。变化前后每个阶段的顺序、并行性和合批条件均需标注，Test-Time Scaling 作为启用条件，任务成功率作为端到端结果。

“长输出占用 Decode 槽位并放大队列等待”的容量测试覆盖低载、稳定高载和过载。低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现平均完成时间掩盖超时尾部，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

“长输出占用 Decode 槽位并放大队列等待”的接口合同包括格式、Shape、缓存键、版本与回退语义。选择质量与延迟门禁进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径，确保实现不会只在理想样本上成立。

为“长输出占用 Decode 槽位并放大队列等待”采集证据时，把策略输入、阈值、候选集合与完成延迟、错误、取消及资源事件放进同一请求链。诊断据此定位选择、执行和负载漂移中的具体环节。

为“长输出占用 Decode 槽位并放大队列等待”准备独立发布单元，包含灰度身份、门禁、停止动作和已预热回滚路径。检测到质量评测与线上任务不一致后执行局部撤回；进程恢复之外，还要确认在途工作、缓存与资源回到稳定状态。

### 机制 3：截止时间把质量优化转化为受限决策

“截止时间把质量优化转化为受限决策”会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；思考预算给出状态条件，质量增益斜率验证结果是否传到请求端。

单请求数据不足以评价“截止时间把质量优化转化为受限决策”。低载用于测量截止时间把质量优化转化为受限决策的固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。超时后模型仍持续生成若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成“截止时间把质量优化转化为受限决策”的实现边界。设计截止时间传播需要在合同冻结后测试正常、无效、极端和资源受限输入。

“截止时间把质量优化转化为受限决策”需要成对的原因和结果字段。原因包括决策特征、阈值和候选，结果包括超时率、错误、取消和资源快照；关联后即可判断机制是否有效以及额外成本出现在哪里。

发布“截止时间把质量优化转化为受限决策”时配置独立开关、灰度身份、停止条件和暖回滚目标。无限提高预算却没有质量收益触发后只撤回相关变化，并继续检查在途请求、缓存和资源释放，直到稳定路径恢复。

### 机制 4：不同难度请求需要不同预算

分析“不同难度请求需要不同预算”时，把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。完成截止时间说明机制何时生效，TTFT 负责确认关键路径是否真的缩短。

对“不同难度请求需要不同预算”分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到难度估计错误分配过多资源后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

为“不同难度请求需要不同预算”确定接口时，同时规定数据与 Shape、缓存和版本身份、错误及回退。随后以无效输入、极端长度和资源不足验证控制超时后的取消与计费，使失败路径与成功路径拥有同样清晰的证据。

观测“不同难度请求需要不同预算”时，原因侧保存策略输入、阈值和候选集合，结果侧保存队列年龄、错误、取消与资源。两侧对齐后，可以区分不同难度请求需要不同预算收益不足、选择错误、实现开销偏大和工作负载漂移。

“不同难度请求需要不同预算”通过独立开关进入灰度，发布记录包含流量身份、停止阈值和可立即启用的回滚修订。出现长请求饿死交互短请求时撤回本项候选，随后核对在途请求、缓存状态与资源是否释放。

## 工程决策与取舍

### 决策 1：设置默认思考预算

设置默认思考预算解决哪项用户问题，需要由思考 Token 数、质量增益斜率和完成延迟共同证明。评审材料同时记录 Reasoning Token 资源账、“更多思考 Token 可能改善任务质量但收益递减”生效条件和无限提高预算却没有质量收益的门禁。启用范围与实际证据范围保持一致。

围绕“设置默认思考预算”运行基线、候选与回退。候选只引入“设置默认思考预算”研究变量，回退保持已验证制品可立即恢复；每组使用同一请求集合和随机种子。报告分开呈现“设置默认思考预算”在不同负载及请求形态下的结果，并记录拒绝项、复查触发器和每成功任务成本是否足以支付维护开销。

### 决策 2：按任务难度分配预算

决定“按任务难度分配预算”是否上线时，服务承诺是评审起点，任务成功率、TTFT、超时率构成结果证据。还需解释 Test-Time Scaling 怎样变化、“长输出占用 Decode 槽位并放大队列等待”在哪些负载下有效，以及遇到长请求饿死交互短请求时如何停止。

“按任务难度分配预算”比较基线、候选和回退三种配置。基线沿用已验证路径，候选只改变“按任务难度分配预算”研究因素，回退无需重新下载大制品即可恢复服务。三组使用相同请求集合与随机种子，并按负载区间、请求形态分组。决策记录包含“按任务难度分配预算”的选择理由、被拒方案、结论到期条件和每成功任务成本对应的维护成本。

### 决策 3：隔离长短请求队列

评审“隔离长短请求队列”时，先写明要改善的用户承诺，以及对应的质量增益斜率、完成延迟和队列年龄。候选需说明思考预算的资源变化、“截止时间把质量优化转化为受限决策”的适用条件及平均完成时间掩盖超时尾部触发的停止动作。只在极端样本成立的收益应限定启用范围。

实验为“隔离长短请求队列”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“隔离长短请求队列”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及每成功任务成本的改善是否覆盖新增运维成本。

### 决策 4：选择质量与延迟门禁

“选择质量与延迟门禁”进入方案评审前，要绑定具体服务承诺和 TTFT、超时率、每成功任务成本。资源侧检查完成截止时间，机制侧限定“不同难度请求需要不同预算”，故障侧为超时后模型仍持续生成准备停止动作。测试样本不代表业务时，结论只覆盖该样本。

验证“选择质量与延迟门禁”需要三条可复现路径：已确认的基线、只改“选择质量与延迟门禁”因素的候选、无需重新取大制品的回退。三者共享请求和随机种子，数据按负载区间与请求形态统计。最终文档保存“选择质量与延迟门禁”的取舍理由、有效期和每成功任务成本相对维护成本的变化。

### 决策 5：设计截止时间传播

设计截止时间传播解决哪项用户问题，需要由完成延迟、队列年龄和思考 Token 数共同证明。评审材料同时记录长输出队列资源账、“取消传播决定超时后的无效计算”生效条件和难度估计错误分配过多资源的门禁。启用范围与实际证据范围保持一致。

### 决策 6：控制超时后的取消与计费

决定“控制超时后的取消与计费”是否上线时，服务承诺是评审起点，超时率、每成功任务成本、任务成功率构成结果证据。还需解释推理质量曲线怎样变化、“预算终止器依据进展信号提前收敛”在哪些负载下有效，以及遇到质量评测与线上任务不一致时如何停止。

## 失败模式与故障诊断

### 失败模式 1：无限提高预算却没有质量收益

记录到“无限提高预算却没有质量收益”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿 Reasoning Token 回放事件，再比较思考 Token 数与任务成功率。若完成数存在账差，先修复计量链。

处理“无限提高预算却没有质量收益”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认 TTFT 没有转移到未计量层。

### 失败模式 2：长请求饿死交互短请求

排查“长请求饿死交互短请求”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看 Test-Time Scaling 的时间线以及任务成功率、质量增益斜率。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

“长请求饿死交互短请求”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验完成延迟。

### 失败模式 3：平均完成时间掩盖超时尾部

诊断“平均完成时间掩盖超时尾部”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查思考预算，结合质量增益斜率与 TTFT 定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

对“平均完成时间掩盖超时尾部”先执行在线保护，再处理复发条件。面向平均完成时间掩盖超时尾部的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查超时率的采集完整性。

### 失败模式 4：超时后模型仍持续生成

出现“超时后模型仍持续生成”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿完成截止时间的事件查看 TTFT 和完成延迟，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

修复“超时后模型仍持续生成”分为影响控制和复验。针对超时后模型仍持续生成可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对队列年龄没有被隐藏。

### 失败模式 5：难度估计错误分配过多资源

针对“难度估计错误分配过多资源”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。长输出队列的时间线配合完成延迟、超时率可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

处理“难度估计错误分配过多资源”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认每成功任务成本没有转移到未计量层。

### 失败模式 6：质量评测与线上任务不一致

“质量评测与线上任务不一致”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查推理质量曲线的阶段事件，并用超时率及队列年龄缩小故障位置。客户端、服务端、计费数据均需完成对账。

“质量评测与线上任务不一致”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验思考 Token 数。

## 机制模拟实验

机制模拟目标是：模拟任务难度、质量收益曲线、思考预算与多优先级队列，比较固定和自适应预算。模拟不调用 GPU，不复刻具体框架 Kernel，而是把 Reasoning Token、思考预算、更多思考 Token 可能改善任务质量但收益递减和预算终止器依据进展信号提前收敛转换成可调参数。输入包含 Reasoning Token 相关负载轨迹、随机种子、策略配置和服务模型；输出统一记录运行状态、配置、指标、失败和限制。

```

```

可执行文件为 `lesson/10-reasoning-tokens/run.py` 。所需的 HTTP、CUDA、统计、报告或状态机原语已经合并到这一入口。下方代码展示入口中内嵌的可读核心实现；下载包不再单独提供内部源码库目录。默认运行 Fixture，加 `--real` 才进入实测路径。

```
"""Lesson 10 — output-budget sweep for reasoning-style requests."""

from __future__ import annotations

import argparse

from phase3lab.shared.evidence import summarize_records
from phase3lab.shared.http_client import completion, discover_models, metrics_evidence
from phase3lab.shared.runner import LabSpec, PreconditionError, run_cli

SPEC = LabSpec(
    lab_id="lesson-10-reasoning-tokens",
    title="Reasoning Token：输出预算、完成率与尾延迟",
    goal="在同一真实端点上扫描输出 Token 上限，保存请求级 usage 与延迟。",
    real_evidence=("OpenAI-compatible usage", "request records by budget", "vLLM metrics hash"),
    required_inputs=("one GPU-backed endpoint", "served model"),
    outputs=("budget sweep", "latency and token summaries", "raw records"),
    acceptance=("at least three budgets", "same prompts/model", "usage is not estimated when absent"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--budgets", default="32,128,512")

def budgets(raw: str) -> list[int]:
    values = sorted(set(int(item) for item in raw.split(",") if item.strip()))
    if len(values) < 3 or any(value < 1 for value in values):
        raise ValueError("--budgets must contain at least three positive values")
    return values

def fixture(args: argparse.Namespace) -> dict:
    return {
        "sweep": [
            {"budget": value, "observed_output_tokens": min(value, 93), "finished_before_limit": value > 93}
            for value in budgets(args.budgets)
        ],
        "token_source": "fixture",
    }

def real(args: argparse.Namespace) -> dict:
    if len(args.base_url) != 1:
        raise PreconditionError("provide exactly one --base-url")
    models = discover_models(args.base_url[0])
    model = models[0] if args.model == "auto" else args.model
    if model not in models:
        raise PreconditionError(f"model {model} is not served")
    evidence = metrics_evidence((args.evidence_url or args.base_url)[0])
    records_by_budget = []
    for budget in budgets(args.budgets):
        records = [
            completion(args.base_url[0], model, f"{args.prompt}\nreasoning_case={index}", budget, request_id=f"budget-{budget}-{index}")
            for index in range(args.requests)
        ]
        if not all(record.ok for record in records):
            raise RuntimeError(f"requests failed at output budget {budget}")
        records_by_budget.append({
            "budget": budget,
            "summary": summarize_records(records),
            "records": [record.json() for record in records],
            "usage_available": all(record.output_tokens is not None for record in records),
        })
    return {"model": model, "metrics": evidence, "sweep": records_by_budget}

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 联合推演 1：Reasoning Token、更多思考 Token 可能改善任务质量但收益递减与设置默认思考预算

围绕设置默认思考预算构造时间线：请求进入时绑定模型、策略和工作负载身份，执行时记录 Reasoning Token 与“更多思考 Token 可能改善任务质量但收益递减”，结束时汇总思考 Token 数。实验保留原始事件和分位数，以便从混合流量中识别无限提高预算却没有质量收益。

容量部分固定模型与资源，分别运行低载、稳定高载和过载。低载体现“更多思考 Token 可能改善任务质量但收益递减”的固定成本，高载反映批处理及资源共享，过载时 Reasoning Token 与队列、截止时间共同作用。三个区间的思考 Token 数均可解释后，才为设置默认思考预算划定边界。

注入“无限提高预算却没有质量收益”后，按检测、隔离、降级、回滚和重新导流记录事件。思考 Token 数帮助定位影响，隔离负责停止无效消耗，回滚目标与 Reasoning Token 保持兼容。缓存、队列与在途请求稳定后，才恢复“更多思考 Token 可能改善任务质量但收益递减”相关流量。

把设置默认思考预算引入的资源与维护成本加总，再除以符合质量和服务等级的有效完成，得到可比较单位。思考 Token 数只是其中一项证据；无限提高预算却没有质量收益会增加无效成本。最终判断注明 Reasoning Token 适用的模型、负载范围与到期条件。

## 联合推演 2：Reasoning Token、更多思考 Token 可能改善任务质量但收益递减与设置默认思考预算

把 Reasoning Token 和“更多思考 Token 可能改善任务质量但收益递减”放进同一条请求时间线后，可以直接评估设置默认思考预算。入口保存模型、策略与工作负载身份，执行层暴露 Reasoning Token 状态，证据层用任务成功率关联前因后果。为防止无限提高预算却没有质量收益被预热或其他请求稀释，实验同时留存事件、分位数和失败计数。

为设置默认思考预算确定容量范围时，模型和资源保持不变，流量依次覆盖轻载、临近容量与过载。“更多思考 Token 可能改善任务质量但收益递减”的启动成本、共享资源竞争以及 Reasoning Token 引起的排队会在不同区间出现。任务成功率只支持实际测过的并发范围。

这组失败验证制造“无限提高预算却没有质量收益”，并检查告警、隔离、降级与回滚是否按顺序执行。任务成功率和相邻字段构成检测证据，稳定制品需兼容 Reasoning Token。重新导流前核实缓存、队列、在途工作和“更多思考 Token 可能改善任务质量但收益递减”状态。

设置默认思考预算的成本分子覆盖计算、显存、训练、加载、监控和日常维护，分母采用有效完成数。结合任务成功率和无限提高预算却没有质量收益可以判断局部性能是否转化为整体收益。结论仅适用于记录的 Reasoning Token、模型与流量，条件变化后重新评估。

## 联合推演 3：Reasoning Token、更多思考 Token 可能改善任务质量但收益递减与设置默认思考预算

这组推演从设置默认思考预算出发，对齐 Reasoning Token 状态与“更多思考 Token 可能改善任务质量但收益递减”的阶段事件。模型、策略、工作负载身份从入口贯穿到结果，质量增益斜率用于验证链路变化。无限提高预算却没有质量收益可能在平均值中消失，所以保留逐请求记录、分位统计及失败计数。

## 课程定位

“如何拆分媒体预处理、编码和 LLM 解码以控制端到端延迟？”贯穿本课。先把媒体预处理、Vision Encoder 及其状态边界讲清楚，再讨论计算、实现和上线证据。在 Multimodal Serving：Encoder、Media Cache 与异构流水中，算法选择只是决策的一部分；负载分布、模型修订、调度、显存、并发和服务等级都会改变结论。每项收益都需要对应可观察的事件与适用范围。

## 工程问题

Multimodal Serving：Encoder、Media Cache 与异构流水没有脱离环境的统一加速数字。评审记录应包含模型修订、长度分布、到达过程、并发、采样、缓存、媒体获取时间定义、服务等级和硬件；随后才能比较“选择图像分辨率或视频采样率”和“部署独立或共置 Encoder”。缺少这些信息时，局部速度无法换算成系统收益。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：为什么“同样一个请求”成本可以差100倍

请求 A：一张 224×224 图片。

请求 B：20 秒 1080p 视频，抽 64 帧。

外部 API 都可能是 1 request，但内部工作量完全不同。

可以定义 multimodal work：

$$
W=\alpha B_{media}+\beta N_{frames}+\gamma N_{visionTokens}+\delta N_{llmTokens}
$$

其中各项系数由实际硬件/模型 profile 得到。

这说明：

多模态平台按 request count 做容量规划尤其危险。

### 媒体输入的四种瓶颈

### 4.1 Download Bound

远程 URL、对象存储或 CDN 慢。

### 4.2 CPU Decode/Preprocess Bound

JPEG/PNG/video decode、resize、normalize 占 CPU。

### 4.3 Encoder Bound

Vision/Audio Encoder 占用 GPU 计算，可能与 LLM 竞争。

### 4.4 LLM Bound

Encoder 输出变成大量 multimodal tokens，进入 LLM 上下文，扩大 Prefill/KV。

只有看完整 trace 才知道瓶颈在哪里。

### CPU/GPU Pipeline

最差实现：

```
CPU 下载
等待
CPU 解码
等待
GPU Encoder
等待
LLM
```

更合理：

```
Req A: Download → Decode → Encoder → LLM
Req B:          Download → Decode → Encoder → LLM
Req C:                   Download → Decode → Encoder → LLM
```

目标是用异步 I/O、线程池和独立 GPU/stream，把不同请求阶段重叠。

注意：这不是重新讲 CUDA stream，而是把它放到多模态 Serving 的资源编排中。

### Media Cache 与 Feature Cache

### Media Cache

缓存原始下载后的 bytes。

Key 可以是：

$$
Hash(URL,ETag,ContentDigest)
$$

### Preprocessed Cache

缓存 resize/normalize 后 Tensor。

Key 还要包含 preprocess config。

### Encoder Feature Cache

缓存 encoder output：

$$
Key=Hash(MediaDigest,EncoderRevision,PreprocessRevision)
$$

如果同一张图片被多个问题重复引用，Feature Cache 可以直接跳过 Encoder。

### 为什么 Feature Cache 不能只用 URL 做 Key

同一个 URL 内容可能变化；同一图片在不同 encoder revision 下 feature 也不同。

安全 Key 至少包含：

- content digest；
- encoder revision；
- preprocess config；
- projector/model revision；
- tenant isolation（视业务要求）。

### Video Serving

视频最大问题是 frame count。

假设：

$$
N_{frames}=fps_{sample}\cdot duration
$$

每帧产生 $V$ 个视觉 token：

$$
N_{vision}=N_{frames}\cdot V
$$

即使 LLM 输出很短，Prefill 也可能巨大。

因此平台需要：

- sampling policy；
- max frames；
- resolution tier；
- duration limit；
- preprocess queue；
- encoder pool。

### Encoder 与 LLM 是否共卡

### 共卡

优点：

- 架构简单；
- 不需要跨 GPU 传 feature。

缺点：

- Encoder burst 会干扰 LLM；
- GPU memory 生命周期更复杂。

### 分池

```
Media → Encoder Pool → Feature → LLM Pool
```

优点：可独立扩缩容和选择硬件。

缺点：需要网络/IPC，增加故障面。

是否拆分必须根据：

$$
T_{encoder}, TrafficMix, FeatureSize, SLO
$$

实测。

### 媒体预处理

解释媒体预处理时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Multimodal Serving：Encoder、Media Cache 与异构流水的请求可能在这些交界处增加等待、计算或复制。与 Vision Encoder 交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕媒体预处理建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。Encoder 将媒体转换为可供 LLM 消费的表示会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

### Media Token

对 Media Token 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Multimodal Serving：Encoder、Media Cache 与异构流水的等待、计算及复制都能沿这些节点定位。Media Token 传给 Media Cache 的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

### Media Cache

在 Multimodal Serving：Encoder、Media Cache 与异构流水中，Media Cache 的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。Media Cache 连接异构流水时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

### 失败模式 1：媒体下载或解码阻塞入口

出现“媒体下载或解码阻塞入口”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿媒体预处理的事件查看媒体获取时间和预处理延迟，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

修复“媒体下载或解码阻塞入口”分为影响控制和复验。针对媒体下载或解码阻塞入口可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对 Media Cache 命中没有被隐藏。

### 失败模式 2：缓存键遗漏裁剪与模型版本

针对“缓存键遗漏裁剪与模型版本”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。Vision Encoder 的时间线配合预处理延迟、Encoder 延迟可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

处理“缓存键遗漏裁剪与模型版本”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认首 Token 延迟没有转移到未计量层。

### 失败模式 3：Encoder 批处理导致交互长尾

“Encoder 批处理导致交互长尾”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查 Media Token 的阶段事件，并用 Encoder 延迟及 Media Cache 命中缩小故障位置。客户端、服务端、计费数据均需完成对账。

“Encoder 批处理导致交互长尾”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验峰值显存。

### 失败模式 4：帧数过多挤压文本上下文

记录到“帧数过多挤压文本上下文”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿 Media Cache 回放事件，再比较 Media Cache 命中与首 Token 延迟。若完成数存在账差，先修复计量链。

对“帧数过多挤压文本上下文”先执行在线保护，再处理复发条件。面向帧数过多挤压文本上下文的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查帧级吞吐的采集完整性。

### 失败模式 5：CPU 预处理成为隐藏瓶颈

排查“CPU 预处理成为隐藏瓶颈”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看异构流水的时间线以及首 Token 延迟、峰值显存。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

修复“CPU 预处理成为隐藏瓶颈”分为影响控制和复验。针对 CPU 预处理成为隐藏瓶颈可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对端到端成功率没有被隐藏。

### 失败模式 6：损坏媒体触发无限重试

诊断“损坏媒体触发无限重试”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查视频帧采样，结合峰值显存与帧级吞吐定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“损坏媒体触发无限重试”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认媒体获取时间没有转移到未计量层。

## 机制模拟实验

机制模拟目标是：模拟媒体尺寸、帧数、缓存、Encoder 批量和 Decode 竞争形成的异构流水。模拟不调用 GPU，不复刻具体框架 Kernel，而是把媒体预处理、Media Token、媒体解码和预处理位于 GPU 推理之前和长 Decode 会与 Encoder 争用设备和内存转换成可调参数。输入包含媒体预处理相关负载轨迹、随机种子、策略配置和服务模型；输出统一记录运行状态、配置、指标、失败和限制。


模拟可以证明媒体解码和预处理位于 GPU 推理之前与媒体获取时间之间在给定假设下的因果方向，也能寻找部署独立或共置 Encoder 的敏感区间。它不能证明媒体解码和预处理位于 GPU 推理之前在真实框架中的执行时间、CUDA Kernel 效率、具体模型质量或线上流量分布，因此报告的数值来源必须标记为 `fixture` 。

```
"""Lesson 13 — image preprocessing and multimodal request evidence."""

from __future__ import annotations

import argparse
import base64
import hashlib
import io
import time
from pathlib import Path

from phase3lab.shared.http_client import auth_headers, discover_models, extract_text, metrics_evidence, request_json
from phase3lab.shared.runner import LabSpec, PreconditionError, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-13-media-preprocess",
    title="Multimodal：图像预处理、输入字节与端到端延迟",
    goal="生成多个真实图像尺寸，分别记录编码成本、请求大小和模型端到端延迟。",
    real_evidence=("input image hashes", "preprocessing timing", "multimodal endpoint responses"),
    required_inputs=("local image", "vision-language endpoint", "Pillow"),
    outputs=("resolution sweep", "payload bytes", "response hashes"),
    acceptance=("image bytes change with resolution", "all variants are submitted", "preprocess and inference time are separate"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--image", default="data/sample.png")
    parser.add_argument("--resolutions", default="224,448,672")

def parse_resolutions(raw: str) -> list[int]:
    values = sorted(set(int(item) for item in raw.split(",") if item.strip()))
    if len(values) < 2 or any(value < 32 or value > 4096 for value in values):
        raise ValueError("provide at least two resolutions in [32, 4096]")
    return values

def fixture(args: argparse.Namespace) -> dict:
    return {"variants": [{"resolution": value, "pixels": value * value, "mime": "image/png"} for value in parse_resolutions(args.resolutions)], "separate_timers": ["preprocess_ms", "request_ms"]}

def real(args: argparse.Namespace) -> dict:
    if len(args.base_url) != 1:
        raise PreconditionError("provide exactly one --base-url")
    image_path = Path(args.image)
    if not image_path.is_file():
        raise PreconditionError(f"image does not exist: {image_path}")
    try:
        from PIL import Image
    except ImportError as exc:
        raise PreconditionError("Pillow is required for the multimodal lab") from exc
    served = discover_models(args.base_url[0])
    model = served[0] if args.model == "auto" else args.model
    if model not in served:
        raise PreconditionError(f"model {model} is not served")
    source = Image.open(image_path).convert("RGB")
    records = []
    for resolution in parse_resolutions(args.resolutions):
        preprocess_started = time.perf_counter()
        variant = source.copy()
        variant.thumbnail((resolution, resolution))
        canvas = Image.new("RGB", (resolution, resolution), "white")
        canvas.paste(variant, ((resolution - variant.width) // 2, (resolution - variant.height) // 2))
        output = io.BytesIO()
        canvas.save(output, format="PNG", optimize=False)
        encoded = output.getvalue()
        preprocess_ms = (time.perf_counter() - preprocess_started) * 1000
        data_uri = "data:image/png;base64," + base64.b64encode(encoded).decode()
        payload = {
            "model": model,
            "messages": [{"role": "user", "content": [
                {"type": "text", "text": args.prompt},
                {"type": "image_url", "image_url": {"url": data_uri}},
            ]}],
            "max_tokens": args.max_new_tokens,
            "temperature": 0,
        }
        request_started = time.perf_counter()
        status, body, _ = request_json("POST", f"{args.base_url[0].rstrip('/')}/v1/chat/completions", payload, timeout=240, headers=auth_headers())
        request_ms = (time.perf_counter() - request_started) * 1000
        if status != 200:
            raise RuntimeError(f"multimodal request for {resolution}px returned HTTP {status}")
        text = extract_text(body)
        records.append({
            "resolution": resolution,
            "image_bytes": len(encoded),
            "image_sha256": hashlib.sha256(encoded).hexdigest(),
            "preprocess_ms": round(preprocess_ms, 4),
            "request_ms": round(request_ms, 4),
            "response_sha256": hashlib.sha256(text.encode()).hexdigest(),
        })
    if len({record["image_sha256"] for record in records}) != len(records):
        raise RuntimeError("resolution sweep produced duplicate image bytes")
    return {
        "model": model,
        "source_image_sha256": hashlib.sha256(image_path.read_bytes()).hexdigest(),
        "metrics": metrics_evidence((args.evidence_url or args.base_url)[0]),
        "records": records,
        "request_latency": latency_summary([record["request_ms"] for record in records]),
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 联合推演 1：媒体预处理、媒体解码和预处理位于 GPU 推理之前与选择图像分辨率或视频采样率

在请求链中同时标记媒体预处理和“媒体解码和预处理位于 GPU 推理之前”，可以看到选择图像分辨率或视频采样率影响的具体阶段。入口记录版本与负载，执行事件呈现媒体预处理变化，媒体获取时间承担结果核验。逐请求事件和失败计数用于揭示可能被平均值遮住的媒体下载或解码阻塞入口。

模型和硬件固定后，逐步将流量从低载推到稳定高载，再超过容量。“媒体解码和预处理位于 GPU 推理之前”的成本、批处理收益和媒体预处理造成的队列效应由媒体获取时间分别呈现。这些数据共同限定选择图像分辨率或视频采样率可采用的负载范围。

故障场景主动注入“媒体下载或解码阻塞入口”。系统应检测媒体获取时间及相邻证据，隔离无效工作，降级或回滚到与媒体预处理兼容的制品，再逐步恢复流量。恢复阶段继续观察缓存、队列和在途请求，确认“媒体解码和预处理位于 GPU 推理之前”没有遗留旧状态。

评估选择图像分辨率或视频采样率的单位经济性时，成本侧包括计算、显存、训练、加载、观测和维护，产出侧只统计满足质量与 SLO 的完成。即便媒体获取时间变好，媒体下载或解码阻塞入口带来的无效工作也可能抵消收益。报告同时限定媒体预处理和复查触发器。

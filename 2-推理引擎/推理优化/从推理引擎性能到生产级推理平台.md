## 课程定位

大模型推理优化常从一个很直观的问题开始：同一块 GPU 上，怎样让模型更快地产生 Token。这个问题重要，但它只覆盖生产系统的一小部分。真实服务面对的是持续到达且形态不一的请求、不断变化的并发、不同长度的输入与输出、多个模型版本、多个租户、跨副本缓存、故障与发布过程。即使单个引擎的每秒 Token 数很高，只要流量被送到错误的副本、模型启动时间过长、长请求堵住交互请求、配额与取消没有传递、故障副本仍被路由命中，用户体验和单位成本都可能很差。

本课建立整门课程的统一工程模型：把推理服务看成一个由数据面、控制面和证据面共同组成的动态系统。数据面处理请求和 Token；控制面决定部署、路由、扩缩容、版本、放置与恢复；证据面采集能够解释系统行为的指标、事件、Trace 和实验记录。后续的生成加速、新型推理工作负载、Gateway、模型多路复用、权重分发、GPU Fleet、可靠性和成本分析，都可以放回这三个平面中理解。

课程目标不是追逐某个框架的一组启动参数，而是学会建立可计算的系统边界。学习者最终需要回答四类问题：瓶颈究竟位于模型计算、引擎调度、跨副本路由还是控制面；一次优化改善了哪个负载区间，又损害了哪个区间；在硬件和流量变化后，结论是否仍然成立；当指标冲突时，应怎样依据服务等级和成本约束做出选择。

## 学习目标

完成本课后，应当能够：

- 区分模型、推理引擎、工作器、副本、路由器、Gateway、控制器和平台之间的责任边界；
- 用请求生命周期解释 TTFT、逐 Token 延迟、端到端延迟、吞吐、Goodput、排队时间和取消浪费之间的关系；
- 识别单卡离线跑分、单副本在线压测和多副本生产系统三种证据的适用范围；
- 把数据面、控制面与证据面连接成一个可观测、可回放、可验收的闭环；
- 为一次优化写出假设、工作负载、控制变量、观测指标、失败条件和验收标准；
- 在任意可用 CUDA GPU 上运行缩小模型的真实路径。
- 解释为什么“平均延迟下降”“峰值吞吐上升”或“GPU 利用率更高”都不能单独证明系统更好。

## 前置知识与环境

学习者需要能够阅读 Python，理解 HTTP 请求、进程、显存和基本概率统计。需要知道大模型按照 Token 生成文本，并了解 Prefill 与 Decode 是两种计算特征不同的阶段。课程会在需要时重新定义工程上不可缺少的概念，但不会把重点放在 GPU 指令、Kernel 编写或训练并行的基础教学上。

机制模拟只依赖 Python 3.11 或更高版本，可以在 CPU 上运行。真实路径以一张任意可用的 CUDA GPU 为基线，不绑定某个显卡型号。脚本应先检查 CUDA、可用显存、模型路径和依赖，再根据资源缩小模型、批量、上下文长度、最大输出长度和样本量。这是一种诚实的实验状态，不是失败，更不能用模拟输出替代真实 GPU 测量。

## 工程问题：为什么单卡更快不等于平台更好

设想一个引擎优化把空载下的逐 Token 延迟降低了百分之二十。如果生产流量很低，而且请求彼此独立，这个收益可能直接改善用户等待时间。但在高并发时，同一优化也许需要额外的 Draft Model、更多 KV Cache、更多 CUDA Graph 或更大的临时张量，导致可容纳的并发下降。请求开始排队后，用户观察到的端到端延迟反而可能上升。一个局部优化同时改变服务时间分布和系统容量，结论不能只看单次生成。

再设想一组副本，其中一个副本命中了长前缀缓存，另一个副本当前队列更短。把请求送到缓存副本可以避免重复 Prefill，但如果该副本已经被多个长输出请求占用，等待时间可能超过重新计算前缀的成本。此时正确决策不是固定选择“缓存命中最高”或“队列最短”，而是估计两条路径的完成时间，并把估计误差、服务等级和故障风险计入决策。

第三个例子是扩容。普通 Web 服务增加一个副本通常只需拉起进程和加载少量代码；大模型副本可能需要下载数十或数百 GB 权重、完成分片、载入 CPU 内存、拷贝到 GPU、建立通信组、捕获执行图并进行预热。如果扩容控制器只观察当前队列，而忽略启动延迟，那么新副本在流量峰值结束后才就绪。控制器看似正确地“扩容了”，却没有在需要的时间产生有效容量。

这些例子说明，生产级推理优化的对象不是一段 Kernel 或一个 Engine，而是从流量到资源、从请求到版本、从部署到恢复的整体闭环。局部性能是闭环中的一个输入，而不是最终目标。

## 知识串讲：建立统一术语

### 模型与模型制品

模型是一个数学函数及其参数化结构；模型制品是可以被系统加载和追踪的一组不可变资源。制品通常包含权重、配置、Tokenizer、Chat Template、推理相关元数据和校验信息。生产系统必须区分“逻辑模型名”和“不可变修订版”。逻辑模型名便于客户端调用，不可变修订版保证同一次发布、回滚和故障分析指向确定字节。若只记录一个可被覆盖的目录名，出现质量回归或加载异常时就无法证明工作器实际加载了什么。

### 推理引擎

推理引擎把模型制品转化为可执行生成过程。它负责显存管理、批处理、KV Cache、调度、采样、约束解码、并行执行和指标输出。引擎的职责通常止于一个进程或一组紧密协作的进程。它可以知道本地正在运行多少请求、剩余多少 KV 块，却不一定知道其他副本的缓存、租户配额、发布计划和全局成本目标。

### 工作器与副本

工作器是对外提供某种推理能力的运行实体，可能对应一个进程、一个容器、一个 Pod 或一个多 GPU 并行组。副本强调多个等价服务实例中的一个。对于张量并行模型，一个“副本”可能占用多张 GPU；不能把 Kubernetes Pod 数、进程数和可独立服务请求的副本数混为一谈。容量规划必须以实际可承接请求的并行组为单位，并同时记录组内拓扑和故障域。

### 路由器与 Gateway

路由器在多个候选工作器之间选择目标，主要关心负载、队列、缓存、模型能力和健康状态。Gateway 位于更外层，负责协议兼容、身份、租户、配额、审计、模型别名、供应商或集群回退以及请求规范化。两者可以部署在同一进程，但逻辑职责应当分开。若把身份鉴权、Token 计量和微秒级副本选择揉进一个不可观测模块，既难以演进，也难以判断延迟来自策略还是实现。

### 控制器

控制器把期望状态持续收敛为实际状态。例如，期望某模型存在三个健康副本，控制器发现只有两个，就创建新工作器；期望流量逐步从旧修订版迁移到新修订版，控制器根据健康和门禁推进或回滚。控制器不是一次性部署脚本，它需要周期性观察、做出幂等决策、处理并发修改并在失败后重试。没有明确状态机的控制面容易产生半发布、孤儿资源和重复扩容。

### 平台

平台把上述组件组织成可被多个团队稳定使用的产品边界。平台不仅提供一个 API，还需要模型接入、容量申请、版本发布、观测、成本归属、权限、故障处理和支持流程。平台成功与否不能只由峰值吞吐判断，还要看交付时间、变更失败率、恢复时间、单位成本和服务等级达成率。

## 知识串讲：请求生命周期

一次在线生成请求可以拆成若干有因果关系的阶段：客户端发送、Gateway 校验与规范化、全局路由、工作器排队、输入预处理、Prefill、首次采样、循环 Decode、流式传输、结束处理和计量落账。多模态请求还可能包含下载、解码、图像或音频预处理与 Encoder；Agentic 请求可能在一次模型输出后触发工具，再形成新的模型调用；结构化输出会引入 Grammar 编译和逐步约束；推测解码会增加草拟和验证。

把端到端延迟写成求和有助于定位问题：

$$
T_{e2e}=T_{gateway}+T_{route}+T_{queue}+T_{preprocess}+T_{prefill}+T_{decode}+T_{stream}+T_{post}
$$

这个式子并不意味着各项完全独立。有些阶段可以重叠，例如客户端接收流式 Token 时服务器继续 Decode；有些阶段共享资源，例如媒体预处理和 Tokenizer 争用 CPU；有些阶段的选择会改变后续成本，例如路由到具有前缀缓存的副本可以减少 Prefill。求和模型的价值是提供检查清单，真实分析还要用 Trace 和时间线识别重叠与等待。

TTFT 是请求发出到第一个有效输出 Token 到达的时间。对一个典型文本请求，TTFT 通常包含 Gateway、路由、排队、预处理和 Prefill，以及产生首 Token 所需的执行。它不等于 Prefill Kernel 的耗时。若只测引擎内部 Prefill，就会漏掉排队和网络；若客户端缓冲流式响应，又可能把传输实现误认为模型慢。

逐 Token 延迟描述首 Token 之后相邻输出之间的时间，但用户感知并不只由平均值决定。偶发的长间隔会让界面卡顿，因此应观察分位数、最大间隔和连续卡顿长度。吞吐描述单位时间完成的工作，可以按请求、输入 Token、输出 Token或总 Token 统计。不同口径不能直接比较；长输出负载可能显示很高的输出 Token 吞吐，却让短交互请求大量超时。

Goodput 只计算满足服务等级的有效工作。若每秒产生很多 Token，但这些 Token 属于已经取消、已经超时或最终被丢弃的请求，吞吐很高而 Goodput 很低。生产优化应优先解释 Goodput 的变化，因为它把性能与用户承诺连接起来。

## 知识串讲：工作负载不是一个平均值

推理负载至少由到达过程、输入长度、输出长度、采样参数、模型或 Adapter、优先级、截止时间、前缀复用、工具调用、媒体数量和失败重试共同定义。只报告“平均输入 512、平均输出 128”会掩盖长尾。两个工作负载可能具有相同平均长度，但一个高度集中，另一个由大量短请求和少量超长请求组成；它们对批处理、KV Cache、排队和取消的压力完全不同。

到达过程决定瞬时并发。固定间隔请求适合调试，但不能代表突发生产流量。泊松到达可以模拟独立请求，回放真实时间戳则能保留业务节律和爆发。开放环压测按照预定速率发送，不会因为系统变慢而自动减速，适合观察过载；闭合环压测等待前一个请求完成再发送，容易在系统变慢时降低施压强度，从而掩盖排队崩溃。

输入长度主要影响 Prefill 计算和首 Token 时间，输出长度主要影响请求驻留时间、KV Cache 增长和 Decode 调度。长思考模型使输出长度成为计算预算；多模态模型还要把媒体数量、分辨率、帧数和 Encoder Token 纳入负载。Agentic 请求的单次用户任务会展开为多次模型调用，因此平台容量不能只按外部 QPS 计算。

前缀复用率会改变最优路由策略。若大量请求共享稳定系统提示和长文档，KV locality 价值很高；若提示高度随机，维护全局缓存索引可能得不偿失。工作负载定义必须记录前缀族、复用时间窗口和缓存失效条件，不能只记录 Token 长度。

## 原理与工程分析：三个平面

![课程配图](https://everythingai.top/api/assets/8e32ecbe-726e-4b4a-aa20-43059c789e85)

\*机制流程：把本课的输入、关键决策、执行与证据闭环连接起来。\*

### 数据面

数据面承载高频请求路径，包括协议解析、请求调度、模型执行、KV Cache、Token 流和必要的数据传输。它的首要目标是低延迟、可预测和可背压。数据面不应在每个 Token 步骤同步访问慢速控制数据库，也不应依赖不稳定的远程配置查询。需要的路由规则、模型元数据和配额快照应以可更新的本地结构进入热路径。

数据面的状态既有短暂状态，也有昂贵状态。请求队列和采样器属于短暂状态；模型权重、CUDA Graph、KV Cache 和媒体特征缓存属于昂贵状态。故障恢复策略取决于状态价值：有些状态可以丢弃重算，有些可以转移，有些应通过版本和校验保证重建一致。把所有状态都当成无状态 Web 服务会低估恢复成本。

### 控制面

控制面负责低频但高影响的决策：注册模型、创建部署、选择并行策略、分配 GPU、扩缩容、发布、回滚、排空和故障替换。控制面必须接受观测延迟和最终一致性。一个副本刚启动时，控制器可能已经看到 Pod Running，却尚未看到权重加载和引擎预热完成；因此健康状态需要区分进程存活、模型就绪和真实推理路径可用。

控制面最重要的设计不是 API 数量，而是状态机和不变量。例如，一个修订版在被路由之前必须通过制品校验、加载、预热和 Canary；一个副本在删除之前必须停止接收新请求并等待在途请求完成或迁移；一个扩容决策必须考虑已创建但尚未就绪的容量，否则控制器会重复扩容。把这些不变量写入控制器比依赖操作手册可靠。

### 证据面

证据面收集用于解释和决策的数据，包括请求级 Trace、引擎指标、队列与缓存事件、部署状态、版本信息、成本归属和实验记录。证据面与普通“监控面板”不同：它必须支持从用户症状反查到模型修订、路由选择、工作器状态和具体执行阶段，也必须支持把优化前后放在相同工作负载下比较。

指标用于聚合趋势，日志用于记录离散事实，Trace 用于表达跨组件因果路径，事件流用于重建控制器和缓存的状态变化。四者不可互相替代。只看平均指标无法解释单次异常；只看日志难以计算总体影响；没有版本和工作负载标签的 Trace 也无法形成可比较证据。

## 原理与工程分析：关键目标函数

系统优化需要明确目标函数。最简单的吞吐最大化可以写成：

$$
\max \; \text{Throughput}(x)
$$

其中 $x$ 表示批量、并发、并行策略、缓存、路由和硬件配置。这个目标通常不够，因为无限增大排队可能提高资源利用率，却让用户等待不可接受。加入服务等级后，可以用 Goodput：

$$
\text{Goodput}=\frac{\sum_i w_i\,\mathbf{1}(T_i\le D_i)\,U_i}{\Delta t}
$$

$T_i$ 是请求端到端延迟， $D_i$ 是截止时间， $U_i$ 是有效工作量， $w_i$ 是业务权重。指示函数只保留在截止时间内完成的工作。若请求被取消、输出无效或违反质量门禁， $U_i$ 也应为零。

成本约束可以写成：

$$
\min \; C_{valid}=\frac{C_{gpu}+C_{cpu}+C_{storage}+C_{network}+C_{failure}}{N_{valid\ token}}
$$

分母是满足质量和服务等级的有效输出 Token，而不是所有计算过的 Token。分子除了 GPU 时间，还包括权重存储与分发、CPU 预处理、网络、观测以及失败和重试造成的浪费。课程后续不会把供应商价格写死，而是把这些项参数化，以便在本地、私有集群和不同云环境复用。

可靠性可以作为约束：

$$
P(T_i\le D_i \land Q_i\ge Q_{min}) \ge SLO
$$

$Q_i$ 表示输出质量或结构正确性。推理系统不能通过截断所有长输出来获得漂亮延迟，也不能通过减少验证使投机解码改变目标分布。性能、质量和可靠性共同定义可接受区域，优化是在这个区域内寻找更低成本或更高容量。

## 原理与工程分析：排队与饱和

当请求到达率接近系统服务能力时，排队延迟会非线性上升。即使平均到达率低于平均服务率，只要请求长度方差很大或流量突发，长请求也会占用容量并形成队列。用简单的利用率 $\rho=\lambda/\mu$ 可以建立直觉： $\lambda$ 是到达率， $\mu$ 是服务率。当 $\rho$ 接近一时，任何抖动都可能造成长时间排队。

大模型推理比普通固定服务时间队列更复杂。请求在 Prefill 和 Decode 阶段消耗不同资源；连续批处理会让多个请求共享一步执行；KV Cache 容量限制可并发驻留请求；取消和抢占会改变实际工作量；投机验证一次处理多个候选 Token，但接受长度随机。尽管如此，排队直觉仍然重要：不能把 GPU 利用率百分之百视为无条件目标。留出适当 Headroom 能吸收突发、故障转移和长度误差。

服务能力也不是一个固定 QPS。相同模型在短输入短输出下可能支持很高 QPS，在长上下文长输出下能力显著下降。容量曲线应该以工作负载分桶表示，例如输入长度、输出长度、并发和缓存命中率，而不是只给一个峰值数字。控制面扩缩容需要查曲线或性能模型，不能把 CPU 服务的请求数阈值直接套用到 Token 工作负载。

## 原理与工程分析：局部优化如何传播

一个优化可能改变多层系统行为。以推测解码为例，草拟器提高接受长度后，每次目标模型验证可以产出更多 Token，低并发逐 Token 延迟下降；同时草拟器占用额外显存和计算，目标验证的序列更长，高并发下会与其他请求争用批处理槽位。路由器如果不知道某些副本启用了不同 Speculator，就可能把工作负载送到不匹配的配置。观测系统若只记录总 Token 数，也无法区分草拟 Token、验证 Token、接受 Token 和浪费 Token。

再看前缀缓存。提高缓存命中减少 Prefill，但缓存条目占用 KV 容量，可能挤压 Decode 请求；跨副本路由维护缓存索引会增加事件和网络开销；模型版本或 Tokenizer 变化会让旧缓存失效。一个“缓存开关”实际涉及数据面内存、全局路由、版本生命周期和证据面命中统计。

权重快速加载同样如此。并行读取和流式载入可以缩短启动，但会增加共享存储压力；多个副本同时扩容可能形成下载风暴；本地缓存提升后续启动速度，却需要磁盘空间、校验和淘汰策略；GPU 驻留权重复用能更快，但需要更严格的进程、设备和版本隔离。优化必须记录它改变的资源和故障模式，不能只记录成功路径的时间。

## 原理与工程分析：版本、配置与可复现性

可复现实验至少要冻结模型修订、Tokenizer、推理框架与提交或版本、CUDA 与驱动、GPU 型号和数量、精度、并行策略、引擎参数、工作负载样本、到达过程、随机种子、预热、测量窗口和客户端实现。遗漏其中一项不一定让实验无效，但会限制结论的可迁移范围。

模型名不是充分标识。远程仓库的同一分支可能更新，Chat Template 变化会改变 Token 数，框架默认参数也会随版本改变。实验记录应保存不可变修订和实际解析后的配置。若依赖自动选择 Attention Backend、量化 Kernel 或并行方式，应把选择结果写入报告，而不是只记录启动命令。

预热与稳态必须分开。首次请求可能触发权重页缓存、Tokenizer 初始化、Kernel 编译、CUDA Graph 捕获或内存池扩展。若目标是测冷启动，应保留这些成本；若目标是比较稳态吞吐，应在测量前执行可说明的预热，并确认指标进入稳定区间。把冷启动样本混入稳态平均值，会使结果既不能代表冷启动，也不能代表稳态。

客户端也会造成偏差。单线程客户端可能无法压满服务；同步读取流式响应可能把本地处理加入间隔；连接建立和 DNS 会影响首请求；超时与重试策略会改变实际到达率。可靠压测要同时观测客户端和服务端时间，并用请求 ID 对齐。

## 工程案例：平均值改善而长尾恶化

某次调度优化把短请求合并得更紧凑，平均 TTFT 从 420 毫秒下降到 360 毫秒，但 P99 从 1.8 秒上升到 3.2 秒。若只看平均值，优化成功；若交互服务的 SLO 要求 99% 请求在两秒内得到首 Token，优化失败。进一步按输入长度分桶后发现，短请求受益，长输入请求在高峰时被不断推迟。

正确分析需要回答：策略是否引入饥饿；优先级是否有等待时间补偿；长请求是否应该进入独立队列；是否需要为每个租户设置最小份额；在负载变化时阈值是否稳定。最终方案可能牺牲少量短请求平均值，换取长尾和公平性达标。平台目标是满足明确服务等级，不是让一个汇总数字最小。

## 工程案例：吞吐提高但有效成本上升

另一次优化提高了输出 Token 吞吐，但取消请求的比例也上升。原因是客户端在超时后断开，服务端没有及时传播取消，已经失去消费者的请求仍继续 Decode。GPU 指标显示忙碌，Token 计数不断增加，用户却没有收到结果。若成本分母使用所有输出 Token，单位成本看似下降；改用有效 Token 后，成本明显上升。

修复需要让取消从 Gateway 传播到路由器和引擎，释放队列、KV Cache 与调度槽位，并记录取消发生在排队、Prefill 还是 Decode。还要区分用户主动取消、客户端超时、网关超时和工作器失败。只有证据面能把“高利用率”重新解释为“无效工作”。

## 工程案例：扩容造成共享存储拥塞

流量峰值触发十个大模型副本同时启动。每个副本都从同一对象存储下载完整权重，下载带宽被均分，所有副本启动时间都变长；现有副本还要读取日志和检查点，共享网络进一步拥塞。扩容器看到新副本迟迟未就绪，又继续创建更多副本，形成正反馈。

解决方案不是简单增加最大副本数，而是把待启动容量计入决策、限制并发加载、使用节点或共享缓存、对权重进行校验和分片、测量下载与 GPU 装载的各段时间，并为扩容器设置冷却与预测。若流量可预测，还应提前预热而不是等队列爆发。这个案例说明控制器需要理解容量到达延迟。

## 工程案例：缓存命中掩盖热点副本

KV-aware 路由倾向把相同前缀送到已有缓存的副本。热门前缀持续命中同一副本，Prefill 成本下降，但 Decode 队列越来越长；其他副本空闲却没有缓存。单看缓存命中率策略非常成功，单看副本负载则明显失衡。

更合理的评分应同时考虑可复用 Token、预计 Prefill 节省、活动请求、等待 Token、KV 占用和预计完成时间。评分还要设置负载上限：当热点副本超过阈值时，即使牺牲缓存命中也应分流。缓存价值是节省的计算时间，不是命中率本身。

## 工程案例：发布健康但真实路径失败

一个新模型 Pod 的进程存活探针通过，HTTP 健康端点也返回成功，控制面开始导流。真实请求到达后才发现 Chat Template 不兼容或 GPU Kernel 在特定序列长度崩溃。被动健康检查只证明进程可以响应，不证明完整推理路径可用。

发布门禁需要分层：制品校验确认文件和配置；加载就绪确认模型已进入 GPU；最小真实推理 Canary 经过 Tokenizer、引擎和流式路径；代表性工作负载检查结构、质量和性能；逐步放量观察错误、TTFT、Decode 间隔和资源。任何一步失败都应停止推进并保留可回滚旧版本。

## 证据链：从假设到结论

![课程配图](https://everythingai.top/api/assets/5d179455-61ff-48fc-b992-f9a1b4c5ef91)

\*小黑故障现场：局部指标看似改善时，仍要追踪排队、资源和下游影响。\*

一次可发布的优化应形成完整证据链。第一步是写假设，例如“在低到中并发、输出长度较长且 Draft 接受率超过某阈值时，启用 Speculator 能降低逐 Token 延迟而不损害 Goodput”。假设包含适用条件和不希望发生的副作用，比“开启功能会更快”更可检验。

第二步定义工作负载，包括输入输出分布、到达过程、并发、采样、前缀复用、模型和硬件。第三步定义基线与候选配置，除被研究因素外保持其他变量一致。第四步选择指标和统计方法，规定预热、测量窗口、重复次数、置信区间和异常样本处理。第五步设置失败条件，例如 OOM、错误率、P99、质量门禁或取消浪费超过阈值。

第六步运行机制模拟，用简化模型验证方向、边界和控制逻辑。第七步运行真实路径，测量模拟没有覆盖的 Kernel、内存、框架和客户端成本。第八步解释差异，不能强迫真实结果符合模拟。最后把结论限定在实际证据覆盖的环境和负载内，并记录下一轮需要补证的范围。

## 机制模拟实验

本课模拟一个包含突发流量、可变服务时间、有限副本和扩容延迟的离散事件系统。模拟比较三种策略：固定副本；只根据队列扩容；同时考虑预测流量、待启动容量和启动时间。它不模拟具体 GPU Kernel，而是暴露控制面延迟如何影响排队、Goodput 和成本。

运行命令：

```
python lesson/00-cuda-baseline/run.py
```

脚本应输出请求数、完成数、SLO 内完成数、平均与分位延迟、最大队列、扩容次数、空闲副本时间和估算成本。验收时不要求得到固定数字，因为参数可以调整；要求满足以下行为：在相同工作负载和服务模型下，预测策略应更早增加有效容量；把启动时间改为零后，各扩容策略差异应显著缩小；把到达率长期提高到容量上限以上时，所有策略都应出现过载，证明控制器不能创造算力。

失败测试包括无效负到达率、零服务能力、启动时间超过模拟窗口和不连续时间戳。脚本应拒绝无效输入并给出清晰错误，而不是输出看似正常的曲线。

模拟证明控制面延迟、流量预测和 Headroom 会改变排队结果，也证明单看当前队列可能反应过晚。它不能证明某个真实引擎的服务时间分布，不能证明特定 GPU 的容量，也不能证明网络、KV Cache 和权重加载与简化模型一致。

## 真实 CUDA 实验

真实工作流直接执行“建立后续实验可复用的设备、计时与显存证据基线。”。运行输入为 `CUDA GPU` 、 `PyTorch` ；报告必须保留 `CUDA event boundary` 、 `request-level timing` 、 `allocator snapshot` 。只有 `source=measured` 可以支撑性能或发布结论， `source=fixture` 只验证控制逻辑。

环境预检：

```
python lesson/00-cuda-baseline/run.py --check-only
```

基线与候选测量：

```
python lesson/00-cuda-baseline/run.py --real --sizes 512,1024,2048 --repeats 5
```

预检至少记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架版本、模型修订或本地校验、精度和最终解析配置。预检必须给出原因、建议缩放项和约定的可识别退出码。

真实实验可以证明在所记录环境和负载下的服务行为，能发现模拟未包含的框架、Kernel、显存和网络成本。它不能直接证明其他 GPU、其他模型、其他推理框架或真实业务流量具有相同容量，也不能把单次短测量外推为长期可靠性。

## 结果分析与故障排查

![课程配图](https://everythingai.top/api/assets/17ccb8fd-7e90-4968-ac13-423796b6b877)

\*证据面板：联合观察工作量、性能、资源和服务等级，避免只看单一均值。\*

分析先检查实验是否有效，再比较性能。确认预检记录完整，预热与测量分开，请求实际达到目标速率，客户端没有成为瓶颈，错误和取消被计入，Token 口径一致。若服务端报告完成一百个请求而客户端只收到九十个，应先查流式连接、超时和统计边界，不能直接计算吞吐提升。

若 TTFT 高而 Decode 间隔稳定，优先检查排队、Prefill、输入预处理和路由。若 TTFT 正常但 Token 间隔长，检查 Decode 批处理、内存带宽、投机策略和同批长请求。若平均值正常但 P99 很高，按输入长度、输出长度、模型、租户、工作器和时间窗口分组，再沿 Trace 寻找共同阶段。

若提高并发后吞吐没有增长而延迟上升，系统已接近容量或受到某种串行资源限制。检查 API 服务器、Tokenizer、CPU、网络、GPU、KV Cache 和同步点。GPU 利用率低不一定表示 GPU 是瓶颈，可能在等待 CPU 或网络；GPU 利用率高也不一定表示工作有效，可能在处理已取消请求或低接受率验证。

若出现 OOM，记录发生阶段。加载即 OOM 通常与权重、精度、并行和固定内存有关；运行中 OOM 常与 KV Cache、并发、上下文或临时张量有关；只有某些结构化或多模态请求 OOM，则需检查额外状态和媒体特征。不要只降低一个全局显存比例而停止分析，应说明被释放的内存将如何影响容量。

若机制模拟预测扩容有效而真实系统无改善，检查新副本的就绪定义、权重下载、GPU 分配、路由发现和流量转移。控制器可能创建了资源但没有产生可路由容量。把启动关键路径分解后，再决定是提前预测、加缓存、限制并发加载还是保留 Warm Pool。

## 代码说明

可执行文件为 `lesson/00-cuda-baseline/run.py` 。所需的 HTTP、CUDA、统计、报告或状态机原语已经合并到这一入口。下方代码展示入口中内嵌的可读核心实现；下载包不再单独提供内部源码库目录。默认运行 Fixture，加 `--real` 才进入实测路径。

```
"""Lesson 00 — establish a real CUDA timing and memory baseline."""

from __future__ import annotations

import argparse

from phase3lab.shared.cuda_ops import cuda_environment, memory_snapshot, require_torch_cuda, timed_cuda
from phase3lab.shared.runner import LabSpec, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-00-cuda-baseline",
    title="CUDA Baseline：矩阵计算、显存与同步计时",
    goal="建立后续实验可复用的设备、计时与显存证据基线。",
    real_evidence=("CUDA event boundary", "request-level timing", "allocator snapshot"),
    required_inputs=("CUDA GPU", "PyTorch"),
    outputs=("shape sweep", "latency summary", "memory snapshot"),
    acceptance=("all shapes execute on CUDA", "samples are synchronized", "no CPU fallback"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--sizes", default="512,1024,2048")
    parser.add_argument("--repeats", type=int, default=5)

def parse_sizes(value: str) -> list[int]:
    sizes = [int(item) for item in value.split(",") if item.strip()]
    if not sizes or any(size < 16 for size in sizes):
        raise ValueError("--sizes must contain integers >= 16")
    return sizes

def fixture(args: argparse.Namespace) -> dict:
    sizes = parse_sizes(args.sizes)
    return {
        "plan": [{"size": size, "multiply_adds": 2 * size**3, "bytes_per_matrix_fp16": size * size * 2} for size in sizes],
        "assertions": {"monotonic_work": all(left < right for left, right in zip(sizes, sizes[1:]))},
    }

def real(args: argparse.Namespace) -> dict:
    torch = require_torch_cuda()
    records = []
    for size in parse_sizes(args.sizes):
        left = torch.randn((size, size), device="cuda", dtype=torch.float16)
        right = torch.randn((size, size), device="cuda", dtype=torch.float16)
        samples, product = timed_cuda(torch, lambda: left @ right, warmups=2, repeats=args.repeats)
        checksum = float(product[0, 0].float().item())
        records.append({"size": size, "latency": latency_summary(samples), "checksum": checksum, "memory": memory_snapshot(torch)})
        del left, right, product
    return {"environment": cuda_environment(torch), "sweep": records}

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

模拟和真实路径共用一套报告字段： `status` 、 `environment` 、 `workload` 、 `metrics` 、 `failures` 、 `limitations` 。统一字段不是为了假装二者等价，而是便于验收器明确区分 `fixture` 、 `measured` 和 `precondition_failed` 。任何数值都必须带来源类型。

## 原理与工程分析：怎样划定系统边界

系统边界决定哪些时间、资源和失败属于被测对象。边界过窄，会把真实成本推到图外；边界过宽，又会让任何变化都无法归因。一个实用方法是先从用户承诺出发，再向下追踪所有能改变承诺的组件。若承诺是“两秒内返回第一个 Token”，客户端连接、Gateway、身份检查、路由、排队、预处理、Prefill、首次采样和流式发送都在边界内。对象存储的日常维护未必在单请求边界内，但如果冷启动依赖它，便属于容量与恢复边界。

边界还要区分拥有者与依赖者。Gateway 团队可能不拥有模型工作器，却必须把工作器错误、超时和 Token 用量准确映射给客户端；控制面不执行 Token，却必须知道何时工作器真正就绪；观测系统不参与路由，却必须保留路由决策所用的输入，否则事后无法解释为什么选中某副本。责任边界不是为了互相甩锅，而是让接口具备可验证契约。

为每个组件写出输入、输出、状态、资源、超时、重试和可观测字段，可以暴露隐含耦合。以路由器为例，输入不只是请求和副本列表，还包括模型能力、版本、健康、活动负载、缓存索引与租户策略；输出不只是地址，还应包含决策原因、候选得分和策略版本。没有策略版本，线上行为改变后无法关联配置；没有候选得分，热点或误路由只能靠猜测。

边界设计还需要处理时间尺度。Token 调度以毫秒甚至更短周期变化，路由负载以几十毫秒到秒变化，扩缩容以秒到分钟变化，容量采购以天到月变化。慢控制环若直接追逐快噪声会振荡，快数据面若同步等待慢控制面会增加尾延迟。正确方式是为每个时间尺度定义抽样、平滑、迟滞和失败降级，并明确数据的新鲜度。

同一事实在不同边界有不同表达。引擎看到“活动序列数”，路由器更关心“预计剩余工作量”，扩缩容器关心“现有和待就绪容量”，成本系统关心“可归属的有效 GPU 时间”。平台不应强迫所有组件只共享一个粗糙利用率，而应建立可转换的指标语义。转换公式、时间窗口和丢失信息都要记录。

## 原理与工程分析：服务等级不是一个延迟阈值

服务等级目标首先需要定义服务对象。交互聊天关注首 Token 和连续流畅；离线批处理关注截止时间前完成的总量；代码 Agent 可能允许较长思考，但工具调用失败必须可恢复；结构化抽取关注格式合法率和字段正确率；多模态请求还要约束媒体解码失败和 Encoder 延迟。把所有请求塞进一个统一 P99，会让重要差异消失。

一个完整 SLO 至少包含指标、对象、窗口、目标比例和排除规则。例如“在滚动二十八天窗口内，标准交互请求中百分之九十九的成功请求 TTFT 不超过两秒”。这里仍有问题：什么是标准请求，成功是否把超时排除，客户端取消如何处理，模型质量失败是否算成功，低流量时间窗如何计算。每个词都需要可执行定义，否则团队可以用不同过滤条件得到不同答案。

不应把失败请求从分母中全部删除。若超时导致客户端断开，而统计只保留完成请求，系统越差，报表反而越漂亮。合理做法是区分有效请求、用户在收到足够响应后主动取消、客户端自身错误、平台拒绝、服务失败和未知状态。平台责任范围内的失败应进入可用性或延迟违约统计。

错误预算把目标比例转化为允许失败量。若目标是百分之九十九点九，一个月可容忍的失败并不多。发布、实验和容量策略应消耗同一个错误预算，而不是各自声称影响很小。当预算消耗过快时，应停止风险发布或降低非关键流量，而不是继续优化平均吞吐。错误预算让可靠性从口号变成资源分配约束。

多等级服务需要明确隔离。高优先级并不意味着可以无限抢占普通请求，否则普通队列会饥饿；低成本等级也不意味着质量和安全可以下降到不可接受。每个等级应规定最大等待、最小份额、可降级项、最大输出、模型集合和成本上限。调度器和 Gateway 必须使用同一等级标识，Trace 也要携带该标识。

服务等级的测量点应贴近用户。服务端内部 TTFT 可帮助定位，但网络缓冲、代理和客户端解析都可能改变用户首 Token。应同时记录客户端与服务端时间，并用统一请求 ID 对齐。两者差值若长期增大，说明问题不在模型 Kernel，而在传输或代理路径。

## 原理与工程分析：分位数、置信区间与比较方法

延迟分布通常偏斜，少量长请求产生很长尾部。平均值对尾部敏感，却不能告诉有多少请求违反目标；中位数稳定，却会忽略少数严重故障；P95、P99 描述高分位，但样本不足时估计不稳定。报告应该同时给出样本数、分桶、关键分位和超标比例，而不是只挑有利数字。

计算 P99 至少需要足够样本。若只有一百个请求，P99 几乎由最慢一个样本决定，重复一次就可能大幅变化。对低流量服务，可以延长窗口或使用直接的 SLO 违约计数；对压测，可以重复多轮并报告分位数区间。不能用一次短跑的 P99 宣称长期可靠性。

比较两个配置时，应尽量使用相同请求序列、到达时间和随机条件，形成配对样本。配对能减少工作负载差异造成的噪声。若模型采样具有随机性，可以固定种子用于性能复现，但还应说明固定种子并不代表真实输出分布。质量比较可能需要多个种子或确定性任务。

置信区间表达估计不确定性。吞吐和平均值可以通过重复运行或自助法估计区间；成功比例可使用适合二项分布的区间；长尾分位可以通过重采样估计，但必须保留请求级数据。若两个配置区间高度重叠，不应把微小点估计差异包装成确定提升。

稳态判断不能仅靠固定等待十秒。应观察关键指标随时间是否稳定，例如加载完成、缓存进入稳定命中率、吞吐和队列不再单调变化、显存池不再持续扩张。预热条件要写入报告。对缓存研究，预热本身是研究对象，不应被无意隐藏。

异常值处理必须预先定义。删除最慢请求可能正好删除系统故障。只有能证明样本来自实验外部问题，如客户端机器同时运行了无关重任务，才可单独标记；原始数据仍应保留。正确做法通常是分类解释，而不是悄悄清洗。

多次调参会产生选择偏差。尝试几十个配置后挑出最好一次，再与基线单次比较，提升可能来自噪声。应把调优集和确认集分开：先在一组负载上探索，再在未参与选择的回放上验证。生产 Canary 又是一层外部验证，它关注真实分布与故障，而不是重复离线跑分。

## 原理与工程分析：工作量口径与 Token 计量

请求数是最容易统计的工作量，却最容易误导。一个输入二十个 Token、输出十个 Token 的请求，与输入三万 Token、输出四千 Token 的请求对 GPU 压力完全不同。平台需要同时记录请求、输入 Token、缓存输入 Token、输出 Token、草拟 Token、验证 Token 和被丢弃 Token，并说明各类是否计费、是否进入容量模型。

Tokenizer 是计量的一部分。不同模型或模板对同一文本产生不同 Token 数；在 Gateway 预估 Token 可能与工作器最终 Token 不同；多模态模型会把图像或音频转化为内部 Token 或特征。计量系统应区分预估和实际，并规定对账误差。配额若只依赖响应结束后的实际 Token，可能在单个超长请求完成前无法阻止超额，因此还需要准入时的上界和运行中的截止机制。

缓存输入 Token 的成本低于重新 Prefill，但并非零。路由、索引、KV 占用和读取仍有成本。成本模型可以给缓存 Token 不同权重，但权重应来自测量而非固定拍脑袋。若缓存命中挤压了 Decode 容量，其机会成本也要考虑。

推测解码会产生目标模型未最终接受的候选。用户只看到接受 Token，但 GPU 执行了草拟与验证。效率指标可以定义为有效输出 Token 与总计算 Token 或总时间之比。高接受率通常有利，却不保证端到端加速，因为 Drafter 成本、验证批量和高并发竞争也会变化。

Agentic 请求需要任务级计量。一项用户任务可能包含规划、多个并行工具调用、重试、总结和反思。仅按单个模型请求计量，会看不见 Fan-out 和重试风暴。应保留外部任务 ID、内部调用 ID 和父子关系，从任务成功角度计算总 Token、总延迟和无效分支。

结构化输出需要把格式合法与语义正确分开。Grammar 可以保证 JSON 结构，却不能保证字段含义正确。Goodput 的质量门禁可以要求结构合法、字段验证通过和业务规则满足；仅统计输出 Token 会把无用但合法的结果算作有效产出。

## 原理与工程分析：路由完成时间估计

副本选择的核心不是“最空闲”，而是估计把这个请求放入某副本后的结果。一个简化完成时间可以写成：

$$
\widehat{T}_{finish,j}=\widehat{T}_{queue,j}+\widehat{T}_{prefill,j}+\widehat{T}_{decode,j}+P_j
$$

下标 $j$ 表示候选副本， $P_j$ 是健康、版本、跨域和不确定性惩罚。排队时间需要考虑活动请求剩余工作量，而不是只数请求；Prefill 时间取决于未命中的输入 Token；Decode 时间取决于预计输出、当前批处理和模型配置。

前缀缓存可以把 Prefill 估计改写为未命中 Token 的函数。设请求前缀长度为 $L$ ，副本可复用长度为 $H_j$ ，则需要重新计算约 $L-H_j$ 个 Token。但缓存条目是否仍在、哈希是否匹配、模型与 Tokenizer 版本是否一致都会引入误差。索引事件延迟意味着路由器看到的缓存状态可能过期，因此惩罚项应随数据新鲜度增加。

活动 Decode 请求的剩余长度通常未知。可以根据请求上限、已生成长度、任务类型和历史分布估计，也可以只使用活动 Token 和经验服务曲线。预测不可能完全准确，策略必须在误差下稳定。若一次低估会让请求错过严格截止时间，可以加入保守分位或安全系数；若目标是整体吞吐，可能接受更激进估计。

Power-of-Two Choices 先随机选少量候选再比较负载，可以降低全局采集成本并避免所有请求同时追逐一个瞬时最优副本。Least-Work 估计排队工作量，KV-aware 再加入缓存价值。策略选择取决于状态获取成本和负载特征，不存在永远最好的固定算法。

路由器还要避免同步拥挤。若所有实例同时根据同一旧快照选择最低负载副本，会出现羊群效应。可以使用局部预留、随机化、短期衰减、每次选择后乐观增加预计负载，或让路由器分片管理候选。任何方法都要记录决策时的状态版本，以便判断失败来自策略还是状态延迟。

跨机架或跨区域路由需要加入网络和故障域。缓存命中很高的远端副本可能增加首包延迟和出站成本；把所有流量集中到一个故障域会降低韧性。完成时间估计应在能力、健康和合规过滤之后进行，不能为了低延迟绕过数据边界。

## 原理与工程分析：扩缩容的状态机

扩缩容至少经历观察、估计、决策、创建、分配、下载、加载、预热、注册、就绪和导流。控制器若只维护“期望副本数”，会忽略各副本所处阶段。有效容量应只计算已通过真实推理就绪的副本；待启动容量应单独记录，以阻止重复扩容；失败启动需要退避和根因分类。

扩容触发信号可以来自队列、活动 Token、KV 使用、SLO 预测、流量预测或性能模型。CPU 利用率通常不是好信号，因为推理瓶颈在 GPU，且 CPU 忙碌可能来自 Tokenizer。GPU 利用率也有滞后和语义问题。队列 Token 与预计完成时间更接近用户影响，但需要引擎暴露可信数据。

缩容比扩容危险，因为会移除正在承载状态的副本。正确流程先停止新请求，再等待或迁移在途请求，处理 KV 和流式连接，注销路由，最后释放资源。强制删除会造成客户端断流和重试，重试又增加剩余副本压力。缩容门槛需要更保守并设置稳定窗口。

迟滞用于避免在阈值附近反复扩缩。例如扩容在利用率高于某值持续一段时间触发，缩容在更低阈值持续更久才触发。冷却时间不能简单设得很大，否则错过真实变化；它应与启动时间、负载波动和成本目标匹配。

预测扩容适合有周期的流量，但预测会错误。平台应设置最大提前量、置信区间和回退；预热容量如果没有到来流量，会产生空闲成本。可用错误预算与成本预算共同决定预测激进程度。对不可预测突发，则依赖 Headroom、快速启动和过载保护。

扩缩容不能独立于路由。新副本刚就绪时没有缓存，若立即均匀分流，可能让缓存总体命中下降；旧副本排空时，路由器必须知道其状态。控制面事件应驱动路由候选集合，路由指标也应反馈给控制器。

## 原理与工程分析：容量规划的四个层次

第一层是单副本性能曲线。对选定模型、精度、并行策略和硬件，测量不同输入输出分布、并发和缓存条件下的吞吐与延迟。曲线不应只有一个峰值点，而应找到从低负载到饱和的变化以及 SLO 可接受边界。

第二层是副本容量模型。把单副本曲线转化为每种工作负载类别所需副本数，并加入实例间不均衡、路由误差和背景任务。简单地用总 QPS 除以峰值 QPS 会低估长尾和混合负载影响。可以用离散事件模拟回放多类别流量，验证队列和缓存相互作用。

第三层是 Fleet 层。考虑模型组合、异构 GPU、并行组、显存碎片、故障域、维护、冷启动和共享存储。即使理论总显存足够，无法形成需要的连续 GPU 组也可能调度失败。容量要按可放置形状统计，而不是只求 GPU 总数。

第四层是业务与成本层。流量增长、模型升级、上下文增长、服务等级和预算都会改变需求。规划要给基线、预测区间、保守情景和触发采购或扩容的门槛。预测不是一次年度表格，而应定期用真实流量和性能曲线校准。

Headroom 包含不同来源：吸收随机突发、允许单副本故障转移、覆盖预测误差、支持发布双跑和应对长度增长。把这些混成一个百分比不利于决策。应分别说明每部分依据，避免在成本压力下随意削减后失去故障能力。

容量规划还要处理模型版本迁移。新版本可能权重更大、Token 更慢或输出更长；灰度期间新旧版本同时占用资源；回滚需要保留旧容量。发布计划必须进入容量日历，否则正常业务容量会被变更挤占。

## 原理与工程分析：故障分类与级联失效

故障可以发生在请求、进程、GPU、节点、网络、存储、控制面和依赖服务。请求级错误包括无效输入、超长上下文、约束冲突和客户端取消；进程级包括 OOM、Kernel 错误、死锁和崩溃；节点级包括 GPU Xid、驱动、温度、网络和磁盘；控制面包括重复发布、状态丢失和错误扩缩容。

不同故障需要不同动作。无效输入应快速拒绝，不应重试；瞬时网络错误可以有限重试，但必须幂等并尊重截止时间；GPU 进程崩溃可能需要摘除整个并行组；共享存储慢不能通过无限增加下载并发解决。统一“重试三次”会把故障放大。

级联失效常从容量损失开始。一个副本失败，流量转移到剩余副本，剩余副本队列上升并触发超时；客户端重试增加流量；扩容同时读取权重又占用网络；观测和日志量暴增；最终多个依赖一起退化。防护包括负载削减、重试预算、熔断、隔离、预留容量和明确降级。

负载削减应在系统失去服务能力前发生。可以按租户、优先级、预计成本或截止时间拒绝，返回可重试信息，并保护已经接收的请求。无差别接收直到全部超时，会消耗更多 GPU 且给所有用户更差体验。

故障隔离需要边界。不同租户、模型和服务等级可使用独立队列或资源池；重要控制组件要避免与大流量数据面共享同一故障资源；多副本应跨适当故障域。隔离会降低某些打包效率，因此要由风险和业务价值决定，而不是追求绝对隔离。

恢复完成的定义不是进程重启，而是服务能力恢复并通过真实路径。需要观测从故障发现、摘除、替换、加载、预热到重新导流的各段时间。平均恢复时间应按故障类型分组，否则一次快速进程重启会掩盖少数长时间权重重载。

## 原理与工程分析：多租户、公平性与资源归属

多租户平台面临的核心问题是不同请求共享昂贵且有状态的 GPU。租户差异体现在速率、长度、优先级、模型、Adapter、缓存和突发。只限制每秒请求数不足以保护系统，因为一个超长请求可能比许多短请求昂贵。应结合输入 Token、预计输出、并发、活动 KV 和累计预算。

准入控制在请求进入昂贵路径前执行。它检查身份、模型权限、上下文上限、服务等级、Token 预算和系统负载。对输出长度未知的请求，可依据上限或历史估计预留预算，完成后按实际结算。预留过少会超额，过多会降低利用率，需要动态校准。

公平调度可以按请求、Token 或 GPU 时间分配份额。按请求公平会偏向长请求，按 Token 公平仍可能忽略 Prefill 与 Decode 成本差异，按 GPU 时间最准确却最难实时估计。工程上通常使用可观测代理量，再通过离线对账修正权重。

优先级必须配合防饥饿。高优先请求可以更快，但普通请求等待达到阈值后应提升有效优先级或获得最小份额。否则持续高优先流量会让普通队列永远不完成。防饥饿规则必须进入模拟和故障测试。

成本归属需要沿请求传播租户、项目、模型、版本和任务 ID。共享缓存、共享基座模型和批处理使精确分摊复杂。可以把直接工作按 Token 或时间归属，把共享固定成本按预定规则分摊，并明确规则局限。成本报表应支持与 Gateway Token 计量、引擎执行和基础设施账单对账。

多租户还涉及隐私与缓存隔离。前缀或媒体缓存不能因追求命中而跨越不允许的边界；日志和 Trace 不应默认记录完整敏感内容；调试采样要有权限与保留策略。性能收益必须在数据治理约束内取得。

## 原理与工程分析：观测字段与基数控制

指标标签需要足够解释问题，又不能产生无限基数。模型逻辑名、稳定版本、服务等级、工作器池和结果状态通常适合指标；完整请求 ID、用户文本和任意租户名可能造成基数爆炸，更适合 Trace 或受控日志。租户指标可使用受管理的内部 ID，并限制活跃集合。

直方图桶应匹配服务目标。若 TTFT 目标是两秒，而最大桶只有一秒，所有超标请求都会挤在同一范围；若桶过密，存储和查询成本增加。桶边界应覆盖从正常到严重退化，并与 SLO 阈值对齐。

Trace 采样不能只随机。随机采样适合总体，但错误、超时、发布、长尾和特定模型版本应提高采样率。尾部采样可以根据完成状态决定保留，却需要缓存 Trace。采样策略和版本本身也要记录，否则样本比例变化会被误认为故障比例变化。

日志字段应结构化并携带时间、请求、任务、租户、模型、修订、工作器、路由决策和错误分类。不要在每个 Token 写冗长日志，避免 I/O 影响热路径。需要逐步信息时可用受控事件或短时诊断模式，并设自动关闭。

指标、日志和 Trace 的时钟需要同步。跨节点时间偏差会让事件顺序错误，尤其在毫秒级路由和流式分析中。报告中应记录客户端和服务端时钟来源，对无法保证同步的环境使用单调时钟测本地间隔，并用事件关系而非墙上时间判断因果。

观测系统也会失败。指标抓取丢失、日志队列拥塞、Trace 后端延迟都可能造成盲区。关键控制器不能把“没有指标”解释为“没有负载”；应设置数据新鲜度、缺失告警和安全回退。证据面容量也要规划，避免故障时数据量激增反过来拖垮数据面。

## 原理与工程分析：决策记录和发布评审

每项重要优化应有简短决策记录，包含问题、环境、备选方案、选择、证据、风险、回滚和复查时间。记录不是长篇会议纪要，而是防止团队几个月后忘记当时约束。框架升级、硬件变化或工作负载漂移后，应重新检查决策是否仍成立。

发布评审先检查证据完整性，再讨论点估计提升。确认课程或团队承诺的指标均被测量，失败测试执行，代码与配置可追踪，客户可见行为未被意外改变。若只在一个短负载上变快，而未测试高并发、长上下文和取消，评审应把结论限制为实验状态。

Canary 需要明确流量选择。随机百分比可能无法覆盖长请求、特定租户或多模态；也可能让同一会话在版本间漂移。可以按租户、会话或请求特征稳定分桶，并保留对照。Canary 指标要关注相对基线和绝对 SLO，同时防止样本太少。

自动回滚门槛要避免误触发和迟触发。单个错误可能是噪声，等待过长又会扩大影响。可以结合最小样本、连续窗口、严重错误立即回滚和多指标规则。回滚本身也要验证，因为旧版本容量可能已经被缩掉或缓存已失效。

发布后仍需观察稳定期。缓存、内存泄漏、流量适配和成本问题可能数小时后出现。完成全量不等于评审结束，应设置长期指标和下一次复查。若效果与离线实验不同，要保存真实流量差异并更新工作负载模型。

## 实验扩展：把模拟与真实测量连接起来

模拟中的服务时间不应随意设定。可以先用真实路径在不同输入、输出和并发下测量 Prefill 与 Decode 时间，再拟合简单曲线作为模拟输入。拟合报告要保留残差和适用范围。模拟利用真实测量后更有解释力，但仍不代表完整生产系统。

一种连接方式是把真实请求级记录转换为可回放 Trace。模拟保留到达时间、长度、类别和截止时间，用抽样或回归估计服务成本，再测试路由和扩缩容。这样无需每次策略探索都占用 GPU，筛选出的少量候选再进入真实验证。

另一种方式是影子决策。生产路由仍使用稳定策略，新策略只计算“本来会选择哪个副本”并记录，不真正导流。结合实际结果可以评估候选策略的状态新鲜度和决策差异。但由于请求没有真的进入候选副本，不能直接知道反事实完成时间，只能作为风险较低的预检。

故障注入也应分层。模拟可以快速测试副本突然消失、启动延迟翻倍和状态事件丢失；本地真实环境可以杀死工作器、断开连接或制造 OOM；生产前测试可以在隔离流量中验证排空和回滚。每层故障强度不同，结论边界必须写清。

实验自动化应保存不可变配置和原始数据。只保留图表会丢失重算能力；只保留聚合 JSON 会看不见异常请求。原始记录可做脱敏和压缩，但至少应保留请求时间、类型、长度、状态、关键阶段和版本。生成的结论应能追溯到原始记录与脚本版本。

当模拟与真实结果冲突时，不应选择更喜欢的一方。检查服务模型是否漏掉批处理、缓存、内存或客户端瓶颈；检查真实实验是否达到目标负载和稳定状态；检查指标口径是否一致。冲突通常是发现新机制的入口，也是模型更新的依据。

## 全景分析：生成加速改变了什么

普通自回归解码每轮读取模型权重与 KV Cache，产生一个新 Token。推测解码引入较便宜的候选生成路径，再由目标模型并行验证多个候选。它保持目标分布的前提，是接受、拒绝和补偿采样严格遵守算法；性能收益则取决于草拟时间、验证时间、接受长度和系统负载。算法正确性与系统加速是两个门槛，任何一个不通过都不能发布。

设平均每轮接受 $a$ 个候选并得到额外 Token，草拟耗时为 $T_d$ ，目标验证耗时为 $T_v(a)$ ，普通单步耗时为 $T_b$ 。理想直觉可写成每个有效 Token 的时间约为 $(T_d+T_v)/(a+1)$ 。但这个表达省略了拒绝、采样、树构造、批处理和排队。它适合解释变量方向，不适合直接预测生产速度。

不同 Drafter 改变 $T_d$ 与接受分布。自回归 Drafter 质量高但草拟仍串行；并行多 Token Drafter 一次产生多个位置，草拟快却可能出现后缀质量衰减；块扩散 Drafter 使用非因果依赖并行预测；候选树用更多验证节点提高命中机会，也增加目标模型成本。工程选择应比较完整 Pareto 前沿，而不是只看论文中的最大速度比。

在低并发时，目标 GPU 可能没有被充分利用，验证多个 Token 能把闲置算力转化为更低逐 Token 延迟。在高并发时，普通连续批处理已经让 GPU 饱和，额外候选会占用批处理容量，可能减少其他请求的服务机会。因此 Speculator 策略应观察负载，根据模型、领域、请求类型和并发选择深度，甚至在过载时关闭。

接受率会随领域和版本漂移。代码、重复文本和固定格式可能容易预测，开放聊天和高温采样更难；Chat Template、Tokenizer、模型修订和用户分布变化都会影响。Speculator 必须像模型制品一样有训练数据、版本、适配关系、离线评测、Canary 和回滚。仅把一个 Draft Checkpoint 放到引擎参数中，不足以形成生产能力。

证据面需要区分草拟 Token、提交验证 Token、接受 Token、额外目标 Token、拒绝位置和每轮时间。只有总吞吐无法解释收益来自接受变长还是批处理变化。还应按并发、领域、采样和输出阶段分组，防止总体平均掩盖特定请求退化。

## 全景分析：长思考请求改变了容量模型

Reasoning 模型的输出可能很长，且长度与问题难度、预算和提示相关。过去把最大输出长度当作保护上限，现在它同时是计算预算和产品策略。平台需要支持用户或服务等级指定预算，调度器依据预算准入，Gateway 对超额行为给出一致响应，计量系统区分思考与最终输出。

长输出使请求驻留更久，KV Cache 持续增长，对其他请求形成占用。若调度只按到达顺序，少量长任务可能提高短请求 TTFT；若总是偏向短请求，长任务又可能饥饿。可以设置独立队列、加权公平、时间片、最小份额或预算分层。策略要在完成率、交互性和吞吐之间明确取舍。

Test-Time Scaling 可能运行多个候选推理再选择答案，外部一个请求会展开为内部多条分支。容量模型应使用分支数、每分支预算、早停和汇总成本，而不是只看用户 QPS。若分支可以并行，瞬时 GPU 压力更大；若串行，端到端延迟更长。路由和取消需要传播到整个任务树。

当截止时间接近时，系统可以停止低价值分支、缩短剩余预算、切换模型或返回已有最好答案，但这些降级必须由产品契约允许。不能为了延迟偷偷截断，使质量无法解释。每个降级动作应作为事件进入 Trace，并在结果中标识。

Reasoning 输出解析也会影响服务。不同模型使用不同思考标记，流式解析必须正确处理边界；结构化最终答案可能只在思考结束后启用 Grammar。错误解析会把思考泄露到不应显示的字段或错误计算 Token。模型版本与 Parser 版本必须绑定。

测量长思考服务时，应按问题类别和预算分桶，报告完成率、首 Token、总时长、平均 Token 间隔、实际输出长度、被截断比例和单位成功任务成本。仅比较每秒 Token 可能鼓励模型产生更多无效思考，必须结合任务质量。

## 全景分析：Agentic 请求为何需要任务级控制

Agentic 请求由模型调用、工具调用、环境交互和状态更新组成。模型可能并行调用多个工具，工具结果又触发后续推理。一个外部请求形成有向执行图，而不是一条固定流水线。平台需要同时管理单次模型请求和整个任务的截止时间、预算、身份与取消。

Deadline Propagation 把外部截止时间分配给内部阶段。每个子调用不仅知道自身超时，还知道任务剩余时间。若工具已经消耗大部分预算，再启动一个不可能按时完成的长推理只会浪费资源。调度器可以基于剩余时间拒绝或降级，但决策要保留原因。

Budget Propagation 同样重要。外部任务的 Token、工具次数和成本上限应在分支之间分配。并发分支若各自认为拥有完整预算，会造成超额。预算服务需要支持预留、提交、释放和幂等，工具失败或分支取消时释放未使用部分。

重试必须具备幂等语义。模型请求通常可以重新计算，但工具可能产生外部副作用，如创建订单或发送消息。没有幂等键的重试会重复执行。Gateway、Agent Runtime 和工具服务应共享任务与调用 ID，并区分安全重试、需要查询状态和禁止重试的操作。

Fan-out 会放大故障。一百个用户任务各产生十个并行分支，内部 QPS 变为一千；某工具变慢后，分支堆积，模型等待又占据会话资源；统一重试进一步放大。平台容量和限流应以任务展开系数建模，并为每个任务限制并发分支。

任务级 Trace 要表达父子、并行、重试和汇合关系。单纯按时间排序日志无法区分哪个分支属于哪个任务。成功率也应从任务目标计算：某个内部调用失败但被替代，任务仍可能成功；所有模型调用都成功但最终没有完成业务目标，任务仍是失败。

## 全景分析：结构化输出的隐性成本

结构化输出不是生成完成后修复 JSON，而是在每一步限制可选 Token。JSON Schema、正则或 EBNF 先编译为 Grammar 或状态机，当前状态决定允许 Token 集合，再把掩码应用到模型 Logits。这样可以保证语法路径合法，但引入编译、缓存、状态更新和掩码成本。

编译成本对短输出尤其明显。若每个请求带一个几乎相同但字节不同的 Schema，缓存无法复用，TTFT 会被 CPU 编译拖慢。平台应规范化 Schema、设计稳定 Cache Key、限制复杂度，并观测命中率、编译时间和缓存大小。Cache Key 必须包含影响语义的版本，避免错误复用。

逐步掩码成本取决于词表、后端、状态复杂度和批处理。不同请求处于不同 Grammar 状态，可能增加批处理分歧；在 GPU 上应用掩码可以减少 CPU 往返，却需要兼容执行图和内存。不能只测一个简单枚举 Schema，就宣称复杂嵌套结构无开销。

Reasoning 模型可能要求思考段不受 Grammar 限制，最终段再启用。状态机需要识别思考结束标记；标记丢失或模型输出异常时，要有超时和失败策略。工具调用本质上也是结构化输出，工具参数 Schema 与 Parser 必须与模型模板匹配。

结构合法不等于语义正确。字段可能为空、类型虽正确但值不合理、枚举选择错误。平台应把 Grammar 合法率、业务验证率和任务成功率分开。若只报告百分之百合法 JSON，会高估质量。

约束解码与推测解码组合时，Drafter 和目标验证必须遵守同一 Grammar 状态。候选被拒绝后状态回退要正确；候选树中不同分支有不同状态。算法正确性测试应覆盖拒绝、回退、流式和缓存，性能测试再比较收益。

## 全景分析：多模态服务的异构关键路径

多模态请求包含下载、格式验证、解码、采样、缩放、分帧、预处理、Encoder、特征投影、LLM Prefill 和 Decode。不同阶段使用网络、CPU、内存和 GPU。只观察 LLM GPU 会漏掉媒体路径，尤其在高并发时，CPU 解码和远程下载可能成为 TTFT 主要来源。

媒体大小不是唯一成本。图像分辨率、切片策略、视频帧数、音频时长和模型处理方式共同决定内部 Token 或特征数量。外部一个 URL 可能指向巨大文件，准入控制要在下载前设置大小、类型、时长和超时上限，防止少量请求占满带宽与内存。

Media Cache 可以保存原始字节、解码结果、预处理张量或 Encoder 特征。越靠后的缓存节省越多计算，但与模型、预处理版本和精度绑定越紧。只用 URL 作为 Key 不安全，因为内容可能变化；应包含内容摘要、处理配置和模型修订。缓存还要遵守租户和隐私边界。

Encoder 与 LLM 可以同卡或分离。同卡减少特征传输和部署复杂度，却会争用显存与计算；分离便于独立扩缩容，增加网络和序列化。选择取决于媒体与文本流量比例、模型大小、特征体积和硬件。应测完整关键路径，而不是分别测两个峰值吞吐后相加。

视频请求具有时间维度。采样更多帧可能提高质量，也线性或更快增加编码成本；场景变化决定均匀采样是否有效。服务可以按预算选择帧数和分辨率，但必须记录实际策略。不同请求的媒体阶段差异会影响批处理，应考虑按形状分桶或异步流水。

多模态失败需要细分为下载、格式、解码、预处理、Encoder、投影、LLM 和输出。统一返回“模型错误”既不利于客户端修复，也不利于平台定位。Trace 应记录媒体摘要和尺寸等非敏感元数据，避免默认记录内容。

## 全景分析：Compound AI 的端到端优化

Compound AI 请求串联检索、Embedding、Reranker、LLM、工具和后处理。端到端延迟由关键路径决定，而不是所有阶段耗时简单相加；并行分支取最大完成时间，串行阶段求和，重试和回退形成条件路径。优化一个不在关键路径上的阶段，可能对用户延迟几乎没有影响。

阶段预算把总截止时间分配给每个组件。预算不应静态平均，因为 LLM Decode 与检索的成本性质不同。可以根据历史分布、请求类型和剩余时间动态分配。每个阶段需要在预算耗尽前返回成功、可降级结果或明确失败，不能无限等待。

Bulkhead 隔离不同阶段的资源。Embedding 高峰不应耗尽 LLM Gateway 连接，慢工具不应占住所有 Agent 工作槽，Reranker 失败不应让检索线程堆积。独立队列、并发限制和超时可以阻止级联，但过度隔离会浪费共享资源，需要按故障影响设计。

Fallback 必须定义质量和成本。Reranker 超时时跳过可能降低结果质量；主模型不可用时切换小模型可能改变输出；检索失败时直接回答可能增加幻觉。每种回退都要由产品允许，并通过质量评测。平台应统计回退触发率和最终任务成功率。

重试预算在链路中共享。若每个阶段独立重试三次，五阶段最坏调用数会爆炸。外层任务应给总重试次数或时间预算，内部阶段根据错误类别消费。已经超过截止时间的重试没有价值。

端到端 Trace 要记录阶段输入输出摘要、版本、缓存、重试和预算，但避免敏感内容。指标同时报告局部服务等级和任务服务等级。局部全部达标而任务不达标，说明预算组合或隐藏等待存在问题。

## 全景分析：模型生命周期与不可变发布

模型发布单元不仅是权重。Tokenizer、模板、量化配置、并行策略、推理框架、Parser、Grammar Backend 和 Speculator 兼容关系都可能改变行为。生产发布应把这些组成不可变 Revision，并生成校验。逻辑模型名只指向经过门禁的 Revision。

生命周期通常包括登记、验证、准备、部署、预热、Canary、扩量、稳定、排空和归档。每个状态有允许操作和退出条件。没有状态机时，用户可能请求到正在加载的副本，控制器可能删除仍有流量的版本，回滚也可能找不到完整旧配置。

制品验证包括文件存在、摘要、格式、配置兼容、Tokenizer 与权重匹配、需要的自定义代码策略和安全扫描。加载验证关注内存与算子；功能验证运行确定输入；质量验证使用代表任务；性能验证检查服务等级。不同验证不能合并为一个“健康”。

Canary 应与旧版本并行，使用稳定分流和可对账指标。模型输出随机使逐请求完全一致不现实，可以使用结构、任务得分、拒答、安全和性能分布比较。严重兼容错误应立即回滚，轻微性能差异需要足够样本。

排空是发布的一部分。停止新流量后，长请求可能仍运行很久；等待、迁移或终止要有上限和客户端语义。强制终止前应发出可重试状态并避免重复副作用。排空时间本身影响发布速度和容量占用。

归档保留可回滚字节、配置、评测和发布证据，但不一定长期保留所有 GPU 缓存。保留策略由恢复目标和存储成本决定。删除旧制品前，要确认没有部署、实验、会话或审计引用。

## 全景分析：权重移动与冷启动关键路径

大模型冷启动可以拆成调度等待、镜像拉取、权重获取、文件读取、反序列化、CPU 内存准备、GPU 拷贝、分片通信、内存分配、执行图准备、Tokenizer 与服务启动、预热和路由注册。总时间由串行段和重叠段构成。只记录 Pod 创建到 Ready 的总时间不能指导优化。

共享存储标称带宽不代表单文件实际带宽。读取模式、并发、文件分片和条带布局都会影响。单线程小块读取可能无法利用并行文件系统；盲目增加并发又可能让多个副本互相争用。应测每阶段吞吐、CPU 和存储队列。

节点缓存避免重复下载，但需要空间与淘汰。缓存命中取决于模型部署位置，放置器若不知道缓存可能错过收益。缓存摘要确保字节一致；模型版本更新要生成新 Key，不能覆盖后让旧进程读到混合文件。

流式加载把权重从对象存储或共享文件系统并发送入 GPU，可以重叠读取与拷贝。预分片权重减少每个并行 Rank 读取无关数据。优化要考虑文件布局与并行策略绑定，错误分片会增加转换或无法复用。

Warm Pool 保留已经准备的资源，换取更快扩容。可以保留空 GPU 节点、已下载权重、CPU 内存副本、休眠引擎或 GPU 驻留权重，层次越靠近执行越快也越贵。业务应根据峰值频率和恢复目标选择，不是所有模型都常驻。

预热应代表真实路径，包括 Tokenizer、模板、最大形状、常用 Grammar 或多模态 Encoder。只生成一个 Token 可能无法触发大形状执行图。预热过重会延长就绪，过轻会把成本推给首批用户，需要分层就绪或后台继续准备。

## 全景分析：异构 GPU 与放置约束

异构 GPU 不只是算力不同，还包括显存、内存带宽、精度支持、互联、NUMA、驱动和可用 Kernel。模型是否能运行先由权重和 KV 内存决定，达到服务等级再由性能决定。放置器必须过滤不可行设备，再比较效率。

多 GPU 副本需要形成并行组。张量并行通常偏好高速互联，跨慢网络会增加同步；流水并行关注阶段平衡；专家并行关注 All-to-All。总 GPU 数足够并不意味着可以找到满足拓扑的组。资源表示应包含设备集合和互联关系。

显存预算由权重、KV Cache、激活、通信缓冲、执行图和框架开销组成。只用参数量乘字节估算会遗漏运行空间。放置前应留 Headroom，并用真实加载校准。不同上下文和并发改变 KV，需要把服务配置与放置绑定。

性能等级不能只按型号静态排名。某些量化或 Kernel 在特定架构上可用，另一些模型受内存带宽而非算力限制。平台可以维护经验证的模型—配置—硬件 Profile，未知组合先进入小规模测量。

亲和性用于利用本地权重、缓存和网络，反亲和性用于故障隔离。两个目标可能冲突：把所有副本放在有缓存的节点启动快，却集中风险。放置评分应把启动收益与故障域约束分开，硬约束先过滤，软偏好再评分。

资源碎片来自形状不匹配。集群剩余多张 GPU，但分散在不同节点或显存等级，不足以放置一个大模型组。Bin Packing 要考虑未来需求，不应总把当前任务塞进最紧位置。保留可形成大组的节点可能提高整体可调度性。

## 全景分析：自动扩缩容为何容易振荡

推理扩缩容具有长反馈延迟。控制器看到队列上升，创建副本；副本几分钟后才就绪。在此期间队列继续上升，若控制器每轮都按当前缺口创建，会严重过量。必须把在途容量和预计就绪时间放入状态。

负载指标也有延迟。Prometheus 抓取、聚合和查询可能让控制器看到数十秒前状态；路由改变后又要等待效果。过短控制周期追逐旧数据会振荡。控制器应记录数据时间戳，使用预测或滤波，并设置速率限制。

扩容与缩容阈值不同，缩容观察窗口更长。扩容错误主要增加短期成本，缩容错误会造成违约和重新冷启动。具体设置由启动时间、流量波动和成本决定，不能照搬 CPU Web 服务模板。

Token-aware 指标比请求数更接近工作量。Prefill 队列可用等待输入 Token，Decode 可用活动 KV 或预计剩余 Token；但模型和硬件服务率不同，需要转换为预计时间。Planner 可以结合性能模型和实时指标。

预测模型可使用周期、趋势和业务事件，但必须有不确定性。预测失败时，实时负载环接管。长期预测给容量下限，短期负载应对突发，两者可以叠加而非互斥。控制器需要防止两个环互相覆盖。

过载时扩容未必来得及，必须同时负载削减。按优先级、成本和截止时间拒绝新请求，保护已接收请求，通常比让所有请求超时更好。拒绝率和原因进入 SLO 与容量复盘。

## 全景分析：可靠发布与故障恢复

可靠性从设计不变量开始。路由器永远不应把新请求送到未就绪或正在排空副本；控制器永远不应把失败启动算作有效容量；计量系统不应把草拟或取消浪费当成用户输出；发布系统不应删除唯一可回滚 Revision。把这些写成自动测试，比故障后补文档有效。

健康检查分为被动和主动。进程存活与 HTTP 健康是被动；Canary 发送最小真实请求经过 Tokenizer、模型和流式输出是主动。主动检查有 GPU 开销，应在空闲或低频执行，并避免使用会产生副作用的请求。

故障发现后先摘除再恢复。路由器快速停止新流量，控制面决定重启、替换或迁移。对未知状态的工作器，不应继续发送请求等待超时。摘除事件和恢复状态需要有租约或心跳，防止网络分区下出现两个所有者。

在途请求恢复取决于状态。若只有已输出 Token，可从文本重新 Prefill，但增加延迟；若能迁移 KV Cache，可减少重算但复杂；对有工具副作用的 Agent 任务，还要恢复调用状态。平台应明确哪些请求可透明恢复，哪些返回可重试错误。

Graceful Drain 先停止准入，等待活动请求降到零或截止时间，必要时迁移或终止。长思考请求可能让排空很慢，可以限制最大排空时间并在发布前估计。客户端要收到清晰结束语义，避免静默断流。

故障演练应覆盖工作器崩溃、GPU 错误、节点失联、共享存储慢、路由状态丢失、控制面重启和观测缺失。演练不仅看是否恢复，还测发现、摘除、替换、就绪和服务恢复时间，并检查是否发生重试风暴或成本异常。

## 全景分析：推理经济学的正确分母

GPU 小时是资源成本，不是产品单位。要比较系统方案，需要选择有效产出作为分母，例如满足质量和 SLO 的输出 Token、成功任务或合格文档。不同业务可以使用不同单位，但必须避免把无效计算计入产出。

成本分子包含直接计算、空闲、冷启动、缓存、存储、网络、CPU、控制面、观测和失败。共享成本可以按容量、使用或业务规则分摊。分摊不一定绝对精确，但规则要稳定、可解释并能对账。

高利用率通常降低空闲成本，却可能增加排队和违约。最经济点常在饱和之前。通过性能曲线找到 Goodput 最大或单位有效产出成本最低的区间，再为突发与故障留余量。单纯追求百分之百利用率会把风险转化为失败成本。

缓存、Speculator 和多路复用都用额外复杂度换取效率。评估时要加入维护、显存和错误风险。某优化在峰值基准节省 GPU，却增加发布失败或不兼容，长期总成本未必更低。决策记录应包括运营成本。

模型选择也是经济决策。小模型成本低但可能需要重试或无法完成任务，大模型单次贵却一次成功。正确比较是成功任务总成本与质量，不是单 Token 价格。Gateway 路由可以按任务难度选择，但要有评测和回退。

价格和硬件会变化，所以课程使用参数化模型。输入设备小时成本、功耗、折旧或云价、有效吞吐、空闲率、失败率和共享费用，输出敏感性分析。判断结论是否只在某个价格假设下成立，比写死一个数字更耐用。

## 全景分析：安全与性能不能分离

推理平台的身份、权限和凭证位于热路径。Gateway 验证调用者并决定可用模型、预算和工具；内部服务使用短期身份访问权重、缓存和遥测。为了降低延迟而绕过鉴权，会让任何性能收益失去发布资格。

多租户缓存需要防止数据越界。前缀、媒体和特征缓存可能包含敏感信息，Cache Key 和访问策略必须绑定允许的共享范围。全局命中率不是最高目标，隔离与合规是硬约束。必要时牺牲跨租户复用。

日志和 Trace 会记录提示、工具参数或输出。默认只保留必要元数据，对内容采样进行脱敏、授权和保留限制。调试模式应有时间和范围，避免故障排查打开永久内容日志。观测数据本身也需要访问控制。

模型制品和自定义代码具有供应链风险。加载前验证来源、摘要和允许的执行方式；不应为方便启用未知远程代码。发布门禁包含依赖和镜像扫描，运行环境限制网络和文件权限。安全失败应阻止导流。

配额同时是成本和安全控制。异常脚本、泄露密钥或循环 Agent 都可能产生巨量 Token。按用户、团队、模型和时间窗限制，并在接近上限时告警。配额状态需要跨 Gateway 实例一致，失败时选择安全策略。

拒绝与错误响应不能泄露内部拓扑、模型路径或凭证。客户需要可操作信息，如输入过长、配额耗尽或暂时过载，内部详细原因进入受控日志。性能压测也应使用测试身份和隔离数据，避免把生产敏感请求复制到不安全环境。

## 全景分析：从本地实验迁移到生产的步骤

第一步建立单进程功能基线，确认输入、输出、正确性和资源。第二步在单 GPU 上测不同工作负载，找到容量曲线。第三步增加真实客户端与流式路径，避免离线 API 差异。第四步部署多个副本和路由，观察负载与缓存。第五步接入控制面、发布、扩缩容和故障。每一步都保留基线和验收。

本地小模型适合验证机制和脚本，但不能代表大模型绝对性能。迁移时重新测权重加载、并行通信、KV 容量和 Kernel。若某功能只在特定硬件可用，课程实验应报告不支持，而不是通过模拟宣称可用。

生产流量不能直接用于第一次实验。先使用合成分布和脱敏回放，验证过载、失败和回滚，再做小比例 Canary。Canary 需要受控租户或稳定分桶，并有停止条件。任何自动调参先影子运行，避免直接改变关键请求。

环境差异要显式。容器、驱动、网络、存储、CPU、GPU 拓扑和观测都会改变。迁移清单记录差异及风险，优先验证可能改变结论的项。不能只说“同样代码所以结果相同”。

生产长期运行暴露内存泄漏、缓存漂移、日志增长、模型热度变化和依赖抖动。短压测通过后还需要浸泡测试和运行期门禁。发布后持续比较基线，出现漂移重新进入实验闭环。

最终，实验不是发布证明的终点，而是证据链的一层。可靠产品把研究假设、代码、配置、原始记录、分析、Canary 和长期指标连接起来。任何人都能从一次异常回到当时模型、负载和决策，才算建立生产级能力。

## 定量推演：判断生成加速是否值得启用

假设普通解码每步耗时十毫秒，一个请求输出一百个 Token，理想 Decode 时间约一秒。候选方案每轮草拟耗时三毫秒，目标验证耗时十二毫秒，平均接受三个候选并得到一个额外 Token，则四个有效 Token 约耗时十五毫秒，表面上每 Token 三点七五毫秒。这个计算提示低并发有潜在收益，但还没有加入初始化、采样、候选树、显存和排队。

若高并发下目标验证因为更长序列和更大批量增长到二十五毫秒，草拟器又占用本可用于 KV 的显存，使并发容量下降，单请求仍可能比普通解码快，但系统 Goodput 可能下降。应在相同到达率下比较完成请求与 SLO，而不是分别让两个配置跑到各自最大吞吐后比较。

接受长度也有分布。平均三不代表每轮都三，若很多轮第一 Token 就拒绝，草拟成本无法摊薄；少数超长接受会抬高平均。报告应给每轮接受直方图、拒绝位置和按请求类型分组。选择验证深度时，应估计额外候选的边际接受概率与边际验证成本。

质量验证先于性能。使用非贪心采样时，接受与补偿必须保持目标分布；结构化输出还要维持 Grammar 状态。可用小词表或已知分布做统计测试，再运行端到端任务。若实现只在温度零正确，必须限制产品配置或修复算法，不能在其他采样下继续报告速度。

显存预算决定可行区间。Drafter 权重、隐藏状态、候选树和额外执行图都占空间。预检应比较普通配置与候选配置的最大稳定并发，而不是只确认能启动。若低并发收益只在牺牲大量容量后出现，可以把功能放在低延迟服务等级，不对吞吐等级启用。

最终策略可能是按模型和负载动态选择：在低 QPS、长输出、已验证高接受领域启用更深草拟；中等负载降低深度；高负载切换轻量 N-gram 或关闭；结构化和特殊采样使用兼容配置。动态策略也要防振荡，使用平滑负载和最小保持时间。

## 定量推演：长请求公平性

设队列中有一个预计输出四千 Token 的推理任务和一百个预计输出四十 Token 的交互请求。严格先来先服务可能让一百个短请求等待长任务；严格最短任务优先又可能在短请求持续到达时让长任务永远不完成。调度目标需要同时保护交互 SLO 与长任务完成率。

一种方法是为服务等级分配份额，例如大部分 Decode 槽位服务交互队列，剩余保证长任务进展。长任务等待越久，有效权重逐步增加。份额不是固定真理，应通过工作负载回放测量短请求尾延迟、长请求完成时间、上下文驻留和总体 Goodput。

KV Cache 让长任务的等待也有成本。暂停但保留 KV 会占显存，逐出后恢复要重新 Prefill 或从外部存储取回。抢占策略应比较保留成本、重建成本和任务价值。对非常长的任务，可以使用独立池或可检查点执行，避免与严格交互池共享同一容量。

截止时间提供另一种信号。若长任务还有一小时截止，短交互两秒截止，调度可优先短请求；当长任务剩余裕量减少时提升优先级。预计服务时间存在误差，因此要留安全余量。错误估计不应导致永久饥饿。

取消必须迅速释放长任务资源。用户停止 Agent 或浏览器断开后，Gateway 把取消传到所有内部分支和引擎。若只关闭客户端连接，长任务仍占 GPU，公平策略观察到的负载会失真。取消传播时间应进入可靠性指标。

公平性不能只看总体。按租户、等级和长度桶计算等待、完成和拒绝。总体 P99 达标时，某小租户仍可能持续饥饿。平台应有最小份额和配额，并在过载时按公开策略拒绝，而不是隐式让弱势队列无限等待。

## 定量推演：缓存价值与负载惩罚

一个请求有八千输入 Token，副本甲可复用七千 Token，但预计排队一秒；副本乙无缓存，预计立即执行。若本机 Prefill 一千 Token 需要五十毫秒，八千 Token 需要六百毫秒，甲的预计路径约一秒加五十毫秒，乙约六百毫秒，选择乙更快。若甲排队只有一百毫秒，则缓存命中更优。

这个例子说明缓存得分应转换为节省时间，而不是直接用命中 Token 数。转换依赖模型、硬件、并发和 Prefix Cache 实现。可以从性能曲线估计未命中 Token 的 Prefill 时间，并根据当前批处理修正。路由器不需要完美预测，但必须使用同一量纲比较。

缓存状态也有置信度。索引事件五秒未更新，而副本 KV 使用很高，七千 Token 可能已经被逐出。路由器应降低这条缓存证据权重或请求更近状态。把过期状态当确定事实会增加误路由。状态新鲜度本身应进入指标。

热点前缀容易集中流量。可以给副本设置最大预计工作量，超过后即使有缓存也分流；也可以复制热门前缀到多个副本或主动预热。复制占用更多 KV，只有稳定热门前缀值得。策略应比较节省 Prefill 与增加 KV 占用。

会话路由还涉及连续性。把同一会话固定到副本能复用 KV，但副本失败或负载过高时需要迁移。会话标识不能成为无法逃离的硬绑定。可以使用软亲和，命中优先但允许在预计完成时间明显更好或健康变化时切换。

版本是缓存 Key 的硬边界。模型、Tokenizer、模板、Adapter 或 Rope 配置变化后，旧 KV 不可复用。路由和缓存索引必须携带完整兼容标识。若只用逻辑模型名，灰度期间可能发生错误命中，结果不可预测。

## 定量推演：模型多路复用的常驻决策

假设一个 GPU 可以常驻一个大模型，另有十个低频模型共享。模型加载需要四十秒，平均请求处理十秒。若某低频模型每小时只有一次请求，常驻会产生大量空闲；按需加载使用户等待很久。可通过热度预测、CPU 或磁盘缓存、Warm Pool 和服务等级组合。

常驻集合可以依据节省的期望加载等待减去占用 GPU 的机会成本。热门模型请求多、加载大，通常常驻；极冷模型按需；中间模型需要结合时间分布。平均每小时请求数不足以描述突发，若请求集中在固定时段，可以提前预热。

模型切换会导致抖动。多个冷模型交替请求，LRU 可能不断逐出又加载，吞吐和延迟都很差。可设置最小驻留时间、加载成本感知淘汰、每租户配额和独立冷模型池。淘汰策略应记录命中、加载、逐出和浪费时间。

Multi-LoRA 的加载更轻，但 Adapter 数量多时也会占 GPU 与 CPU 缓存。基础模型共享提高效率，Adapter Rank、目标层和并发活跃数影响 Kernel 与图捕获。不能把 Adapter 当成零成本标签。应测不同活跃 Adapter 数量和切换频率。

热更新 Adapter 要保证请求一致性。正在执行的请求应继续使用原版本，新请求切到新版本，或明确采用会话固定。原地覆盖若没有版本引用，Trace 无法说明输出来自哪组权重。控制面需要不可变 Adapter Revision 和原子别名切换。

常驻决策还受故障和发布影响。若只有一个副本缓存某模型，节点故障会触发长冷启动；为重要模型保留第二副本是可靠性成本。成本优化不能删除所有冗余，应把服务等级和恢复目标作为约束。

## 定量推演：冷启动容量到达

设当前两个副本每个在 SLO 内支持每秒两请求，流量从每秒三升到八。控制器检测和决策需要十秒，新副本启动九十秒，每个新副本同样提供每秒二请求。如果高峰只持续一分钟，事件驱动扩容几乎没有帮助；需要预热、Headroom 或拒绝策略。

若控制器每五秒根据当前缺口计算并忽略待启动副本，它可能连续创建大量副本。九十秒后这些副本一起就绪，高峰已过，产生空闲成本。正确状态包含正在创建的副本、预计完成时间和失败概率。每轮只补充尚未覆盖的未来缺口。

缩短启动可以逐段优化。镜像慢用节点预拉或小镜像；权重下载慢用缓存和分发；文件读取慢改并发与分片；GPU 拷贝慢用流式加载；图捕获和预热慢调整形状与分层就绪。只说“冷启动九十秒”无法选择方案。

Warm Pool 层次决定成本。保留空 GPU 节点只能省节点供给时间；保留权重磁盘缓存省下载；保留 CPU 内存副本省读取；休眠引擎省大部分初始化；GPU 权重服务最快但占昂贵显存。应计算峰值频率与节省违约成本，选择适当层次。

扩容期间要保护共享资源。限制并发下载，给生产请求网络和存储优先级，避免十个新副本拖慢现有服务。控制器观察加载带宽，必要时序列化或从已有工作器点对点分发。下载成功后做摘要校验，不能为了速度跳过一致性。

就绪必须经过真实请求。权重在 GPU 不代表 Tokenizer、模板、通信和流式都正确。最小 Canary 应在路由注册前完成。若预热较长，可以先标记基础就绪，再限制流量和形状，后台完成全部 Profile，但状态语义要明确。

## 定量推演：异构 Fleet 的成本效率

假设两类 GPU：甲小时成本较低但显存小，乙小时成本较高但容量和吞吐更大。若模型需要的权重与 KV 超过甲显存，甲不可行；若通过量化可行，还要检查质量和 Kernel。不能只用理论每秒浮点数除以价格。

对每个可行组合，应测 SLO 边界下的有效吞吐，再计算单位有效产出成本。乙虽然贵，若吞吐高很多且能容纳更大批量，单位成本可能更低；甲在低流量时空闲少，也可能更经济。流量形态决定最佳选择。

多 GPU 并行组把成本和故障放大。四张便宜 GPU 的总价可能接近一张大 GPU，但通信使吞吐不线性；任一节点故障影响整个组；放置更难。Profile 必须包含完整组和拓扑，不可用单卡结果推算。

异构路由可以把短交互送低延迟设备，批处理送高吞吐设备，长上下文送大显存设备。模型输出应保持兼容，版本和量化差异需要质量验证。路由器把请求特征与设备能力匹配，并在设备池过载时有回退。

容量采购要考虑可放置形状。增加十张分散的小 GPU 未必能支持需要八卡高速互联的新模型。Fleet 规划从未来模型与服务等级反推节点形状、网络和存储，而不是只采购总算力。

能源、散热和机房限制也会成为容量上限。本地成本模型可以加入功耗与利用率，云环境加入实例、存储和网络。课程不写死价格，但要求学习者显式填写假设并做敏感性分析。

## 定量推演：一次故障如何变成重试风暴

假设五个副本中一个失效，百分之二十容量消失。客户端超时一秒后最多重试两次，Gateway 也对五百错误重试一次，而工作器内部对依赖再重试。一个原始请求可能变成多次内部尝试。剩余副本负载上升、响应变慢，更多请求超时，重试率继续增加。

第一道防线是错误分类。明确不可重试的输入错误、配额、结构冲突；对暂时过载返回重试建议；对未知执行状态避免重复副作用。第二道是全链路重试预算，外层已经重试时内层减少。第三道是随机退避，避免同时重发。

路由器应快速摘除失败副本，不等待每个请求超时。健康状态使用租约和主动检查；网络分区时宁可暂时降低容量，也不要继续向不可达节点发送。摘除后控制面创建替代，但扩容时间内要负载削减。

已经接收的请求优先于新请求。过载保护可以拒绝低优先和预计无法按截止时间完成的请求，把资源留给接近完成的工作。让所有请求一起变慢看似公平，实际造成更多无效 GPU 工作。

观测需要显示原始请求与尝试次数。只统计工作器 QPS 会把重试误认为业务增长。Trace 中每次尝试是子 Span，携带重试原因和剩余预算；指标报告放大系数。放大系数上升是级联早期信号。

恢复后也要缓慢导流。替代副本刚启动没有缓存，大量流量瞬间进入可能再次过载。使用渐进权重、预热和健康观察。故障演练应验证整个过程，而不仅是副本最终重新出现。

## 定量推演：为什么平均单位成本会欺骗决策

设配置甲每小时成本十，产生一万输出 Token，其中九千满足 SLO；配置乙每小时成本十二，产生一万四千 Token，其中一万三千满足 SLO。按总 Token，甲每千 Token 成本一，乙约零点八六；按有效 Token，甲约一点一一，乙约零点九二，乙仍更好。

若乙额外产生大量低质量长输出，只有八千 Token 通过质量门禁，则有效成本变为一点五，结论反转。分母必须连接业务有效性。对 Agent 任务，更合适的分母可能是成功任务数，而不是 Token。

空闲与冗余成本也要解释。为了容灾保留一个备用副本会提高正常时单位成本，却减少故障损失。可以把预期失败成本加入分子，或把可靠性作为硬约束。不能用正常一小时跑分证明删除冗余更经济。

优化开发和运营成本难以精确量化，但不应忽略。复杂自定义 Drafter 若需要频繁训练、兼容和值班，而性能收益很小，长期未必值得。决策记录至少列出维护项和风险，并设复查时间。

共享成本分摊会影响租户行为。若所有租户均摊冷模型常驻成本，低频模型请求者没有优化动力；按模型池分摊更准确，但复杂。平台可以先用稳定规则，再通过敏感性分析观察决策是否受分摊方法显著影响。

成本优化要避免把支出转移到未计量层。减少 GPU 但增加大量 CPU 预处理、网络传输或对象存储请求，GPU 报表变好而总成本上升。完整分子和资源 Trace 能发现这种转移。

## 端到端推演：一次容量与路由联合变更

假设一个企业代码助手准备把主模型从旧修订版升级到新修订版，同时启用前缀缓存感知路由。平台团队希望降低首 Token 长尾和单位有效请求成本，但业务侧要求代码正确率不能下降，交互请求在工作时段的首 Token P99 仍需低于约定阈值，后台索引任务不得挤占交互容量。这个问题不能拆成“换模型”和“换路由”两个互不相关的开关，因为新模型的权重体积、KV 占用、平均输出长度和缓存复用特征都会改变容量边界。

第一步是冻结工作负载合同。团队从生产 Trace 中提取脱敏后的到达间隔、输入长度、最大输出长度、仓库身份、会话身份、缓存命中、取消时刻和优先级，形成多个可重放窗口。工作日午后窗口代表持续高负载，早晨窗口代表冷启动后快速爬升，发布日窗口包含大量相似代码上下文，夜间窗口则以低优先索引任务为主。若只使用均匀到达和固定长度合成请求，前缀路由的收益会被错误估计，突发排队和租户不均也无法出现。

第二步是建立容量基线。旧修订版在固定 GPU 池上完成预热，记录不同并发下的首 Token、逐 Token 间隔、完成延迟、Goodput、显存余量、KV 驱逐率和取消后浪费计算。实验不追求找一个最好看的单点，而是扫描从低载到过载的完整区间，确定服务等级开始失守、队列持续增长和有效吞吐下降的位置。稳定容量取失稳点之前留有安全余量的区间，不能把短时间峰值吞吐当作长期可承诺容量。

第三步是验证新模型本身。先关闭新的缓存路由，保持入口、批处理策略、请求集合和观测口径不变，只替换不可变模型制品。门禁依次检查权重摘要、分词器与模板、数值合法性、代码任务正确率、结构化工具参数、流式结束原因以及基准负载下的资源曲线。若输出更长导致完成延迟上升，即使首 Token 更快，也不能把结果简单标记为性能提升；必须把长度变化作为质量行为和容量输入同时解释。

第四步是用机制模拟检查路由策略。模拟器为每个副本维护缓存键、队列工作量、活动序列、模型修订和健康状态，路由分数同时考虑预计缓存节省、预计排队、数据亲和约束与副本过期惩罚。团队构造两个反例：一个热点仓库使单副本缓存命中很高却严重排队；一个大租户的长上下文挤压其他租户。若策略只最大化命中率，会在这两个场景下恶化 P99 和公平性。加入负载上限、候选打散和租户份额后，模拟才进入真实验证。

第五步是设计相互独立的灰度维度。新模型修订和新路由策略分别使用独立标识，四种组合都能被观测：旧模型加旧路由、旧模型加新路由、新模型加旧路由、新模型加新路由。这样出现回归时可以判断来源，回滚也不必同时撤销所有变化。若发布系统只提供一个总开关，至少应分成先模型、后路由的两个阶段，并在阶段间等待足够长的稳定窗口。

第六步是处理冷启动和缓存污染。新副本上线时没有前缀缓存，直接接收按缓存收益筛选后的热点流量可能形成瞬时高载。发布控制器先验证权重与就绪状态，再导入一小部分代表性请求完成引擎预热，随后按逐级权重接收真实流量。观测面分别标记冷副本、预热副本和稳态副本，避免把初始样本混入稳态结论。旧修订版在回滚窗口结束前保留最小暖容量，从而避免故障发生后重新加载权重。

第七步是把客户端行为纳入验收。代码助手在首 Token 超时后可能自动重试，用户也可能取消再发送。若服务端只按尝试计数，灰度池的请求量会被重试放大，表现得像路由失衡。入口为原始交互生成稳定身份，每次尝试记录父子关系、剩余截止时间与取消原因。路由器不会把已经接近截止时间的请求送入长队列，工作器在取消传播后尽快释放未完成序列，Goodput 只统计满足截止时间并通过质量门禁的最终交付。

第八步是验证多租户隔离。灰度开始时总指标可能正常，但一个大型仓库的高复用请求会占据热点副本，其他租户转入冷副本。团队分别查看租户级首 Token、拒绝率、排队工作量和缓存收益，并用加权公平指标观察份额偏离。路由收益不能以少数租户明显受损为代价。策略为每个租户设置软份额和突发额度，空闲时允许借用，压力出现时按照优先级回收，同时保留后台任务的可暂停能力。

第九步是演练故障而不是等待故障。团队在灰度池中依次模拟一个工作器失联、对象存储读取变慢、缓存目录损坏和控制器短暂不可用。工作器失联时，路由器应快速停止派发，但不能因为心跳瞬时抖动反复摘挂；存储变慢时，新副本启动受限，现有暖容量应得到保护；缓存损坏时，请求应回退到无缓存执行而非返回错误；控制器不可用时，数据面应在有限时间内继续使用最后已知配置。每个演练都记录检测、隔离、降级、恢复和重新导流的时间线。

第十步是定义停止条件。若代码正确率置信区间越过允许下界、交互请求 P99 连续多个窗口超限、重试放大系数异常、特定租户拒绝率激增、GPU 错误率上升或旧修订版暖容量不足，发布自动暂停。停止不等于立刻全量回滚：如果问题只来自路由策略，可恢复旧路由并保留新模型；如果模型输出行为异常，则把模型流量切回旧修订版。精确的变更身份让回滚范围与故障范围一致。

第十一步是核算有效成本。新模型可能提高单卡 Token 吞吐，缓存路由也可能减少重复 Prefill，但更大的权重要求更多常驻显存，热点打散会牺牲部分命中，保留暖回滚容量还会增加短期成本。成本报告包含 GPU、CPU、网络、存储、观测和冗余，分母采用按时完成且通过代码质量门禁的请求。团队同时报告稳态成本、发布期间成本和预期故障损失，不用一个混合平均值掩盖不同阶段。

第十二步是形成可复查结论。发布记录保存制品摘要、配置版本、流量窗口、实验代码版本、原始指标位置、统计摘要、失败演练、例外审批和回滚目标。最终结论不是“新方案快百分之多少”，而是说明在何种模型、负载、硬件和服务等级下，新模型与缓存路由组合能增加多少有效容量，代价是什么，哪些租户或请求形态不适用，以及模型、框架或流量变化到什么程度必须重新验证。

这个推演说明，生产优化的最小决策单元不是一个参数，而是一组可追溯假设和保护条件。任何局部收益都要经过工作负载代表性、正确性、排队稳定性、隔离、故障恢复和经济性六类证据。课程后续每个专题都会重复使用这套验收骨架，使新算法、新框架和新硬件能够放进同一决策语言中比较。

只有证据链完整，局部优化才具备进入持续生产运行的工程资格。

实践中还应为课程实验和生产变更保留可比较的最小证据集：同一份请求样本、同一套指标定义、可定位到提交与模型摘要的运行配置、完整的环境清单、原始结果以及解释结论。证据集不要求个人电脑复刻集群绝对性能，但必须让另一位工程师能够复现机制方向、判断运行状态并理解为何某些能力被标记为跳过。这样，从本地模拟到单卡执行，再到可选的多副本扩展，结论的适用边界始终清晰，课程中的数字也不会被误读成对任意硬件和任意流量都成立的承诺。

## 设计审查：十二个必须回答的问题

第一，优化对象是什么：单步 Kernel、引擎、单副本、路由池还是端到端任务。第二，用户承诺是什么：首 Token、连续流畅、截止时间、质量或成本。第三，工作负载怎样定义，是否保留长度、到达、缓存、模型和优先级分布。

第四，控制变量是什么，基线和候选是否除研究因素外一致。第五，指标口径是什么，分母是否只包含有效产出。第六，样本和统计是否足以支持结论，是否报告不确定性和长尾。

第七，机制模拟简化了什么，哪些结论必须由真实环境验证。第八，真实实验记录了哪些硬件、软件、模型和配置。第九，优化改变了哪些资源、状态和故障模式。

第十，发布门禁、Canary 和回滚是什么，怎样证明完整推理路径可用。第十一，观测能否从用户症状追到路由、工作器、模型修订和执行阶段。第十二，结论在何时失效，框架、模型、流量或硬件变化后怎样复查。

若十二个问题中有多个只能回答“默认”“大概”或“之后再看”，说明方案仍是实验想法，不是可发布工程。评审的价值不是阻止创新，而是把隐含假设变成可测条件，让失败更早、更便宜地出现。

## 学习方法：如何使用后续课程

每一课先找中心工程问题，不要从参数列表开始。读完知识串讲后，应能用自己的话定义实体、状态和资源；读完原理分析后，应能写出变量关系和适用边界；完成模拟后，应理解方向与反例；完成真实路径后，应知道本机证据覆盖到哪里。

遇到框架参数，先问它改变了哪个机制。例如一个路由开关可能改变候选集合和状态来源，一个显存比例改变 KV 容量，一个 Speculator 深度改变草拟和验证。理解机制后，参数名变化仍能迁移；只背命令会随版本失效。

每次实验保留原始配置和记录。不要只截一张图。用同一报告字段对齐基线和候选，先验证正确性与环境，再看性能。完成模拟和预检。

练习不只求最终数字。需要提交假设、计算、代码、运行状态、解释和限制。故意制造无效输入、过载、缓存失效或工作器故障，观察系统是否给出正确保护。只测试成功路径无法建立生产能力。

视觉图用于表达关系，不替代推理。流程图帮助看状态和因果，拓扑图帮助看组件与资源，手绘图帮助记住判断和反例。最终决策仍要回到正文定义、实验和证据。若图与正文冲突，以经过验证的课程清单和正文事实为准并修正图。

完成阶段项目时，把多课组件连接起来，重新检查接口、版本、身份、截止时间和观测传播。项目验收看可运行、可测量、可演示和可故障恢复，不是把多个脚本放在同一目录。综合能力来自跨层约束，而不是文件数量。

## 练习

### 练习一：重写一个模糊性能目标

把“让推理更快”改写成包含模型、负载、并发区间、服务等级、质量约束和成本边界的可验证目标。列出至少一个预期收益和两个可能副作用，并说明需要什么证据才能发布。

### 练习二：画出请求证据链

选择文本聊天、结构化输出、多模态或 Agentic 请求之一，用阶段列表描述从客户端到完成计量的路径。为每个阶段选择指标、日志、Trace 或事件中的一种主要证据，并说明为什么其他证据不足。

### 练习三：识别错误口径

给定“GPU 利用率提高到 98%，输出 Token 每秒提高 15%，所以成本下降 15%”这一结论，列出缺失条件。至少检查有效 Token、取消、质量、SLO、并发、输入输出分布、预热、客户端和成本分子。

### 练习四：制造过载

逐步提高模拟到达率，观察平均延迟、P99、最大队列和 Goodput 的变化。找出吞吐仍增长但 Goodput 开始下降的区间，并解释为什么这个区间不能作为稳定容量。

### 练习五：比较冷启动与稳态

在真实路径中分别保留首轮冷启动样本和预热后的稳态样本。拆分权重加载、引擎初始化、首请求与持续请求，说明不同业务应关注哪一种时间。

### 练习六：设计发布门禁

为一个新模型修订版设计从制品校验、加载、Canary、灰度到全量的门禁。每一步写出通过条件、失败动作和回滚目标。避免只使用进程存活作为就绪条件。

## 本课小结

\*小黑工程复盘：把本课机制、取舍与证据收束到同一张决策图。\*

生产级推理优化的对象是动态系统，不是孤立的单卡跑分。模型和引擎负责计算，工作器提供可路由容量，Gateway 和路由器管理请求入口与副本选择，控制器管理期望状态，证据面让每个结论可解释、可回放、可验收。

任何优化都必须放回工作负载、排队、缓存、版本、启动、故障和成本中分析。平均延迟、峰值吞吐和 GPU 利用率只是局部信号；Goodput、服务等级、有效成本和恢复能力更接近平台目标。机制模拟用于暴露因果和边界，真实实验用于测量实际实现成本，两类证据相互补充但不能混淆。

后续课程会沿着同一框架深入：先研究新一代生成加速怎样改变草拟与验证成本，再处理长思考、工具调用、结构化和多模态工作负载，然后进入跨副本路由、模型多路复用、权重与启动、GPU Fleet、可靠性和推理经济学。无论技术怎样变化，始终用明确边界、可计算模型和真实证据做决策。

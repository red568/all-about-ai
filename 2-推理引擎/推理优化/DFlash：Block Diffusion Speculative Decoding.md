## 课程定位

“并行块草拟如何消除草拟串行路径，又会引入哪些验证与显存约束？”贯穿本课。先把 Block Diffusion Drafter、非因果块内注意力及其状态边界讲清楚，再讨论计算、实现和上线证据。在 DFlash：Block Diffusion Speculative Decoding 中，算法选择只是决策的一部分；负载分布、模型修订、调度、显存、并发和服务等级都会改变结论。每项收益都需要对应可观察的事件与适用范围。

个人电脑即可完成本课的双路径验证：CPU 模拟负责检验 Block Diffusion Drafter 到非因果块内注意力的方向，CUDA 实验负责测量真实执行代价。模拟、实测和外部资料不会混用。围绕 Block Diffusion Drafter 得出的结果只对记录的模型、软件、设备和负载负责，同时给出失败原因与回滚入口。

## 学习目标

1. 准确解释 Block Diffusion Drafter、非因果块内注意力和 Target Hidden-State Conditioning 之间的状态与资源关系。
2. 使用“T\_block = T\_condition + S\*T\_denoise + T\_verify(B)；Yield = E\[accepted\]/T\_block”建立可计算的收益边界并解释全部变量。
3. 围绕块接受长度、去噪步延迟、候选并行度和短输出回退率设计可复现实验。
4. 识别去噪步过多重新形成长关键路径、块过大导致大面积拒绝浪费和条件特征传输成为瓶颈等典型失败模式。
5. 对“并行块草拟如何消除草拟串行路径，又会引入哪些验证与显存约束？”给出包含适用条件、证据、风险和回滚的工程答案。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：Diffusion 不需要替代 Target Model

很多学习者第一次听到 diffusion language model，会自然想到：

“是不是要把原来的 autoregressive LLM 整个换掉？”

DFlash 展示的是另一条工程路线：

```
高质量 Autoregressive Target Model
              +
轻量 Block-Diffusion Draft Model
```

Diffusion Drafter 不负责最终答案质量，它只需要：

1. 足够便宜；
2. 一次并行提出多个合理未来 token；
3. 让 Target Model 能接受足够长前缀。

最终正确性仍由 Target verification 决定。

### Block Draft 是怎样形成的

假设当前已经生成到位置 $t$ ，希望草拟 $K$ 个未来 token。

AR Drafter：

```
x1 = Draft(context)
x2 = Draft(context, x1)
x3 = Draft(context, x1, x2)
...
```

Block-Diffusion Drafter 可以把未来位置初始化成 mask：

```
context | [MASK] [MASK] [MASK] [MASK]
```

Drafter 同时看：

- Target Model 提供的上下文 hidden states；
- 这些未来 mask position；
- block 内允许的双向/非因果交互。

然后在一次轻量 forward 中产生每个位置的分布：

$$
q_\theta(x_{t+1:t+K}\mid H_{target},M_{1:K})
$$

这里最重要的不是“数学上像图像 diffusion 一样走很多步”，而是 \*\*block 内 token 可以并行预测\*\*。

### 为什么需要 Target Hidden-State Conditioning

如果只给一个很小的 Drafter 原始 token 上下文，它可能没有足够模型容量准确预测多个未来位置。

Target 已经为上下文计算了丰富表示：

$$
H_{target}=\{h_t^{(l_1)},h_t^{(l_2)},...\}
$$

把这些 feature 提供给 Drafter，相当于：

Target 先做一次“高质量理解”，Drafter 再利用这份理解快速猜未来 block。

这也是为什么 DFlash 不是一个完全独立的通用 diffusion LLM。

### 非因果 Draft Attention 的意义

AR 生成要求未来位置不能看未来位置，因为输出必须逐 token 保持因果性。

但 Draft Model 只是在\*\*提出候选\*\*，最终仍会被 AR Target 验证。

因此 Drafter 可以让多个未来 mask 位置之间相互通信：

```
Mask1 ←→ Mask2 ←→ Mask3 ←→ Mask4
   ↖        ↑        ↑        ↗
       Target Context Features
```

这允许所有 draft positions 在一个 forward 中共同形成候选。

### DFlash 的性能模型

AR Drafter：

$$
T_{draft}^{AR}(K)\approx Kt_d
$$

DFlash：

$$
T_{draft}^{DF}(K)\approx t_{block}(K)
$$

理想情况下 $t_{block}(K)$ 对 $K$ 的增长远慢于线性 rollout。

但最终：

$$
T_{eff}^{DF}=\frac{t_{block}(K)+T_V(K)+T_O}{E[A(K)]}
$$

因此 Block Size 同时影响：

- Drafter 计算；
- 后缀准确率；
- Target verify token 数；
- 被拒绝 token 数；
- verifier batch occupancy。

### 为什么 Block Size 不是越大越好

假设每个位置的 conditional survival 概率下降：

```
1: 0.95
2: 0.90
3: 0.82
4: 0.70
5: 0.55
6: 0.40
```

把 Block 从 4 增到 16，如果后面 12 个位置几乎不会通过，只会：

- 增加 Draft 输出；
- 增加 verify；
- 占用更多 GPU token budget；
- 让高并发吞吐变差。

因此后续 DDTree、CaDDTree、DSpark 都可以看成在继续解决：

“有了并行 Draft 以后，怎样更聪明地使用这些候选？”

### Anchor 与 Prefix Dependency

并行 Draft 最大困难是后缀缺少真实前缀条件。

可以把整个 Block 看成：

```
已验证 Prefix + Anchor / Target Feature + 多个并行位置
```

越远位置越依赖一个“可能不完全正确”的内部关系。因此训练重点之一是让 Drafter 学会：

- 充分使用 target context；
- 建模 block 内关联；
- 不让后缀 confidence 无控制衰减。

### DFlash 与 EAGLE-3 怎么选

不是“新的永远替代旧的”。

EAGLE-3：

- AR draft；
- 强 prefix dependency；
- draft cost 随 rollout depth 增长；
- 生态成熟度与 checkpoint 覆盖可能更广。

DFlash：

- block-parallel draft；
- Draft 延迟更低的潜力大；
- 对 block 后缀质量要求高；
- 与 block size / verifier capacity 强相关。

选择应回到：

$$
\text{Goodput / GPU-hour under SLO}
$$

### Target Hidden-State Conditioning

对 Target Hidden-State Conditioning 做边界检查，要覆盖输入、输出、状态归属和销毁时点。DFlash：Block Diffusion Speculative Decoding 的等待、计算及复制都能沿这些节点定位。Target Hidden-State Conditioning 传给并行去噪步的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

### 并行去噪步

在 DFlash：Block Diffusion Speculative Decoding 中，并行去噪步的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。并行去噪步连接块大小时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

### 失败模式 1：去噪步过多重新形成长关键路径

排查“去噪步过多重新形成长关键路径”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看 Block Diffusion Drafter 的时间线以及块接受长度、去噪步延迟。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

### 失败模式 2：块过大导致大面积拒绝浪费

诊断“块过大导致大面积拒绝浪费”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查非因果块内注意力，结合去噪步延迟与候选并行度定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“块过大导致大面积拒绝浪费”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认条件特征带宽没有转移到未计量层。

### 失败模式 3：条件特征传输成为瓶颈

出现“条件特征传输成为瓶颈”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿 Target Hidden-State Conditioning 的事件查看候选并行度和验证浪费率，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

### 失败模式 4：并行候选占用过多显存

针对“并行候选占用过多显存”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。并行去噪步的时间线配合验证浪费率、条件特征带宽可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

对“并行候选占用过多显存”先执行在线保护，再处理复发条件。面向并行候选占用过多显存的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查端到端速度的采集完整性。

### 失败模式 5：短输出无法摊销初始化

“短输出无法摊销初始化”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查块大小的阶段事件，并用条件特征带宽及显存增量缩小故障位置。客户端、服务端、计费数据均需完成对账。

```
"""Lesson 05 — block-shaped candidate verification sweep."""

from __future__ import annotations

import argparse
import itertools

from phase3lab.shared.cuda_ops import cuda_environment, load_causal_lm, memory_snapshot, timed_cuda
from phase3lab.shared.runner import LabSpec, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-05-block-draft",
    title="Block Draft：候选块宽度、深度与验证成本",
    goal="构造明确的候选块几何并测量 Target 批量验证，而不是把普通解码延迟改名为 Block Diffusion。",
    real_evidence=("candidate matrix", "width/depth sweep", "CUDA verifier timing"),
    required_inputs=("causal LM", "CUDA GPU"),
    outputs=("block geometry", "verification latency", "peak memory"),
    acceptance=("all candidates share the same prefix", "geometry varies", "each sweep point is measured"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--widths", default="2,4,8")
    parser.add_argument("--depths", default="2,4")
    parser.add_argument("--repeats", type=int, default=4)

def positive_list(raw: str, label: str) -> list[int]:
    values = [int(item) for item in raw.split(",") if item.strip()]
    if not values or any(value < 1 for value in values):
        raise ValueError(f"{label} values must be positive")
    return values

def candidate_grid(tokens: list[int], width: int, depth: int) -> list[list[int]]:
    if len(tokens) < width:
        raise ValueError("not enough root candidates")
    return [[tokens[(branch + position) % width] for position in range(depth)] for branch in range(width)]

def accepted_prefix(proposed: list[int], predicted: list[int]) -> int:
    count = 0
    for left, right in zip(proposed, predicted):
        if left != right:
            break
        count += 1
    return count

def fixture(args: argparse.Namespace) -> dict:
    widths = positive_list(args.widths, "width")
    depths = positive_list(args.depths, "depth")
    tokens = list(range(100, 100 + max(widths)))
    return {"sweep": [{"width": width, "depth": depth, "candidates": candidate_grid(tokens, width, depth)} for width, depth in itertools.product(widths, depths)]}

def real(args: argparse.Namespace) -> dict:
    torch, tokenizer, model, load = load_causal_lm(args.model)
    prefix = tokenizer(args.prompt, return_tensors="pt").input_ids.to("cuda")
    widths = positive_list(args.widths, "width")
    depths = positive_list(args.depths, "depth")
    with torch.inference_mode():
        root_logits = model(prefix, use_cache=False).logits[:, -1, :]
    roots = torch.topk(root_logits, k=max(widths), dim=-1).indices[0].tolist()
    records = []
    for width, depth in itertools.product(widths, depths):
        candidates = candidate_grid(roots, width, depth)
        candidate_tensor = torch.tensor(candidates, device="cuda")
        batch_prefix = prefix.repeat(width, 1)
        input_ids = torch.cat([batch_prefix, candidate_tensor], dim=1)
        torch.cuda.reset_peak_memory_stats()
        prediction_start = prefix.shape[1] - 1
        with torch.inference_mode():
            samples, logits = timed_cuda(torch, lambda: model(input_ids, use_cache=False).logits[:, prediction_start:prediction_start + depth, :], warmups=1, repeats=args.repeats)
        predicted = torch.argmax(logits, dim=-1).tolist()
        accepted = [accepted_prefix(branch, target_branch) for branch, target_branch in zip(candidates, predicted)]
        records.append({
            "width": width,
            "depth": depth,
            "candidate_tokens": candidates,
            "accepted_positions": accepted,
            "verification_latency": latency_summary(samples),
            "memory": memory_snapshot(torch),
        })
    return {"environment": cuda_environment(torch), "load_ms": load, "sweep": records}

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 课程定位

理解 P-EAGLE：并行 Drafter 与长上下文训练，需要先回答“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”。本课沿着概念边界、性能关系、实现证据和发布条件四条线展开，其中 P-EAGLE 并行 Drafter 与多深度 Token 预测头是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定多个深度预测头并行产生候选以移除串行草拟链是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径。CPU 机制模拟隔离 P-EAGLE 并行 Drafter 与多深度 Token 预测头的因果关系；真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，各深度准确率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 学习目标

1. 准确解释 P-EAGLE 并行 Drafter、多深度 Token 预测头和共享前缀表示之间的状态与资源关系。

4. 识别并行头输出高度相关、深位置准确率快速下降和共享层成为带宽瓶颈等典型失败模式。
5. 对“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”给出包含适用条件、证据、风险和回滚的工程答案。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：并行不等于没有条件

最朴素 parallel MTP：

```
当前 hidden ─→ head1 → t+1
           ├→ head2 → t+2
           ├→ head3 → t+3
           └→ head4 → t+4
```

问题是 $t+4$ 预测时不知道 $t+1,t+2,t+3$ 最终是什么。

而自回归 Drafter：

```
t+1 → 作为条件 → t+2 → 作为条件 → t+3
```

质量更稳定，但串行。

P-EAGLE 类方法真正要解决的不是“并行输出四个 Logits”这么简单，而是：

如何在并行计算时，给更深位置足够的条件信息，让它不要完全变成盲猜。

### 把 Draft Depth 看成多任务

设要预测未来 $K$ 个位置：

$$
q_k(x_{t+k}\mid h_t),\quad k=1,...,K
$$

最简单的多头训练：

$$
\mathcal L=\sum_{k=1}^{K}w_k\mathcal L_k
$$

其中深位置通常更难，可以使用不同权重 $w_k$ 。

但如果每个 $q_k$ 只看同一个 $h_t$ ，就缺少中间 token 条件。COD 类思想可以用前一个/前几个位置的\*\*分布信息\*\*而不是离散采样 token 作为条件，从而保留可并行训练/推理的空间。

抽象地写：

$$
q_k(x_{t+k}\mid h_t, q_1,...,q_{k-1})
$$

关键是这些条件可以以张量形式并行构造，而不要求真实走完 $k-1$ 次完整 autoregressive forward。

### Parallel Draft 的两个主要风险

### 5.1 Suffix Accuracy Decay

越靠后的位置条件越弱，准确率通常下降。

如果：

$$
p_k=P(\text{position }k\text{ accepted}\mid 1...k-1\text{ accepted})
$$

那么：

$$
P(A\ge k)=\prod_{i=1}^{k}p_i
$$

一个位置稍微下降，长前缀存活概率会快速下降。

### 5.2 Verification Waste

一次并行预测很便宜，容易诱惑我们把 $K$ 开得很大。

但 Target 仍需验证这些位置。假设 verifier cost：

$$
T_V(K)=a+bK+cK^2_{mask}
$$

即使 Draft cost 近似常数，过大的 $K$ 仍可能把浪费转移到 verifier。

### 并行 Drafter 的真正优势在哪里

AR Drafter：

$$
T_D^{AR}(K)\approx K\cdot t_d
$$

Parallel Drafter：

$$
T_D^{P}(K)\approx t_{base}+\Delta(K)
$$

如果 $\Delta(K)$ 增长较慢，就可以在相似 Draft latency 下提出更多候选。

但最终收益条件仍是：

$$
\frac{E[A_P]}{T_D^P+T_V^P}> \frac{E[A_{AR}]}{T_D^{AR}+T_V^{AR}}
$$

### 训练数据与域适配

parallel drafter 对 workload 分布非常敏感。

代码补全常有强局部结构；数学推理可能有固定模式；开放创作的不确定性更高。

因此 Speculator 训练数据应覆盖真实 serving workload，而不是只在通用语料上追求平均 token accuracy。

建议训练评测至少分：

- coding；
- math/reasoning；
- general chat；
- structured/template；
- bilingual/multilingual。

对每类分别报告 position-wise acceptance。

### 实验设计

本课实验不另建 Lab，复用 Lab02：

加入两个模型：

1. AR：Draft latency 随 $K$ 线性增加，但 $p_k$ 衰减慢；
2. Parallel：Draft latency 近似固定，但 $p_k$ 衰减更快。

扫描 $K=1..16$ ，比较：

- accepted length；
- effective token latency；
- verification waste；
- 最优 $K$ 。

学生最终应看到：

Parallel Drafter 的优势不是“永远更准”，而是用低 Draft latency 换取更多候选空间，再由质量决定能留下多少。

### 生产系统还要考虑动态 Depth

固定 $K$ 是最容易实现的，但不同请求的可预测性不同。

更合理的系统会根据：

- 前几个位置 confidence；
- 最近 acceptance 历史；
- request domain；
- verifier 当前负载；
- SLO；

动态选择 draft depth。

这正是后续 DSpark 和第 09 课动态 Speculator Policy 的接口。

### P-EAGLE 并行 Drafter

对 P-EAGLE 并行 Drafter 做边界检查，要覆盖输入、输出、状态归属和销毁时点。P-EAGLE：并行 Drafter 与长上下文训练的等待、计算及复制都能沿这些节点定位。P-EAGLE 并行 Drafter 传给多深度 Token 预测头的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

P-EAGLE 并行 Drafter 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。共享表示降低重复计算但会耦合不同深度任务通常只先改变其中几项，其他资源随后可能进入关键路径。P-EAGLE 并行 Drafter 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，P-EAGLE 并行 Drafter 对系统的贡献也会变化。设计深度损失权重应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 P-EAGLE 并行 Drafter 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。长上下文训练样本不足会触发停止与回退，系统恢复到已有证据支持的配置。

P-EAGLE 并行 Drafter 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。接受长度必须附带口径。缺少这些信息时，关于“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”的判断无法在上线后复核。

### 多深度 Token 预测头

在 P-EAGLE：并行 Drafter 与长上下文训练中，多深度 Token 预测头的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。多深度 Token 预测头连接共享前缀表示时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量多深度 Token 预测头时分别记录算力、显存、带宽、CPU 开销与同步。发生“越深位置依赖更长未知前缀而预测难度上升”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐多深度 Token 预测头的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估多深度 Token 预测头需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。采样或剪枝并行候选至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

多深度 Token 预测头进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。并行草拟减少延迟却增加显存峰值一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察多深度 Token 预测头需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。显存峰值同时注明单位、窗口和分母。这些字段使“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”可以在发布后按原条件回放。

### 共享前缀表示

解释共享前缀表示时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。P-EAGLE：并行 Drafter 与长上下文训练的请求可能在这些交界处增加等待、计算或复制。与位置条件与深度条件交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕共享前缀表示建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。长上下文改变特征分布与 KV 访问成本会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

按负载调整 Depth 是否合适，取决于共享前缀表示所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

共享前缀表示带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现静态 Depth 在负载变化时失效时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

共享前缀表示的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。长上下文退化没有单位、统计窗口和分母时不参与决策。完整记录用于复查“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”在具体负载下是否成立。

### 位置条件与深度条件

位置条件与深度条件在 P-EAGLE：并行 Drafter 与长上下文训练中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与并行草拟延迟之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

预测头相关性过高会降低候选多样性对位置条件与深度条件的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认位置条件与深度条件的变化来自哪里，本课对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

位置条件与深度条件的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证决定是否为长上下文单独训练时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖位置条件与深度条件影响到的 Token、采样、结构、结束状态与错误。若检测到并行头输出高度相关，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为位置条件与深度条件建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。净 Goodput 的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“并行多 Token 草拟如何降低串行草拟延迟并保持可扩展训练？”。

## 工程决策与取舍

### 决策 1：确定并行头数量

决定“确定并行头数量”是否上线时，服务承诺是评审起点，各深度准确率、并行草拟延迟、接受长度构成结果证据。还需解释 P-EAGLE 并行 Drafter 怎样变化、“多个深度预测头并行产生候选以移除串行草拟链”在哪些负载下有效，以及遇到并行头输出高度相关时如何停止。

“确定并行头数量”比较基线、候选和回退三种配置。基线沿用已验证路径，候选只改变“确定并行头数量”研究因素，回退无需重新下载大制品即可恢复服务。三组使用相同请求集合与随机种子，并按负载区间、请求形态分组。决策记录包含“确定并行头数量”的选择理由、被拒方案、结论到期条件和净 Goodput 对应的维护成本。

### 决策 2：选择共享层与独立层

评审“选择共享层与独立层”时，先写明要改善的用户承诺，以及对应的候选多样性、验证节点数和显存峰值。候选需说明多深度 Token 预测头的资源变化、“共享表示降低重复计算但会耦合不同深度任务”的适用条件及深位置准确率快速下降触发的停止动作。只在极端样本成立的收益应限定启用范围。

实验为“选择共享层与独立层”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“选择共享层与独立层”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及净 Goodput 的改善是否覆盖新增运维成本。

### 决策 3：设计深度损失权重

“设计深度损失权重”进入方案评审前，要绑定具体服务承诺和并行草拟延迟、接受长度、长上下文退化。资源侧检查共享前缀表示，机制侧限定“越深位置依赖更长未知前缀而预测难度上升”，故障侧为共享层成为带宽瓶颈准备停止动作。测试样本不代表业务时，结论只覆盖该样本。

验证“设计深度损失权重”需要三条可复现路径：已确认的基线、只改“设计深度损失权重”因素的候选、无需重新取大制品的回退。三者共享请求和随机种子，数据按负载区间与请求形态统计。最终文档保存“设计深度损失权重”的取舍理由、有效期和净 Goodput 相对维护成本的变化。

### 决策 4：采样或剪枝并行候选

采样或剪枝并行候选解决哪项用户问题，需要由验证节点数、显存峰值和净 Goodput 共同证明。评审材料同时记录位置条件与深度条件资源账、“长上下文改变特征分布与 KV 访问成本”生效条件和长上下文训练样本不足的门禁。启用范围与实际证据范围保持一致。

围绕“采样或剪枝并行候选”运行基线、候选与回退。候选只引入“采样或剪枝并行候选”研究变量，回退保持已验证制品可立即恢复；每组使用同一请求集合和随机种子。报告分开呈现“采样或剪枝并行候选”在不同负载及请求形态下的结果，并记录拒绝项、复查触发器和净 Goodput 是否足以支付维护开销。

### 决策 5：按负载调整 Depth

决定“按负载调整 Depth”是否上线时，服务承诺是评审起点，接受长度、长上下文退化、各深度准确率构成结果证据。还需解释并行草拟延迟怎样变化、“预测头相关性过高会降低候选多样性”在哪些负载下有效，以及遇到并行草拟减少延迟却增加显存峰值时如何停止。

“按负载调整 Depth”比较基线、候选和回退三种配置。基线沿用已验证路径，候选只改变“按负载调整 Depth”研究因素，回退无需重新下载大制品即可恢复服务。三组使用相同请求集合与随机种子，并按负载区间、请求形态分组。决策记录包含“按负载调整 Depth”的选择理由、被拒方案、结论到期条件和净 Goodput 对应的维护成本。

### 决策 6：决定是否为长上下文单独训练

评审“决定是否为长上下文单独训练”时，先写明要改善的用户承诺，以及对应的显存峰值、净 Goodput 和候选多样性。候选需说明长上下文训练的资源变化、“在线负载决定并行草拟节省是否能覆盖验证成本”的适用条件及静态 Depth 在负载变化时失效触发的停止动作。只在极端样本成立的收益应限定启用范围。

实验为“决定是否为长上下文单独训练”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“决定是否为长上下文单独训练”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及净 Goodput 的改善是否覆盖新增运维成本。

## 失败模式与故障诊断

### 失败模式 1：并行头输出高度相关

“并行头输出高度相关”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查 P-EAGLE 并行 Drafter 的阶段事件，并用各深度准确率及候选多样性缩小故障位置。客户端、服务端、计费数据均需完成对账。

“并行头输出高度相关”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验验证节点数。

### 失败模式 2：深位置准确率快速下降

记录到“深位置准确率快速下降”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿多深度 Token 预测头回放事件，再比较候选多样性与并行草拟延迟。若完成数存在账差，先修复计量链。

对“深位置准确率快速下降”先执行在线保护，再处理复发条件。面向深位置准确率快速下降的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查接受长度的采集完整性。

### 失败模式 3：共享层成为带宽瓶颈

排查“共享层成为带宽瓶颈”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看共享前缀表示的时间线以及并行草拟延迟、验证节点数。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

修复“共享层成为带宽瓶颈”分为影响控制和复验。针对共享层成为带宽瓶颈可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对显存峰值没有被隐藏。

### 失败模式 4：长上下文训练样本不足

诊断“长上下文训练样本不足”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查位置条件与深度条件，结合验证节点数与接受长度定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“长上下文训练样本不足”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认长上下文退化没有转移到未计量层。

### 失败模式 5：并行草拟减少延迟却增加显存峰值

出现“并行草拟减少延迟却增加显存峰值”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿并行草拟延迟的事件查看接受长度和显存峰值，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

“并行草拟减少延迟却增加显存峰值”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验净 Goodput。

### 失败模式 6：静态 Depth 在负载变化时失效

针对“静态 Depth 在负载变化时失效”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。长上下文训练的时间线配合显存峰值、长上下文退化可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

对“静态 Depth 在负载变化时失效”先执行在线保护，再处理复发条件。面向静态 Depth 在负载变化时失效的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查各深度准确率的采集完整性。

```
"""Lesson 03 — batch verification for parallel draft branches."""

from __future__ import annotations

import argparse

from phase3lab.shared.cuda_ops import cuda_environment, load_causal_lm, timed_cuda
from phase3lab.shared.runner import LabSpec, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-03-parallel-drafter",
    title="P-EAGLE：并行候选分支与 Target 批量验证",
    goal="从同一前缀构造多个候选分支，核对串行与批量 Target 得分并测量验证成本。",
    real_evidence=("candidate token IDs", "serial/batched logits", "verification timing"),
    required_inputs=("causal LM", "CUDA GPU"),
    outputs=("branch trace", "numerical agreement", "latency comparison"),
    acceptance=("more than one branch", "same candidate set", "batched and serial scores agree"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--branches", type=int, default=4)
    parser.add_argument("--repeats", type=int, default=5)

def branch_plan(top_ids: list[int], branches: int) -> list[dict]:
    if branches < 2:
        raise ValueError("--branches must be at least 2")
    if len(top_ids) < branches:
        raise ValueError("candidate list is smaller than branch count")
    return [{"branch": index, "token_id": token} for index, token in enumerate(top_ids[:branches])]

def fixture(args: argparse.Namespace) -> dict:
    branches = branch_plan([91, 17, 44, 8, 32, 5], args.branches)
    return {"branches": branches, "serial_calls": len(branches), "batched_calls": 1, "candidate_identity_preserved": True}

def real(args: argparse.Namespace) -> dict:
    torch, tokenizer, model, load = load_causal_lm(args.model)
    encoded = tokenizer(args.prompt, return_tensors="pt").input_ids.to("cuda")
    with torch.inference_mode():
        root_logits = model(encoded, use_cache=False).logits[:, -1, :]
        k = min(args.branches, root_logits.shape[-1])
        top_ids = torch.topk(root_logits, k=k, dim=-1).indices[0].tolist()
        plan = branch_plan(top_ids, k)
        branch_tokens = torch.tensor([[item["token_id"]] for item in plan], device="cuda")
        repeated = encoded.repeat(k, 1)
        batched_input = torch.cat([repeated, branch_tokens], dim=1)

        def batched_forward():
            return model(batched_input, use_cache=False).logits[:, -1, :]

        def serial_forward():
            return torch.cat([model(batched_input[index:index + 1], use_cache=False).logits[:, -1, :] for index in range(k)], dim=0)

        batch_samples, batch_scores = timed_cuda(torch, batched_forward, warmups=1, repeats=args.repeats)
        serial_samples, serial_scores = timed_cuda(torch, serial_forward, warmups=1, repeats=args.repeats)
    max_difference = float((batch_scores.float() - serial_scores.float()).abs().max().item())
    tolerance = 0.05 if batch_scores.dtype in (torch.float16, torch.bfloat16) else 1e-4
    if max_difference > tolerance:
        raise RuntimeError(f"serial/batched verification mismatch: {max_difference}")
    for index, item in enumerate(plan):
        item["target_next_token"] = int(torch.argmax(batch_scores[index]).item())
    return {
        "environment": cuda_environment(torch),
        "load_ms": load,
        "branches": plan,
        "batched_latency": latency_summary(batch_samples),
        "serial_latency": latency_summary(serial_samples),
        "max_logit_difference": max_difference,
        "tolerance": tolerance,
        "measurement_note": "candidate branches come from Target top-k; a trained parallel Drafter can be substituted without changing the verifier contract",
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

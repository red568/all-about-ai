**导航**

本课系统理解数据、张量、流水线与专家并行，学会为不同模型规模选择合适的分布式训练方案。

## 课程定位

单卡训练像一个人完成整套装修：设计、搬料、施工、验收都在同一处。模型继续变大后，问题不再只是“多买几张 GPU”，而是怎样分工：数据怎样分、参数怎样分、层怎样分、长序列怎样分、MoE 专家怎样分，以及这些分工产生的数据交换是否值得。

本课建立大模型分布式训练的全景图。目标不是背诵 DP、TP、PP 等缩写，而是拿到模型规模、序列长度、GPU 数量和互联拓扑后，能够先判断“放不下、算不完、还是传不动”，再选择最少且最合适的并行维度。第 16～18 课会分别深入 NCCL、通信优化和 FSDP；本课先把它们放回同一个系统模型中。

## 学习目标

- 解释 rank、world size、process group、local rank 和 DeviceMesh 的关系；

- 理解消费级双卡 PCIe 实验能验证什么，以及不能代表什么。

## 核心直觉：先分清是哪一种“不够”

大模型分布式训练通常在解决四类问题：

1. \*\*容量不够\*\*：参数、梯度、优化器状态和激活无法同时放进一张卡。
2. \*\*计算不够\*\*：模型能放下，但一次训练要几个月，需要更多计算设备缩短时间。
1. \*\*通信太多\*\*：设备增加后，等待 All-Reduce、All-Gather、Reduce-Scatter、All-to-All 或点对点传输的时间超过新增算力带来的收益。
2. \*\*系统不稳\*\*：节点、网络、数据读取或检查点任何一层的长尾都会拖慢整个同步训练作业。

不同并行策略切的是不同维度：

| 策略 | 主要切分对象 | 首要收益 | 主要代价 |
| --- | --- | --- | --- |
| DP / DDP | Batch 样本 | 提高吞吐 | 梯度同步 |
| ZeRO / FSDP | 模型状态 | 降低单卡状态显存 | 参数/梯度通信 |
| TP | 层内矩阵 | 单层也能跨卡 | 高频层内 Collective |
| PP | 网络深度 | 分摊层和参数 | 流水线气泡与激活传输 |
| SP | 部分序列维激活 | 配合 TP 降低激活冗余 | 额外切分/聚合 |
| CP | 完整上下文序列 | 支持超长序列 | Attention 通信与负载均衡 |
| EP | MoE 专家 | 分摊专家参数和计算 | Token All-to-All 与负载不均 |

最重要的工程原则是：\*\*能用较简单的策略达到目标，就不要过早叠加更多并行维度。\*\* 每增加一个维度，都会增加通信组、配置约束、检查点格式和故障排查复杂度。

## 分布式训练的坐标系

### Rank、World Size 与 Local Rank

- `world_size` ：参与默认进程组的总进程数；常见配置是一块 GPU 对应一个进程。
- `rank` ：进程在全局进程组中的唯一编号，范围为 `0 ... world_size-1` 。
- `local_rank` ：进程在当前节点内的编号，常用于绑定本机 GPU。
- `process_group` ：执行一组 Collective 的进程集合。DP、TP、PP、CP、EP 往往各有自己的组。

两台机器、每台 8 张 GPU 时，通常 `world_size=16` 。节点 1 的第 3 个本地进程可能是 `local_rank=3, rank=11` 。它不一定同时属于同样大小的 DP、TP 和 PP 组。

`torchrun` 负责启动进程并提供环境变量；它不替你决定模型怎样切分。DDP 负责梯度同步，也不会自动把输入 Batch 切开，因此真实训练仍应使用 `DistributedSampler` 或等价的数据分片方案。

### DeviceMesh：把一维 Rank 重新排成多维网格

假设 16 张 GPU 采用 `TP=4, PP=2, DP=2` ，可把 rank 看成一个三维坐标：

```
world_size = DP × PP × TP = 2 × 2 × 4 = 16

(dp=0, pp=0, tp=0..3)  第一组层内并行
(dp=0, pp=1, tp=0..3)  第二个流水线阶段
(dp=1, pp=0, tp=0..3)  另一份数据副本
(dp=1, pp=1, tp=0..3)
```

实际框架可能采用不同的维度顺序和 rank 映射，不能根据乘积猜通信组；必须读取框架配置或打印 group 成员。

## 七种并行策略

### 1\. 数据并行：模型复制，数据分开

DDP 在每个数据并行 rank 上保存一份完整模型，各 rank 读取不同样本，反向传播时聚合梯度。同步完成后，每份模型继续保持一致。

全局 Batch 为：

$$
B_{global}=B_{micro}\times N_{acc}\times D
$$

其中 `B_micro` 是每个数据并行 rank 每个微步的 Batch， `N_acc` 是梯度累积步数， `D` 是\*\*数据并行度\*\*。混合并行时不能把总 GPU 数直接当作 `D` 。

DDP 的优点是实现简单、计算量均匀、吞吐扩展直观；缺点是每张卡都保存完整模型状态，且每一步都要同步梯度。

### 2\. ZeRO / FSDP：让模型状态也分片

经典混合精度 Adam 训练常按每个参数约 16 Bytes 估算模型状态：

- FP16/BF16 参数：2 Bytes；
- 梯度：2 Bytes；
- FP32 主参数：4 Bytes；
- Adam 一阶、二阶矩：8 Bytes。

设某个 TP×PP 分区内仍有 $P_{local}$ 个参数，数据并行度为 D，忽略 padding、临时缓冲、碎片和激活后，可做粗略估算：

$$
M_{DDP}\approx 16P_{local}
$$

$$
M_{ZeRO1}\approx 4P_{local}+\frac{12P_{local}}{D}
$$

$$
M_{ZeRO2}\approx 2P_{local}+\frac{14P_{local}}{D}
$$

$$
M_{ZeRO3}\approx \frac{16P_{local}}{D}
$$

直觉上，ZeRO-1 分片优化器状态，ZeRO-2 再分片梯度，ZeRO-3 再分片参数。越彻底的分片越省静态模型状态，但前向和反向需要更频繁地聚合/散布参数与梯度。本公式只是容量规划的起点，不是显存承诺；激活、通信 Bucket、CUDA Context、Allocator 碎片和 Kernel Workspace 仍需实测。

### 3\. 张量并行：一层矩阵也由多张卡共同计算

Transformer 的线性层可按列或按行切分。以 $Y=XW$ 为例：

- 列并行切 `W` 的输出列，每个 rank 计算一部分输出；
- 行并行切 `W` 的输入行，各 rank 得到部分和，再做归约。

TP 能解决“单层都放不下”的问题，但通常每层都产生 Collective，通信频率高。工程上常把 TP 组放在 NVLink/NVSwitch 等最快的互联域内。两张 RTX 3080 只能通过 PCIe 通信时，仍可验证正确性和观察通信，但其 TP 扩展性不能代表 A100/H100/B200 的高速互联系统。

### 4\. 流水线并行：按网络深度切成阶段

PP 把连续层放到不同设备：阶段 0 输出激活给阶段 1，反向时再反向传递梯度。为避免只有一个阶段工作，Batch 被拆成多个微批次，采用 GPipe、1F1B 或交错式调度。

对于最简单、阶段计算时间相等的 GPipe 模型，设阶段数为 p、微批次数为 m，只看填充和排空时的气泡比例：

$$
Bubble\approx\frac{p-1}{m+p-1}
$$

增加 `m` 可降低气泡，但会影响激活显存、调度开销和有效 Batch。阶段间层数相同也不保证计算相同：Attention、MoE、Embedding、输出头和重计算都可能造成 stage imbalance。

### 5\. 序列并行：减少 TP 区域里的激活冗余

Sequence Parallel 通常与 TP 配合，将 LayerNorm、Dropout 等原本在 TP rank 间重复保存/计算的激活沿序列维切分。它不是“任意长序列并行”的统称，也不是 Context Parallel 的旧名字。

### 6\. 上下文并行：把完整长上下文跨卡分担

Context Parallel 把输入序列沿 token 维分到多个 rank，并在 Attention 中交换必要的 Key/Value 或中间结果，以分摊长上下文激活和计算。它解决的是完整序列长度过大，通信模式和 SP 不同。可变长度样本还会引入负载不均，需要位置、mask、数据打包和通信调度共同配合。

### 7\. 专家并行：把 MoE 专家放到不同 Rank

EP 把专家参数和专家计算分布到多张 GPU。Router 选择专家后，token 通过 All-to-All 发往专家所在 rank，计算完成再返回。EP 的首要风险不是“专家数量不够”，而是路由不均：最忙 rank 决定同步步骤的尾延迟。

MoE 的并行组关系依赖框架实现，不能总写成 `world=DP×TP×PP×CP×EP` 。一些实现中 EP 与数据并行维度发生折叠或重新分组。配置前应让框架打印每个 process group，并验证每个 rank 的成员资格。

## 混合并行：从可行解走向高效解

### 一个稳健的选型顺序

1. 先测单卡容量和单步时间；能放下时先用 DDP。
2. 模型状态 OOM，优先尝试激活重计算、混合精度和 FSDP/ZeRO。
1. 单层或单个矩阵无法落在一张卡上，再引入 TP。
2. 层数很多、需要跨节点分摊深度时，引入 PP。
1. 超长上下文使激活或 Attention 计算成为瓶颈时，引入 CP/SP。
2. 模型是 MoE 且专家无法放下或需要扩大专家吞吐时，引入 EP。
1. 最后依据拓扑重排 rank，并调通信重叠、Bucket 和微批次数。

| 观察到的问题 | 首选方向 | 先验证什么 |
| --- | --- | --- |
| 完整模型能放下但训练太慢 | DDP | 弱扩展、数据管线、All-Reduce |
| 参数/梯度/优化器状态 OOM | ZeRO/FSDP | 模型状态与峰值激活占比 |
| 单层矩阵无法放下 | TP | 层内通信是否有高速互联 |
| 模型深度大、跨节点较多 | PP | stage balance 与气泡 |
| 长序列激活 OOM | CP/SP/重计算 | Attention 与激活内存 |
| MoE 专家参数或计算过大 | EP | token 分布与 All-to-All |

### 拓扑感知

通信频率越高，越应靠近最快互联：

- TP 通常每层通信，应优先放在单机 NVLink/NVSwitch 域；
- EP 的 token dispatch 对 All-to-All 敏感，应关注双向带宽和拥塞；
- PP 主要在相邻阶段间传激活，适合做清晰的链路映射；
- DP 梯度同步数据量大，但可 Bucket 化并与反向计算重叠，常跨越更大范围；
- 最优映射不是固定口诀，仍要以实际模型、拓扑和 Profiler 结果为准。

## 关键性能模型

### 环形 All-Reduce 通信量

对于 D 个数据并行 rank、大小为 G Bytes 的梯度，理想环形 All-Reduce 每个 rank 的收发总量约为：

$$
V_{ring}\approx 2\frac{D-1}{D}G
$$

简化通信时间模型为：

$$
T_{comm}\approx n_{step}\alpha+\frac{V}{B_{effective}}
$$

其中 $\alpha$ 是每个通信步骤的启动延迟，B\\\_{effective} 是包含协议、拓扑和争用后的有效带宽。小 Bucket 更容易提前启动并重叠，但消息过碎会放大延迟；大 Bucket 带宽利用好，却可能等到反向末尾才开始。

### 通信重叠不是简单相加

没有重叠时：

$$
T_{step}\approx T_{compute}+T_{comm}+T_{input}
$$

理想重叠时，关键区间更接近：

$$
T_{step}\approx \max(T_{compute},T_{comm})+T_{unhidden}+T_{input,critical}
$$

所谓“通信被隐藏”并非通信消失，而是通信与计算占用不同资源并发执行。若 GPU Kernel、DMA、PCIe、NVLink 或网络共享瓶颈，二者也可能互相拖慢。

### 扩展效率

$$
E_N=\frac{Throughput_N}{N\times Throughput_1}
$$

- \*\*强扩展\*\*：总问题规模不变，增加设备；每卡工作变小，通信占比往往升高。
- \*\*弱扩展\*\*：每卡问题规模不变，总问题规模随设备增加；更容易得到较好效率，但全局 Batch 改变了优化语义。

因此，“两卡比一块卡快 1.8 倍”必须同时说明是强扩展还是弱扩展、全局 Batch 是否相同、精度和数据是否一致。

## 瓶颈分析方法

### 第一步：先问容量还是速度

记录至少四类显存：参数/梯度/优化器状态、保存用于反向的激活、通信与临时 Workspace、Allocator reserved/fragmentation。只看 `nvidia-smi` 无法区分它们。

### 第二步：分解 Step 时间

将端到端 Step 分解为：

```
Data wait → H2D → Forward → Backward compute
          → Gradient communication → Optimizer → Checkpoint/logging
```

观察每个 rank 的时间，而不是只看 rank 0。同步训练的步耗时由最慢 rank 决定。

### 第三步：检查通信是否在关键路径

- DDP Bucket 是否在反向过程中逐步启动？
- Collective 前是否出现长时间空白或 CPU Launch Gap？
- 某个 rank 是否因为数据、频率、温度或 MoE 路由更慢？
- 通信是否落在预期网卡、PCIe Root Complex、NVLink 或 InfiniBand 上？
- 梯度累积时，非最后微步是否用了 `no_sync()` ，避免每个微步都 All-Reduce？

### 第四步：区分算法瓶颈和拓扑瓶颈

同一份代码在两张 PCIe 消费卡上扩展差，并不能证明 DDP 算法无效；也不能用单机 NVLink 结果外推跨机网络。需要同时保存 GPU 型号、互联拓扑、NCCL 日志、消息大小和软件版本。

### Level 0：纯 Python 并行方案规划器

保存为 `parallelism_planner.py` ：

```
#!/usr/bin/env python3
import argparse
import json

GIB = 1024 ** 3

def model_state_bytes(params, dp, zero_stage):
    # 经典混合精度 Adam 粗略模型：参数2B、梯度2B、主参数4B、动量8B。
    if zero_stage == 0:
        return 16 * params
    if zero_stage == 1:
        return 4 * params + 12 * params / dp
    if zero_stage == 2:
        return 2 * params + 14 * params / dp
    if zero_stage == 3:
        return 16 * params / dp
    raise ValueError("zero_stage 必须为 0、1、2 或 3")

def main():
    p = argparse.ArgumentParser(description="分布式训练并行度与静态显存规划器")
    p.add_argument("--params-b", type=float, default=7.0)
    p.add_argument("--world-size", type=int, default=8)
    p.add_argument("--tp", type=int, default=1)
    p.add_argument("--pp", type=int, default=1)
    p.add_argument("--micro-batch", type=int, default=1)
    p.add_argument("--grad-accum", type=int, default=8)
    p.add_argument("--pipeline-microbatches", type=int, default=None)
    p.add_argument("--zero-stage", type=int, default=0)
    p.add_argument("--sequence-length", type=int, default=4096)
    p.add_argument("--hidden-size", type=int, default=4096)
    p.add_argument("--layers", type=int, default=32)
    args = p.parse_args()

    if min(args.world_size, args.tp, args.pp, args.micro_batch,
           args.grad_accum, args.sequence_length, args.hidden_size,
           args.layers) <= 0:
        raise ValueError("并行度、Batch 和模型形状必须为正数")
    model_parallel = args.tp * args.pp
    if args.world_size % model_parallel != 0:
        raise ValueError("world_size 必须能被 tp × pp 整除")

    dp = args.world_size // model_parallel
    total_params = args.params_b * 1e9
    local_partition_params = total_params / model_parallel
    global_batch = args.micro_batch * args.grad_accum * dp
    state_bytes = model_state_bytes(
        local_partition_params, dp, args.zero_stage
    )

    m = args.pipeline_microbatches or args.grad_accum
    bubble = 0.0 if args.pp == 1 else (args.pp - 1) / (m + args.pp - 1)

    # 仅用于比较形状规模，不等同于真实激活显存。
    activation_elements_proxy = (
        args.micro_batch * args.sequence_length * args.hidden_size
        * (args.layers / args.pp)
    )

    # 仅是普通 DDP 梯度环形 All-Reduce 的粗略通信量。
    grad_bytes = 2 * local_partition_params
    ddp_ring_bytes = 0.0 if dp == 1 else 2 * (dp - 1) / dp * grad_bytes

    result = {
        "degrees": {"world": args.world_size, "dp": dp,
                    "tp": args.tp, "pp": args.pp},
        "global_batch": global_batch,
        "local_partition_params_b": local_partition_params / 1e9,
        "zero_stage": args.zero_stage,
        "approx_model_state_gib_per_rank": state_bytes / GIB,
        "simple_pipeline_bubble_fraction": bubble,
        "activation_elements_proxy": activation_elements_proxy,
        "ddp_ring_gradient_traffic_gib_per_rank": ddp_ring_bytes / GIB,
        "warnings": [
            "显存估算不含激活、通信缓冲、临时Workspace和碎片",
            "activation_elements_proxy不是激活显存公式",
            "ZeRO/FSDP的真实通信模式不能用普通DDP流量替代",
        ],
    }
    print(json.dumps(result, ensure_ascii=False, indent=2))

if __name__ == "__main__":
    main()
```

运行：

```
python parallelism_planner.py \
  --params-b 7 --world-size 8 --tp 2 --pp 2 \
  --micro-batch 2 --grad-accum 8 --zero-stage 2 \
  --sequence-length 4096 --hidden-size 4096 --layers 32
```

预期现象：

- `DP=2, TP=2, PP=2` ，乘积等于 8；
- 全局 Batch 为 `2×8×2=32` ，不是 `2×8×8=128` ；
- 7B 参数先被 TP×PP 分为每个 rank 约 1.75B 参数，再由 ZeRO-2 对部分状态按 DP 分片；
- 增大 PP 阶段数而保持微批次数不变时，简单气泡比例上升；
- 结果不能直接判断 20GB 显存是否一定可跑，因为激活和临时内存尚未计入。

### Level 1：CPU/GPU 通用 DDP Benchmark

保存为 `ddp_train_lab.py` ：

```
#!/usr/bin/env python3
import argparse
import contextlib
import json
import os
import time

import torch
import torch.distributed as dist
import torch.nn as nn
import torch.nn.functional as F
from torch.nn.parallel import DistributedDataParallel as DDP

def parse_args():
    p = argparse.ArgumentParser()
    p.add_argument("--hidden", type=int, default=1024)
    p.add_argument("--layers", type=int, default=4)
    p.add_argument("--local-batch", type=int, default=32)
    p.add_argument("--grad-accum", type=int, default=1)
    p.add_argument("--warmup", type=int, default=3)
    p.add_argument("--steps", type=int, default=20)
    p.add_argument("--bucket-mb", type=float, default=25.0)
    return p.parse_args()

def make_model(hidden, layers):
    modules = []
    for _ in range(layers):
        modules += [nn.Linear(hidden, hidden), nn.GELU()]
    modules.append(nn.Linear(hidden, hidden))
    return nn.Sequential(*modules)

def sync(device):
    if device.type == "cuda":
        torch.cuda.synchronize(device)

def main():
    args = parse_args()
    use_cuda = torch.cuda.is_available()
    backend = "nccl" if use_cuda else "gloo"
    dist.init_process_group(backend=backend)

    rank = dist.get_rank()
    world = dist.get_world_size()
    local_rank = int(os.environ.get("LOCAL_RANK", "0"))

    if use_cuda:
        torch.cuda.set_device(local_rank)
        device = torch.device("cuda", local_rank)
    else:
        device = torch.device("cpu")
        # 多进程 CPU 实验避免每个进程都占满全部 CPU 线程。
        torch.set_num_threads(max(1, (os.cpu_count() or 2) // world))

    # 构造模型前使用相同种子，使各 rank 初始参数一致。
    torch.manual_seed(2026)
    model = make_model(args.hidden, args.layers).to(device)
    ddp = DDP(
        model,
        device_ids=[local_rank] if use_cuda else None,
        bucket_cap_mb=args.bucket_mb,
        gradient_as_bucket_view=True,
    )
    optimizer = torch.optim.SGD(ddp.parameters(), lr=1e-3)
    params = sum(p.numel() for p in ddp.parameters())

    # 数据种子按 rank 区分，模拟不同数据分片。
    generator = torch.Generator(device=device)
    generator.manual_seed(1000 + rank)

    def train_step():
        optimizer.zero_grad(set_to_none=True)
        loss_value = 0.0
        for micro in range(args.grad_accum):
            # 非最后微步不做梯度同步；forward 也必须位于 no_sync 内。
            ctx = (
                ddp.no_sync()
                if micro < args.grad_accum - 1
                else contextlib.nullcontext()
            )
            with ctx:
                x = torch.randn(
                    args.local_batch, args.hidden,
                    device=device, generator=generator
                )
                target = torch.randn(
                    args.local_batch, args.hidden,
                    device=device, generator=generator
                )
                loss = F.mse_loss(ddp(x), target) / args.grad_accum
                loss.backward()
                loss_value += float(loss.detach())
        optimizer.step()
        return loss_value

    for _ in range(args.warmup):
        train_step()
    sync(device)
    dist.barrier()

    if use_cuda:
        torch.cuda.reset_peak_memory_stats(device)

    start = time.perf_counter()
    last_loss = None
    for _ in range(args.steps):
        last_loss = train_step()
    sync(device)
    dist.barrier()
    elapsed = time.perf_counter() - start

    # 同步训练应使用最慢 rank 的耗时计算端到端吞吐。
    elapsed_tensor = torch.tensor(elapsed, dtype=torch.float64, device=device)
    dist.all_reduce(elapsed_tensor, op=dist.ReduceOp.MAX)
    max_elapsed = float(elapsed_tensor.item())

    local_samples = args.steps * args.local_batch * args.grad_accum
    global_samples = local_samples * world
    peak_gib = (
        torch.cuda.max_memory_allocated(device) / (1024 ** 3)
        if use_cuda else None
    )

    if rank == 0:
        print(json.dumps({
            "world_size": world,
            "backend": backend,
            "device": str(device),
            "torch_version": torch.__version__,
            "parameters": params,
            "local_batch_per_microstep": args.local_batch,
            "grad_accum": args.grad_accum,
            "global_batch_per_optimizer_step": (
                args.local_batch * args.grad_accum * world
            ),
            "max_elapsed_s": max_elapsed,
            "step_ms": max_elapsed * 1000 / args.steps,
            "global_samples_per_s": global_samples / max_elapsed,
            "peak_allocated_gib_rank0": peak_gib,
            "last_loss_rank0": last_loss,
        }, indent=2))

    dist.destroy_process_group()

if __name__ == "__main__":
    main()
```

### 预期现象与结果分析

- GPU 模式使用 NCCL，CPU 回退使用 Gloo；
- 两个 rank 使用不同随机数据，但 DDP 同步后参数更新保持一致；
- 强扩展中每卡矩阵变小，计算效率可能下降，通信占比上升；
- 弱扩展通常更容易获得较高吞吐，但全局 Batch 变化后不能直接比较收敛；
- `grad_accum>1` 时，代码只在最后一个微步同步梯度；若移除 `no_sync()` ，每个微步都可能触发通信；
- 双 RTX 3080 没有 NVLink，通信经过 PCIe，扩展效率受主板拓扑、PCIe 代际和 CPU Root Complex 影响；
- 本实验是合成 MLP，结果只代表当次环境，不能替代真实 Transformer、真实序列长度和真实数据管线的 Benchmark。

比较时要使用相同 warmup、steps、精度、功耗状态和软件环境，至少重复三次并报告中位数。

## 优化前后对照

| 场景 | 优化前 | 优化后 | 验证指标 |
| --- | --- | --- | --- |
| 多 GPU 但吞吐不升 | 直接复制单卡脚本 | DDP + 数据分片 + 正确计时 | samples/s、扩展效率 |
| 累积梯度通信过多 | 每个微步都同步 | 非最后微步 `no_sync()` | Collective 次数、step time |
| 模型状态 OOM | 每卡完整 Adam 状态 | FSDP/ZeRO 分片 | peak memory、通信暴露 |
| 单层无法放下 | 只扩大 DP | 引入 TP | 单卡分区参数、层内通信 |
| PP 利用率低 | 微批次少、阶段不均 | 调微批次和层映射 | bubble、stage idle time |
| 长序列 OOM | 把 SP/CP 混为一谈 | 根据激活与 Attention 选 SP/CP | peak memory、attention time |
| MoE 长尾 | 只看平均专家负载 | 跟踪每 rank token 与 All-to-All | P99 rank time、负载差异 |

真正的优化前后对照必须保证数值精度、训练语义和有效 Batch 可比。显存下降但吞吐大幅下降，或吞吐提高但收敛目标改变，都不能只用一个数字宣布“优化成功”。

## 常见错误与排查

### 1\. 程序启动后永久等待

常见原因是 rank 数、地址/端口、网络接口或 Collective 调用顺序不一致。确认所有节点的 `nnodes` 、 `nproc-per-node` 一致，每个 rank 以相同顺序进入 Collective，并使用 `TORCH_DISTRIBUTED_DEBUG=DETAIL` 找到失配点。

### 2\. 两卡反而更慢

先确认比较的是强扩展还是弱扩展。小矩阵、很小 Batch、PCIe 互联、CPU 数据瓶颈、GPU 降频和频繁同步都会让通信/启动开销超过收益。

### 3\. OOM 与估算差距很大

16 Bytes/参数模型没有包含激活、Attention 临时张量、通信 Bucket、CUDA Context 和碎片。分别测 allocated/reserved、峰值激活，并用缩短序列、减小微批次和关闭某一功能的方法定位。

### 4\. 增加 GPU 后 Loss 曲线变了

检查全局 Batch、学习率、warmup、随机种子、数据采样和梯度缩放。DP 度变化会改变全局 Batch；若要保持优化语义，应相应调整微批次或梯度累积，并重新验证学习率策略。

### 5\. 梯度累积没有减少通信

仅仅把 Loss 除以累积步数不够。DDP 默认每次 backward 都同步；非最后微步要把 forward 与 backward 一起放入 `no_sync()` 上下文。

### 6\. 某些参数没有梯度

动态图分支可能产生 unused parameters。先确认模型逻辑； `find_unused_parameters=True` 可以帮助某些模型正确运行，但会增加图遍历开销，不应作为不理解问题时的永久开关。

### 7\. 训练正常，保存/恢复后不一致

混合并行检查点需要记录并行度、rank 映射、优化器分片、随机数状态、数据游标和框架版本。改变 TP/PP/EP 后通常需要显式的检查点重分片或转换工具。

## 面试题与答案

### 1\. DDP 会自动把输入数据分给不同 GPU 吗？

不会。DDP 同步梯度，不负责切分输入。通常使用 `DistributedSampler` ，并在每个 epoch 设置一致的 epoch 种子，确保各 rank 读取互不重复且可复现的数据分片。

### 2\. 为什么混合并行里的全局 Batch 不能乘总 GPU 数？

TP、PP、CP 等 rank 在共同处理同一份样本，只有数据并行副本处理独立 Batch。应使用 `micro_batch × grad_accum × DP_degree` 。

### 3\. ZeRO-3 与 TP 的核心区别是什么？

ZeRO-3 在数据并行组中分片参数、梯度和优化器状态，计算某层前按需聚合参数；TP 则把层内矩阵计算本身拆给多个 rank。二者都能降低单卡参数占用，但通信时机、计算分工和适用瓶颈不同。

### 4\. Sequence Parallel 和 Context Parallel 有什么区别？

SP 通常配合 TP，把特定操作和激活沿序列维切分，减少 TP 区域的冗余；CP 面向完整长上下文，把 Attention 的序列工作与激活跨 rank 分担。名称相似，但通信语义和解决的问题不同。

### 5\. 为什么 TP 一般优先放在节点内？

TP 往往每层都有 Collective，消息频率高，对延迟和带宽敏感。节点内 NVLink/NVSwitch 通常比跨节点网络更适合这种通信；但最终仍需结合实际拓扑和模型测量。

### 6\. 梯度通信与反向计算怎样重叠？

DDP 按 Bucket 收集梯度。当靠后的层先完成反向并填满 Bucket 后，即可异步启动 Collective，同时继续计算更前面的层。Bucket 太大启动晚，太小则消息过碎，需要 Profiler 调整。

### 7\. PP 的气泡怎样降低？

增加微批次数、采用 1F1B/交错调度、平衡每个 stage 的计算和减少阶段间不对称。但更多微批次可能增加调度和激活压力，不能只优化公式中的气泡比例。

### 8\. 为什么同步训练要看最慢 Rank？

Collective 和同步点会让快 rank 等待慢 rank。平均 rank 时间可能掩盖数据长尾、网络拥塞、温度降频和 MoE 路由不均，因此端到端步骤时间取决于尾部。

### 9\. 弱扩展效率高是否代表训练时间一定同比缩短？

不一定。弱扩展扩大了总问题规模或全局 Batch。虽然单位时间处理样本更多，但收敛所需优化步数、学习率和最终质量可能变化，应同时看 time-to-quality 或训练 Goodput。

### 10\. 如何选择 DP、TP、PP 的组合？

先满足容量：单层放不下用 TP，层总量放不下可用 PP/FSDP；再减少高频通信跨越慢链路；最后用剩余 GPU 形成 DP 提高吞吐。通过显存实测、通信模型和端到端 Benchmark 迭代，而不是套固定比例。

## Checklist

### 并行语义

- 能区分 global rank、local rank、world size 和 process group。
- 全局 Batch 只乘数据并行度，不误乘 TP/PP。
- 知道 DDP 不负责自动切分输入。
- 能区分 DP、ZeRO/FSDP、TP、PP、SP、CP、EP。
- 不把 SP 与 CP 当成同义词。

### 容量与性能模型

- 显存估算包含模型状态和激活的独立分析。
- 了解经典 Adam 16 Bytes/参数假设及其边界。
- 会估算环形 All-Reduce 每 rank 通信量。
- 会计算 PP 简化气泡比例。
- 会区分强扩展、弱扩展和扩展效率。

### 实验正确性

- GPU 异步计时前后正确同步。
- DDP 使用每 GPU 一个进程，设备绑定正确。
- 各 rank 数据不同、初始模型参数一致。
- 梯度累积时正确使用 no\\\_sync()。
- 使用最慢 rank 耗时计算同步训练吞吐。
- 性能结果记录模型形状、Batch、精度、软件与拓扑。

- Ampere 包含 RTX 3080/3090、A100。

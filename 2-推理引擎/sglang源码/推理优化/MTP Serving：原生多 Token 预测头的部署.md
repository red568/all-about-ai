## 课程定位

这一课回答的问题是“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”。分析从原生 MTP 预测头与训练目标与服务目标的关系开始，随后落到计算模型、实现路径和发布验收。MTP Serving：原生多 Token 预测头的部署会同时受到工作负载、模型修订、运行时调度、显存容量、并发状态与服务等级约束。正文会把相关机制还原成原生 MTP 预测头等可观察实体，再据此划定收益条件与额外成本。

证据分为机制模拟和真实 CUDA 测量。前者用可控变量观察原生 MTP 预测头怎样影响训练目标与服务目标，后者把框架、Kernel、内存和硬件成本计入结果。两条路径使用不同来源标签，并保留原生 MTP 预测头相关环境与限制；参数组合可以随版本改变，证据链仍要支持复现、定位和回退。

## 学习目标

1. 准确解释原生 MTP 预测头、训练目标与服务目标和 MTP Depth 之间的状态与资源关系。
2. 使用“Utility(d) = Saved\_target\_time(d) - MTP\_cost(d) - Verify\_overhead(d)”建立可计算的收益边界并解释全部变量。
3. 围绕 MTP 头准确率、位置接受率、服务加速比和回退率设计可复现实验。
4. 识别训练指标提升但接受长度不变、MTP 头与主干权重错配和代码任务有效而对话退化等典型失败模式。
5. 对“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”给出包含适用条件、证据、风险和回滚的工程答案。

## 前置知识与环境

阅读 MTP Serving：原生多 Token 预测头的部署需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及原生 MTP 预测头时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕原生 MTP 预测头的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及学习者自行准备的本地小模型或兼容制品。

验证原生 MTP 预测头前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把原生 MTP 预测头状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 工程问题

评估 MTP Serving：原生多 Token 预测头的部署时，先不要回答“打开以后能快多少”。需要固定模型与修订、输入输出长度分布、到达过程、并发、采样、缓存状态、MTP 头准确率口径、服务等级和硬件环境，再评审“选择可部署的 MTP 深度”和“是否微调 MTP 头”。这些条件共同决定收益、成本和资源竞争。

分析范围由八个可观察概念组成：原生 MTP 预测头、训练目标与服务目标、MTP Depth、Target 主干复用、Checkpoint 绑定、域适配、多 LoRA 条件、服务引擎接口。算法层的变化会经运行时和平台层传到 Adapter 切换延迟与回退率。每个概念都像原生 MTP 预测头一样绑定具体状态、责任边界、观测字段和故障表现。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：MTP 为什么适合当 Speculator

如果目标模型内部已经有未来 token 预测模块：

```
Target hidden state h_t
   ├─ main LM head → x_{t+1}
   ├─ MTP head 1  → x_{t+2}
   ├─ MTP head 2  → x_{t+3}
   └─ MTP head k  → x_{t+k+1}
```

优势是：

- 不需要再部署一个完整独立小语言模型；
- 可能复用 Target 的 embedding / hidden state；
- 模型作者已经在训练阶段注入未来 token supervision；
- checkpoint 与 Target 结构天然关联。

但注意：

“模型有 MTP 模块”不等于“线上打开一个参数就一定获得加速”。

必须看 Runtime 是否支持、MTP head 质量、验证路径、并发与硬件。

### MTP Training 与 MTP Serving 不是同一件事

训练阶段可能使用：

$$
\mathcal L=\mathcal L_{next}+\lambda\sum_{k=1}^{K}\mathcal L_{mtp,k}
$$

它的目的可能包括：

- 改善 representation；
- 提高 sample efficiency；
- 为未来 speculative inference 提供 head。

Serving 阶段关注的是：

$$
Speedup=f(HeadQuality,HeadCost,VerifyCost,Concurrency)
$$

一个训练上有益的 MTP head，如果推理时额外计算很重或 acceptance 不高，未必适合 Serving。

### MTP Depth 的选择

假设有 $K$ 个未来 heads。

更深的 head 通常预测更难，因此可以定义：

$$
a_k=P(\text{head }k\text{ survives prefix verification})
$$

在线上不应默认全部开启。可以根据真实数据扫描：

```
Depth 1 → accepted 1.8 / round
Depth 2 → accepted 2.5 / round
Depth 4 → accepted 3.0 / round
Depth 8 → accepted 3.1 / round，但 verify cost 明显上升
```

最优点由实际性能决定。

### 域适配：为什么同一个 MTP 在代码上很好，在开放聊天上可能一般

MTP 学到的是未来 token 条件分布。

如果上线 workload 与训练分布不同：

$$
P_{train}(x)\neq P_{serve}(x)
$$

则 acceptance 可能明显下降。

因此可以针对：

- code；
- math；
- reasoning；
- customer-service；
- JSON/tool call；

分别做轻量 MTP finetune 或 calibration。

但必须同时确认：

只微调 MTP 模块是否保持 Target 主模型输出分布不变？

Speculator 可以改变候选，但最终 Target verification 仍需保证结果正确。

### MTP Checkpoint 生命周期

一个生产平台至少要记录：

```
Target model revision
Target tokenizer revision
MTP speculator revision
MTP depth
Training dataset/version
Runtime version
Compatibility hash
```

不能只把文件名写成：

```
mtp_final.pt
```

因为 Target 升级后，旧 MTP 可能直接不兼容或 acceptance 下降。

### MTP 与 Multi-LoRA 的关系

这是生产环境里很容易遗漏的组合问题。

如果 Base Model 上叠加不同 LoRA：

```
Base + LoRA A
Base + LoRA B
```

Target 输出分布已经发生变化。原来针对 Base 训练的 MTP speculator 是否仍然有高 acceptance，需要单独验证。

可能的策略：

1. Base 共用 MTP，接受 acceptance 下降；
2. 热门 LoRA 单独适配 MTP；
3. 低流量 LoRA 关闭 MTP；
4. Router 根据 adapter id 选择 speculator policy。

### 性能模型

MTP 一轮成本可抽象为：

$$
T_{MTP}=T_{feature}+T_{heads}(K)+T_{verify}(K)+T_{commit}
$$

如果多个 head 真正并行， $T_{heads}(K)$ 增长可能较慢；如果实现仍然串行或触发多个小 Kernel，则优势会被 Runtime overhead 抵消。

因此真实测试至少采集：

- MTP forward latency；
- Target verify latency；
- mean accepted length；
- per-position acceptance；
- TPOT；
- total throughput；
- extra VRAM。

### 实验

本课复用 Project01 的 MTP 路径，章节阶段先做 Level 0 模拟：

- 设置 1/2/4/8 个 heads；
- 为更深 head 设置不同 acceptance；
- 设置并行/串行 head cost；
- 扫描并发。

Level 2 使用实际支持 MTP 的模型/Runtime 时，必须记录具体模型 revision 和 Runtime 版本，不把一个模型结果泛化到所有 MTP 模型。

### 原生 MTP 预测头

在 MTP Serving：原生多 Token 预测头的部署中，原生 MTP 预测头的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。原生 MTP 预测头连接训练目标与服务目标时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量原生 MTP 预测头时分别记录算力、显存、带宽、CPU 开销与同步。发生“训练损失改善不保证服务净收益”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐原生 MTP 预测头的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估原生 MTP 预测头需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。如何绑定制品版本至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

原生 MTP 预测头进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。多 LoRA 热切换后缓存污染一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察原生 MTP 预测头需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。加载时间同时注明单位、窗口和分母。这些字段使“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”可以在发布后按原条件回放。

### 训练目标与服务目标

解释训练目标与服务目标时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。MTP Serving：原生多 Token 预测头的部署的请求可能在这些交界处增加等待、计算或复制。与 MTP Depth 交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕训练目标与服务目标建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。深度增加会提升候选数量也会累积低置信位置会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

按域启用或禁用是否合适，取决于训练目标与服务目标所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

训练目标与服务目标带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现引擎只支持部分模型架构时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

训练目标与服务目标的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。域内外差异没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”在具体负载下是否成立。

### MTP Depth

MTP Depth 在 MTP Serving：原生多 Token 预测头的部署中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与 Target 主干复用之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

Checkpoint 与分词器及主干修订必须一致对 MTP Depth 的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认 MTP Depth 的变化来自哪里，本课对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

MTP Depth 的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证为 Adapter 共享还是专用 MTP 时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖 MTP Depth 影响到的 Token、采样、结构、结束状态与错误。若检测到深度增加造成验证和显存反噬，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为 MTP Depth 建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。Adapter 切换延迟的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”。

### Target 主干复用

对 Target 主干复用做边界检查，要覆盖输入、输出、状态归属和销毁时点。MTP Serving：原生多 Token 预测头的部署的等待、计算及复制都能沿这些节点定位。Target 主干复用传给 Checkpoint 绑定的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

Target 主干复用的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。域适配改变未来 Token 的可预测性通常只先改变其中几项，其他资源随后可能进入关键路径。Target 主干复用的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，Target 主干复用对系统的贡献也会变化。选择引擎回退路径应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 Target 主干复用的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。训练指标提升但接受长度不变会触发停止与回退，系统恢复到已有证据支持的配置。

Target 主干复用相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。回退率必须附带口径。缺少这些信息时，关于“如何把训练期 MTP 头转化为可测量、可回滚的推理加速路径？”的判断无法在上线后复核。

“是否微调 MTP 头”进入方案评审前，要绑定具体服务承诺和位置接受率、额外显存、域内外差异。资源侧检查训练目标与服务目标，机制侧限定“训练损失改善不保证服务净收益”，故障侧为 MTP 头与主干权重错配准备停止动作。测试样本不代表业务时，结论只覆盖该样本。

验证“是否微调 MTP 头”需要三条可复现路径：已确认的基线、只改“是否微调 MTP 头”因素的候选、无需重新取大制品的回退。三者共享请求和随机种子，数据按负载区间与请求形态统计。最终文档保存“是否微调 MTP 头”的取舍理由、有效期和回退率相对维护成本的变化。

决定“按域启用或禁用”是否上线时，服务承诺是评审起点，额外显存、域内外差异、回退率构成结果证据。还需解释 Target 主干复用怎样变化、“Checkpoint 与分词器及主干修订必须一致”在哪些负载下有效，以及遇到多 LoRA 热切换后缓存污染时如何停止。

实验为“为 Adapter 共享还是专用 MTP”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“为 Adapter 共享还是专用 MTP”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及回退率的改善是否覆盖新增运维成本。

### 决策 6：选择引擎回退路径

“选择引擎回退路径”进入方案评审前，要绑定具体服务承诺和域内外差异、回退率、位置接受率。资源侧检查域适配，机制侧限定“多 LoRA 会让共享 MTP 的条件分布发生变化”，故障侧为深度增加造成验证和显存反噬准备停止动作。测试样本不代表业务时，结论只覆盖该样本。

验证“选择引擎回退路径”需要三条可复现路径：已确认的基线、只改“选择引擎回退路径”因素的候选、无需重新取大制品的回退。三者共享请求和随机种子，数据按负载区间与请求形态统计。最终文档保存“选择引擎回退路径”的取舍理由、有效期和回退率相对维护成本的变化。

## 失败模式与故障诊断

### 失败模式 1：训练指标提升但接受长度不变

记录到“训练指标提升但接受长度不变”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿原生 MTP 预测头回放事件，再比较 MTP 头准确率与位置接受率。若完成数存在账差，先修复计量链。

对“训练指标提升但接受长度不变”先执行在线保护，再处理复发条件。面向训练指标提升但接受长度不变的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查额外显存的采集完整性。

### 失败模式 2：MTP 头与主干权重错配

排查“MTP 头与主干权重错配”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看训练目标与服务目标的时间线以及位置接受率、服务加速比。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

修复“MTP 头与主干权重错配”分为影响控制和复验。针对 MTP 头与主干权重错配可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对加载时间没有被隐藏。

### 失败模式 3：代码任务有效而对话退化

诊断“代码任务有效而对话退化”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查 MTP Depth，结合服务加速比与额外显存定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“代码任务有效而对话退化”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认域内外差异没有转移到未计量层。

### 失败模式 4：多 LoRA 热切换后缓存污染

出现“多 LoRA 热切换后缓存污染”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿 Target 主干复用的事件查看额外显存和加载时间，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

“多 LoRA 热切换后缓存污染”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验 Adapter 切换延迟。

### 失败模式 5：引擎只支持部分模型架构

针对“引擎只支持部分模型架构”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。Checkpoint 绑定的时间线配合加载时间、域内外差异可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

对“引擎只支持部分模型架构”先执行在线保护，再处理复发条件。面向引擎只支持部分模型架构的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查回退率的采集完整性。

### 失败模式 6：深度增加造成验证和显存反噬

“深度增加造成验证和显存反噬”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查域适配的阶段事件，并用域内外差异及 Adapter 切换延迟缩小故障位置。客户端、服务端、计费数据均需完成对账。

修复“深度增加造成验证和显存反噬”分为影响控制和复验。针对深度增加造成验证和显存反噬可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对 MTP 头准确率没有被隐藏。

```
"""Lesson 04 — paired serving check for a native MTP deployment."""

from __future__ import annotations

import argparse

from phase3lab.shared.evidence import require_distinct_endpoints, summarize_records
from phase3lab.shared.http_client import completion, discover_models, metrics_evidence
from phase3lab.shared.runner import LabSpec, PreconditionError, require_count, run_cli
from phase3lab.shared.stats import paired_delta

SPEC = LabSpec(
    lab_id="lesson-04-mtp-serving",
    title="MTP Serving：原生多 Token 预测头的部署核验",
    goal="对同一 Target 的 MTP-disabled 与 MTP-enabled 服务做成对请求和证据采集。",
    real_evidence=("two endpoint identities", "paired request records", "metrics snapshots"),
    required_inputs=("two separately configured endpoints", "same served Target model"),
    outputs=("paired latency delta", "per-endpoint metrics hashes", "request records"),
    acceptance=("endpoints are distinct", "model identity matches", "both sides receive every prompt"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--require-metric-fragment", default="mtp")

def validate_model_pair(left: list[str], right: list[str], requested: str) -> str:
    if requested != "auto":
        if requested not in left or requested not in right:
            raise PreconditionError(f"requested model {requested} is not served by both endpoints")
        return requested
    overlap = sorted(set(left) & set(right))
    if not overlap:
        raise PreconditionError("endpoints have no common served model ID")
    return overlap[0]

def fixture(args: argparse.Namespace) -> dict:
    baseline = [112.0, 108.0, 115.0, 110.0]
    candidate = [98.0, 94.0, 100.0, 97.0]
    return {
        "endpoint_roles": {"baseline": "mtp-disabled", "candidate": "mtp-enabled"},
        "paired_delta": paired_delta(baseline, candidate),
        "metric_fragment_present": True,
        "pairs": len(baseline),
    }

def real(args: argparse.Namespace) -> dict:
    require_count(args.base_url, 2, "MTP A/B experiment")
    if len(args.base_url) != 2:
        raise ValueError("MTP A/B experiment accepts exactly two --base-url values")
    require_distinct_endpoints(args.base_url)
    models = [discover_models(url) for url in args.base_url]
    model = validate_model_pair(models[0], models[1], args.model)
    metrics_before = [metrics_evidence(url) for url in (args.evidence_url or args.base_url)]
    if len(metrics_before) != 2:
        raise ValueError("provide zero or exactly two --evidence-url values")
    fragment = args.require_metric_fragment.lower()
    if fragment and not any(fragment in name.lower() for item in metrics_before for name in item["sample_names"]):
        raise PreconditionError(f"metrics do not expose a name containing {fragment!r}; cannot attribute MTP state")

    pairs = []
    for index in range(args.requests):
        prompt = f"{args.prompt}\npaired_case={index}"
        left = completion(args.base_url[0], model, prompt, args.max_new_tokens, request_id=f"pair-{index}-baseline")
        right = completion(args.base_url[1], model, prompt, args.max_new_tokens, request_id=f"pair-{index}-candidate")
        pairs.append({"pair_id": index, "baseline": left.json(), "candidate": right.json()})
    left_records = [completion_record(pair["baseline"]) for pair in pairs]
    right_records = [completion_record(pair["candidate"]) for pair in pairs]
    if not all(item.ok for item in left_records + right_records):
        raise RuntimeError("one or more paired requests failed")
    metrics_after = [metrics_evidence(url) for url in (args.evidence_url or args.base_url)]
    return {
        "model": model,
        "endpoint_models": models,
        "metrics_before": metrics_before,
        "metrics_after": metrics_after,
        "baseline": summarize_records(left_records),
        "candidate": summarize_records(right_records),
        "paired_delta": paired_delta([item.latency_ms for item in left_records], [item.latency_ms for item in right_records]),
        "pairs": pairs,
    }

def completion_record(value: dict):
    from phase3lab.shared.http_client import RequestRecord
    return RequestRecord(**value)

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 课程定位

理解 Agentic Inference：工具调用、Fan-out 与长会话，需要先回答“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”。本课沿着概念边界、性能关系、实现证据和发布条件四条线展开，其中 Agentic Task 与工具调用轮次是最先核对的状态。工作负载、模型修订、运行时、资源余量和服务承诺共同决定一次用户任务会展开为多次模型与工具调用是否值得采用，后续每个结论都会注明这些条件。

实验采用两条证据路径。CPU 机制模拟隔离 Agentic Task 与工具调用轮次的因果关系；真实 CUDA 路径记录实现、框架和硬件开销。报告分别标记两类结果，任务成功率的模拟值不充当 GPU 基准，单台设备的绝对速度也不外推。最终结论必须能够复现、诊断并回滚。

## 学习目标

1. 准确解释 Agentic Task、工具调用轮次和 Fan-out 之间的状态与资源关系。
2. 使用“T\_task = Σ(serial stages) + max(parallel branches)；Amp = total attempts / original tasks”建立可计算的收益边界并解释全部变量。
3. 围绕任务成功率、模型调用次数、工具调用次数和每成功任务成本设计可复现实验。
4. 识别循环工具调用耗尽预算、并行分支形成请求风暴和非幂等工具被重复执行等典型失败模式。
5. 对“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”给出包含适用条件、证据、风险和回滚的工程答案。

## 前置知识与环境

阅读 Agentic Inference：工具调用、Fan-out 与长会话需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及 Agentic Task 时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 Agentic Task 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及学习者自行准备的本地小模型或兼容制品。

验证 Agentic Task 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Agentic Task 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 工程问题

决定是否采用 Agentic Inference：工具调用、Fan-out 与长会话前，先冻结模型版本、长度分布、流量到达、并发、采样、缓存状态、任务成功率、服务等级和硬件配置。评审“限制最大轮次和 Fan-out”和“选择串行或并行工具调用”时，由这些记录解释收益分子、成本分母及共享资源竞争。

本课跟踪八个概念：Agentic Task、工具调用轮次、Fan-out、任务截止时间、会话状态、幂等工具、审批节点、任务级计量。虽然它们分属不同系统层级，恢复成功率和每成功任务成本会同时受到这些状态影响。后文从 Agentic Task 开始，逐项说明谁维护状态、在哪里计量、什么情况下失效，以及结果怎样传到请求端。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：1 QPS 用户流量可能变成 10 QPS 模型流量

设外部请求到达率：

$$
\lambda_u
$$

每个 Agent 请求平均触发 $F$ 次模型调用，则内部模型调用率：

$$
\lambda_m=\lambda_u\cdot E[F]
$$

如果一个请求平均 fan-out 8 次：

```
外部 20 req/s
→ 内部可能 160 model calls/s
```

而且它们往往不是平滑到达，而是在 Planner 决策后同时爆发。

这就是 \*\*traffic amplification\*\*。

### Agent Request 的生命周期

一个完整会话可能经历：

```
RUNNING_LLM
   ↓
WAITING_TOOL
   ↓
RUNNING_LLM
   ↓
WAITING_USER/APP
   ↓
RUNNING_LLM
   ↓
DONE
```

这与普通持续 Decode 完全不同。

关键问题：工具等待时：

- 是否保留会话状态？
- KV 是否继续占 GPU？
- 多久后 offload/recompute 更划算？
- 工具超时后是否取消下游模型调用？

### Fan-out / Fan-in

并行工具调用：

```
Planner
      /   |   \
Tool A Tool B Tool C
      \   |   /
       Aggregator
```

端到端延迟受最慢分支影响：

$$
T_{fanout}\approx\max_i T_i + T_{merge}
$$

但成本近似是所有分支之和：

$$
C_{fanout}\approx\sum_i C_i
$$

因此并行会降低 wall-clock latency，却可能增加瞬时资源压力和总成本。

### Deadline Propagation

用户给整个 Agent 30 秒，不代表每一步都能用 30 秒。

需要维护：

$$
D_{remain}=D_{global}-Now
$$

进入子调用时分配：

$$
D_i\le D_{remain}
$$

如果某个 Tool 已耗时 25 秒，再启动一个预期 20 秒的 Deep Reasoning 调用，大概率只会浪费资源。

所以 Gateway/Agent Runtime 应把 deadline 传播到：

- sub-agent；
- LLM call；
- tool call；
- reranker/embedding；
- final synthesis。

### Budget Propagation

类似 Deadline，Cost/Token Budget 也要共享。

设整个 Agent 有预算 $B$ ：

$$
\sum_i B_i\le B
$$

如果 Planner 前两步已花掉 80%，后续就应：

- 减少 candidates；
- 切换小模型；
- 降低 reasoning budget；
- 跳过低价值工具；
- 提前总结。

### Idempotency 与 Retry Storm

Agent 链路长，任何一步都可能失败。

如果上游简单重试整个请求：

```
原请求触发 8 个子调用
超时 → 整体重试
又触发 8 个
```

很容易形成 retry amplification。

需要：

- request\_id；
- step\_id；
- idempotency key；
- per-step retry；
- exponential backoff；
- retry budget。

尤其对 Code/Payment/DB Write 等有副作用工具，幂等不是性能优化，而是正确性要求。

### Observability：必须用 Trace，不是只有日志

一个 Agent 请求应该有一个 root trace：

```
trace_id=abc
├─ planner_llm
├─ search_tool
├─ embedding
├─ reranker
├─ subagent_llm
└─ final_llm
```

这样才能回答：

用户说“Agent 很慢”，到底是模型慢、搜索慢、工具超时还是 fan-out 过多？

第 28 课会系统讲 Distributed Tracing。

### Agent Workload 的容量模型

传统 capacity 常按：

$$
QPS\times AvgTokens
$$

Agent 需要：

$$
Work_u=\sum_{i\in Invocations(u)}Tokens_i\cdot ModelWeight_i
$$

同时记录 fan-out distribution：

- P50 calls/request；
- P95；
- P99；
- max burst。

扩缩容不能只看外部 API QPS。

本课不单独建 Lab，Project02 的 workload generator 增加 Agent 模式：

- 0～8 tool branches；
- 每 branch 0～2 次 LLM；
- final 1 次。

输出内部 QPS 放大倍数和 burstiness。

### Agentic Task

对 Agentic Task 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Agentic Inference：工具调用、Fan-out 与长会话的等待、计算及复制都能沿这些节点定位。Agentic Task 传给工具调用轮次的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

Agentic Task 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。并行 Fan-out 缩短关键路径但扩大资源峰值通常只先改变其中几项，其他资源随后可能进入关键路径。Agentic Task 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，Agentic Task 对系统的贡献也会变化。设置任务与子调用预算应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 Agentic Task 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。审批后上下文或凭证过期会触发停止与回退，系统恢复到已有证据支持的配置。

Agentic Task 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。Fan-out 峰值必须附带口径。缺少这些信息时，关于“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”的判断无法在上线后复核。

### 工具调用轮次

在 Agentic Inference：工具调用、Fan-out 与长会话中，工具调用轮次的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。工具调用轮次连接 Fan-out 时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量工具调用轮次时分别记录算力、显存、带宽、CPU 开销与同步。发生“工具失败和重试会放大模型调用次数”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐工具调用轮次的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估工具调用轮次需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。持久化会话检查点至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

工具调用轮次进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。子调用超时未传播到父任务一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察工具调用轮次需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。重试放大系数同时注明单位、窗口和分母。这些字段使“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”可以在发布后按原条件回放。

### Fan-out

解释 Fan-out 时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Agentic Inference：工具调用、Fan-out 与长会话的请求可能在这些交界处增加等待、计算或复制。与任务截止时间交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕 Fan-out 建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。会话状态影响恢复与重放正确性会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

定义工具幂等和重试是否合适，取决于 Fan-out 所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

Fan-out 带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现只按 Token 计费忽略工具资源时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

Fan-out 的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。恢复成功率没有单位、统计窗口和分母时不参与决策。完整记录用于复查“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”在具体负载下是否成立。

### 任务截止时间

任务截止时间在 Agentic Inference：工具调用、Fan-out 与长会话中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与会话状态之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

审批暂停会跨越普通请求生命周期对任务截止时间的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认任务截止时间的变化来自哪里，本课对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

任务截止时间的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证引入人工审批与恢复时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖任务截止时间影响到的 Token、采样、结构、结束状态与错误。若检测到循环工具调用耗尽预算，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为任务截止时间建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。每成功任务成本的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”。

### 任务级计量

任务级计量在 Agentic Inference：工具调用、Fan-out 与长会话中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与 Agentic Task 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

任务级计量的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证持久化会话检查点时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖任务级计量影响到的 Token、采样、结构、结束状态与错误。若检测到子调用超时未传播到父任务，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为任务级计量建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。关键路径时长的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“一个用户任务如何膨胀为多次模型调用，并在截止时间内稳定完成？”。

### 机制 1：一次用户任务会展开为多次模型与工具调用

### 机制 3：工具失败和重试会放大模型调用次数

## 工程决策与取舍

### 决策 1：限制最大轮次和 Fan-out

决定“限制最大轮次和 Fan-out”是否上线时，服务承诺是评审起点，任务成功率、工具调用次数、Fan-out 峰值构成结果证据。还需解释 Agentic Task 怎样变化、“一次用户任务会展开为多次模型与工具调用”在哪些负载下有效，以及遇到循环工具调用耗尽预算时如何停止。

实验为“引入人工审批与恢复”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“引入人工审批与恢复”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及每成功任务成本的改善是否覆盖新增运维成本。

## 失败模式与故障诊断

![课程配图](https://everythingai.top/api/assets/36b83517-5707-4d64-911e-aa80625816b7)

\*小黑故障现场：局部指标看似改善时，仍要追踪排队、资源和下游影响。\*

### 失败模式 1：循环工具调用耗尽预算

排查“循环工具调用耗尽预算”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看 Agentic Task 的时间线以及任务成功率、模型调用次数。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

“循环工具调用耗尽预算”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验关键路径时长。

### 失败模式 2：并行分支形成请求风暴

诊断“并行分支形成请求风暴”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查工具调用轮次，结合模型调用次数与工具调用次数定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

对“并行分支形成请求风暴”先执行在线保护，再处理复发条件。面向并行分支形成请求风暴的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查 Fan-out 峰值的采集完整性。

### 失败模式 3：非幂等工具被重复执行

出现“非幂等工具被重复执行”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿 Fan-out 的事件查看工具调用次数和关键路径时长，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

修复“非幂等工具被重复执行”分为影响控制和复验。针对非幂等工具被重复执行可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对重试放大系数没有被隐藏。

### 失败模式 4：审批后上下文或凭证过期

针对“审批后上下文或凭证过期”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。任务截止时间的时间线配合关键路径时长、Fan-out 峰值可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

处理“审批后上下文或凭证过期”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认恢复成功率没有转移到未计量层。

### 失败模式 5：子调用超时未传播到父任务

“子调用超时未传播到父任务”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查会话状态的阶段事件，并用 Fan-out 峰值及重试放大系数缩小故障位置。客户端、服务端、计费数据均需完成对账。

“子调用超时未传播到父任务”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验每成功任务成本。

### 失败模式 6：只按 Token 计费忽略工具资源

记录到“只按 Token 计费忽略工具资源”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿幂等工具回放事件，再比较重试放大系数与恢复成功率。若完成数存在账差，先修复计量链。

对“只按 Token 计费忽略工具资源”先执行在线保护，再处理复发条件。面向只按 Token 计费忽略工具资源的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查任务成功率的采集完整性。

```
"""Lesson 11 — execute an agentic fan-out/fan-in request DAG."""

from __future__ import annotations

import argparse
import concurrent.futures
import hashlib
import time

from phase3lab.shared.http_client import auth_headers, discover_models, extract_text, metrics_evidence, request_json
from phase3lab.shared.runner import LabSpec, PreconditionError, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-11-agentic-dag",
    title="Agentic Task：并行分支、汇聚与端到端证据",
    goal="让多个真实模型调用形成 fan-out/fan-in DAG，并区分节点延迟与端到端延迟。",
    real_evidence=("node dependency IDs", "per-node endpoint calls", "critical-path timing"),
    required_inputs=("one OpenAI-compatible endpoint", "served model"),
    outputs=("DAG trace", "node latency", "final response hash"),
    acceptance=("fan-out executes concurrently", "fan-in consumes branch outputs", "trace IDs are complete"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--fanout", type=int, default=3)

def dag_shape(fanout: int) -> list[dict]:
    if fanout < 2:
        raise ValueError("--fanout must be at least 2")
    nodes = [{"node_id": f"branch-{index}", "depends_on": ["input"]} for index in range(fanout)]
    nodes.append({"node_id": "synthesis", "depends_on": [item["node_id"] for item in nodes]})
    return nodes

def fixture(args: argparse.Namespace) -> dict:
    nodes = dag_shape(args.fanout)
    durations = {node["node_id"]: 10 + index * 3 for index, node in enumerate(nodes)}
    critical_path = max(durations[node] for node in nodes[-1]["depends_on"]) + durations["synthesis"]
    return {"nodes": nodes, "durations_ms": durations, "critical_path_ms": critical_path, "fan_in_consumed_all_branches": True}

def invoke(base: str, model: str, prompt: str, request_id: str, max_tokens: int) -> tuple[dict, str]:
    payload = {"model": model, "messages": [{"role": "user", "content": prompt}], "max_tokens": max_tokens, "temperature": 0}
    started = time.perf_counter()
    status, body, _ = request_json("POST", f"{base.rstrip('/')}/v1/chat/completions", payload, timeout=180, headers=auth_headers())
    latency = (time.perf_counter() - started) * 1000
    if status != 200:
        raise RuntimeError(f"node {request_id} returned HTTP {status}")
    text = extract_text(body)
    return ({"node_id": request_id, "status_code": status, "latency_ms": round(latency, 4), "output_sha256": hashlib.sha256(text.encode()).hexdigest(), "output_chars": len(text)}, text)

def real(args: argparse.Namespace) -> dict:
    if len(args.base_url) != 1:
        raise PreconditionError("provide exactly one --base-url")
    graph = dag_shape(args.fanout)
    served = discover_models(args.base_url[0])
    model = served[0] if args.model == "auto" else args.model
    if model not in served:
        raise PreconditionError(f"model {model} is not served")
    branch_prompts = [
        f"{args.prompt}\n你是分支 {index}，只分析一个不同风险，并给出依据。"
        for index in range(args.fanout)
    ]
    started = time.perf_counter()
    with concurrent.futures.ThreadPoolExecutor(max_workers=args.fanout) as pool:
        futures = [pool.submit(invoke, args.base_url[0], model, prompt, f"branch-{index}", args.max_new_tokens) for index, prompt in enumerate(branch_prompts)]
        branch_results = [future.result() for future in futures]
    branch_records = [item[0] for item in branch_results]
    branch_texts = [item[1] for item in branch_results]
    synthesis_prompt = "汇总以下分支，指出一致点与冲突：\n" + "\n---\n".join(branch_texts)
    synthesis_record, final_text = invoke(args.base_url[0], model, synthesis_prompt, "synthesis", args.max_new_tokens)
    wall_ms = (time.perf_counter() - started) * 1000
    return {
        "model": model,
        "metrics": metrics_evidence((args.evidence_url or args.base_url)[0]),
        "graph": graph,
        "nodes": branch_records + [synthesis_record],
        "branch_latency": latency_summary([item["latency_ms"] for item in branch_records]),
        "wall_ms": round(wall_ms, 4),
        "serial_latency_sum_ms": round(sum(item["latency_ms"] for item in branch_records) + synthesis_record["latency_ms"], 4),
        "final_output_sha256": hashlib.sha256(final_text.encode()).hexdigest(),
        "fan_in_input_sha256": hashlib.sha256(synthesis_prompt.encode()).hexdigest(),
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

这组失败验证制造“循环工具调用耗尽预算”，并检查告警、隔离、降级与回滚是否按顺序执行。任务成功率和相邻字段构成检测证据，稳定制品需兼容 Agentic Task。重新导流前核实缓存、队列、在途工作和“一次用户任务会展开为多次模型与工具调用”状态。

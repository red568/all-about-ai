## 课程定位

这一课回答的问题是“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”。分析从 Grammar 与有限状态机 FSM 的关系开始，随后落到计算模型、实现路径和发布验收。Structured Output Serving：Grammar、FSM 与 XGrammar 会同时受到工作负载、模型修订、运行时调度、显存容量、并发状态与服务等级约束。正文会把相关机制还原成 Grammar 等可观察实体，再据此划定收益条件与额外成本。

证据分为机制模拟和真实 CUDA 测量。前者用可控变量观察 Grammar 怎样影响有限状态机 FSM，后者把框架、Kernel、内存和硬件成本计入结果。两条路径使用不同来源标签，并保留 Grammar 相关环境与限制；参数组合可以随版本改变，证据链仍要支持复现、定位和回退。

## 学习目标

1. 准确解释 Grammar、有限状态机 FSM 和 XGrammar 之间的状态与资源关系。
2. 使用“T\_total = T\_compile(cache miss) + Σ(T\_decode + T\_mask)；Net = RetrySaved - ConstraintOverhead”建立可计算的收益边界并解释全部变量。
3. 围绕编译延迟、缓存命中率、每 Token 掩码延迟和重试节省设计可复现实验。
4. 识别首次编译造成 TTFT 尖峰、缓存键忽略 Schema 版本和复杂递归导致状态爆炸等典型失败模式。
5. 对“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”给出包含适用条件、证据、风险和回滚的工程答案。

## 前置知识与环境

阅读 Structured Output Serving：Grammar、FSM 与 XGrammar 需要理解自回归生成、Tokenizer、Prefill、Decode、KV Cache、批处理和分位延迟的基本含义。涉及 Grammar 时，所有缩写都会在正文首次出现处定义；没有某个特定框架经验不妨碍理解机制。实验需要 Python 3.11 或兼容版本。围绕 Grammar 的机制模拟只依赖 CPU；真实路径需要任意可用的 CUDA GPU、与驱动兼容的 PyTorch，以及学习者自行准备的本地小模型或兼容制品。

验证 Grammar 前必须记录 GPU 名称、数量、可用显存、驱动、CUDA、PyTorch、推理框架、模型摘要、精度、批量、序列长度和完整命令。脚本根据可用显存缩放模型、批量、上下文和样本数，并把 Grammar 状态写入报告；可选 CUDA 入口不下载未经确认的大模型。

## 工程问题

评估 Structured Output Serving：Grammar、FSM 与 XGrammar 时，先不要回答“打开以后能快多少”。需要固定模型与修订、输入输出长度分布、到达过程、并发、采样、缓存状态、编译延迟口径、服务等级和硬件环境，再评审“选择 JSON Schema 或 Grammar”和“缓存编译结果”。这些条件共同决定收益、成本和资源竞争。

分析范围由八个可观察概念组成：Grammar、有限状态机 FSM、XGrammar、Token Mask、Grammar 编译缓存、结构合法性、词表映射、受约束采样。算法层的变化会经运行时和平台层传到吞吐损失与重试节省。每个概念都像 Grammar 一样绑定具体状态、责任边界、观测字段和故障表现。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：不是“生成后修 JSON”，而是“非法 token 根本不能被采样”

普通采样：

$$
p(x)=softmax(logits)
$$

约束采样先构建合法集合 $A_s$ ，其中 $s$ 是 grammar 当前状态：

$$
logits'_i=\begin{cases} logits_i,&i\in A_s\\ -\infty,&i\notin A_s \end{cases}
$$

再采样：

$$
p^{'} \left(x\right) = s o f t m a x \left(l o g i t s^{'}\right)
$$

因此生成路径始终满足 grammar。

### Schema → Grammar → State

例如 JSON Schema：

```
object
├─ name: string
└─ age: integer
```

编译后可形成状态机：

```
START
 ↓
{
 ↓
"name"
 ↓
:
 ↓
STRING
 ↓
,
 ↓
"age"
 ↓
:
 ↓
INTEGER
 ↓
}
 ↓
END
```

真实 tokenizer 不是字符级，因此还要把 grammar 允许的字符/字节序列映射为合法 token IDs。

这一步是 Structured Output 性能工程的关键。

### 两个成本：Compile 与 Step

### 5.1 Grammar Compile Cost

第一次收到一个新 Schema，需要：

- parse；
- normalize；
- build automaton；
- tokenizer mapping；
- cache。

记为：

$$
T_{compile}
$$

如果每个请求都提交一个不同 Schema，并且不缓存，TTFT 会明显受影响。

### 5.2 Per-Token Mask Cost

每生成一个 token，需要：

1. 根据当前 FSM state 找 allowed set；
2. 生成/应用 token mask；
3. 采样；
4. 更新 state。

成本：

$$
T_{structured}=T_{model}+T_{mask}+T_{state}
$$

当模型很小、batch 很大或 token 很短时，CPU mask overhead 可能不再可忽略。

### Schema Cache

如果大量请求使用同一个工具 schema：

```
Tenant A: weather schema
Tenant B: weather schema
Tenant C: weather schema
```

可以使用 cache key：

$$
Key=Hash(NormalizedSchema,TokenizerRevision,BackendVersion)
$$

而不是只 hash 原始字符串。

原因：

- whitespace/字段顺序可能不同但语义相同；
- tokenizer 变化会改变 token mapping；
- backend 编译格式可能升级。

### FSM 状态与 Batching

同一个 batch 内不同请求可能处于不同 grammar state：

```
Req A：等待字段名
Req B：正在生成字符串
Req C：等待整数
```

因此 allowed-token mask 不同。

如果每个请求都在 CPU 生成一个全词表 bool mask：

$$
O(B\cdot |V|)
$$

可能很贵。

高性能实现会使用：

- 稀疏 allowed set；
- precomputed transition；
- bitset；
- trie；
- batched mask kernel；
- backend-specific compiler。

### 与 Speculative Decoding 的组合

Speculator 提出的候选也必须满足 grammar。

如果 Drafter 不知道 grammar：

```
大量 draft token → grammar 一票否决 → acceptance 下降
```

因此可选方案：

1. Drafter 也应用 constraint；
2. Target verify 前快速过滤；
3. 对 structured workload 选择不同 Speculator；
4. 直接降低 speculative depth。

这必须单独 Benchmark。

### 与 Tool Calling 的关系

Agent 的工具调用通常要求固定 schema。

因此 Structured Output 不是单纯“格式美观”，而是 Agent Runtime 的协议边界：

```
LLM → JSON args → Tool Executor
```

非法参数会直接变成失败/retry，引发更高总成本。

### Grammar

在 Structured Output Serving：Grammar、FSM 与 XGrammar 中，Grammar 的边界由输入、输出、状态和拥有者共同确定。把生命周期写清楚，才能定位请求在哪个阶段等待、计算或复制。Grammar 连接有限状态机 FSM 时还要传播身份和版本，避免把另一套配置的结果归到当前实验。

测量 Grammar 时分别记录算力、显存、带宽、CPU 开销与同步。发生“每步 Token Mask 排除不合法候选”后，缩短的阶段可能让另一项资源成为瓶颈。分析因此对齐 Grammar 的阶段事件和资源轨迹，不让单个平均利用率代替因果证据。

评估 Grammar 需要把负载分布写入实验：输入输出长度、并发、到达突发、采样方式和业务域都可能移动收益边界。限制 Schema 复杂度至少比较低载、临近容量与过载，结论只覆盖实际运行过的区间。

Grammar 进入候选路径后，输出校验继续检查 Token、采样、结构、结束原因和错误传递。掩码处理成为 CPU 瓶颈一旦出现，质量结果优先于速度数字；发布停止，流量回到已验证修订，相关请求留作重放。

观察 Grammar 需要稳定请求身份、模型与策略修订、起止时间、阶段耗时、资源快照和失败原因。合法输出率同时注明单位、窗口和分母。这些字段使“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”可以在发布后按原条件回放。

### 有限状态机 FSM

解释有限状态机 FSM 时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Structured Output Serving：Grammar、FSM 与 XGrammar 的请求可能在这些交界处增加等待、计算或复制。与 XGrammar 交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕有限状态机 FSM 建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。词表到语法终结符的映射影响编译与内存会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

选择 CPU 或 GPU 掩码路径是否合适，取决于有限状态机 FSM 所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

有限状态机 FSM 带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现 Tokenizer 映射错误拒绝合法 Token 时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

有限状态机 FSM 的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。TTFT 没有单位、统计窗口和分母时不参与决策。完整记录用于复查“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”在具体负载下是否成立。

### XGrammar

XGrammar 在 Structured Output Serving：Grammar、FSM 与 XGrammar 中的生命周期需要落到组件接口：输入从哪里来，状态由谁持有，输出交给谁，失败如何传播。它与 Token Mask 之间的身份和版本若未绑定，请求时间线就可能混入旧配置。

缓存复用能够摊销重复 Schema 编译对 XGrammar 的影响会分散到计算、显存、内存带宽、主机处理和同步等待。某一阶段变短时，被遮蔽的成本可能随即暴露。为确认 XGrammar 的变化来自哪里，本课对齐请求时间线与资源采样，而非只看整段运行的 GPU 平均值。

XGrammar 的边际价值会随输入长度、输出长度、并发、流量突发、采样和任务域变化。验证设置非法结构回退时分别运行低载、接近饱和与过载区间，并使用代表性分布。单一长度、批量或短窗口只能说明该测试点。

正确性门禁覆盖 XGrammar 影响到的 Token、采样、结构、结束状态与错误。若检测到只验证 JSON 语法却忽略业务语义，当前性能结果不进入候选评审，并立即切回已验证配置。失败样本与版本信息要一并保存。

为 XGrammar 建立证据链时，统一保存请求 ID、模型及策略修订、关键时间点、资源快照和错误。吞吐损失的定义随报告存档，包括单位、窗口和分母。这样才能按同一条件重放“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”。

### Token Mask

对 Token Mask 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Structured Output Serving：Grammar、FSM 与 XGrammar 的等待、计算及复制都能沿这些节点定位。Token Mask 传给 Grammar 编译缓存的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

Token Mask 的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。复杂递归结构扩大状态和分支通常只先改变其中几项，其他资源随后可能进入关键路径。Token Mask 的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，Token Mask 对系统的贡献也会变化。隔离不可信 Schema 应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对 Token Mask 的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。首次编译造成 TTFT 尖峰会触发停止与回退，系统恢复到已有证据支持的配置。

Token Mask 相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。重试节省必须附带口径。缺少这些信息时，关于“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”的判断无法在上线后复核。

受约束采样的资源账要拆成计算、显存、内存带宽、主机开销和同步等待。词表到语法终结符的映射影响编译与内存通常只先改变其中几项，其他资源随后可能进入关键路径。受约束采样的请求时间线和资源曲线可以呈现这种转移，平均 GPU 利用率只作为辅助信号。

工作负载一变，受约束采样对系统的贡献也会变化。选择 CPU 或 GPU 掩码路径应覆盖长短输入、不同输出、并发、突发、采样与任务域，并保留低载、稳定高载和过载记录。容量判断不能从一次固定批量的短运行外推。

对受约束采样的优化只有在输出合同不变时才有效。Token 序列、采样分布、结构合法性、结束原因和错误传播均需对账。Tokenizer 映射错误拒绝合法 Token 会触发停止与回退，系统恢复到已有证据支持的配置。

受约束采样相关事件要能关联到稳定请求身份、模型与策略版本、开始结束时间、阶段耗时、资源采样和失败原因。状态数必须附带口径。缺少这些信息时，关于“约束解码如何保证结构合法，同时控制编译、缓存和逐步掩码成本？”的判断无法在上线后复核。

### 决策 1：选择 JSON Schema 或 Grammar

评审“选择 JSON Schema 或 Grammar”时，先写明要改善的用户承诺，以及对应的编译延迟、每 Token 掩码延迟和合法输出率。候选需说明 Grammar 的资源变化、“语法约束被编译为可推进的状态机”的适用条件及首次编译造成 TTFT 尖峰触发的停止动作。只在极端样本成立的收益应限定启用范围。

### 失败模式 1：首次编译造成 TTFT 尖峰

诊断“首次编译造成 TTFT 尖峰”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查 Grammar，结合编译延迟与缓存命中率定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

对“首次编译造成 TTFT 尖峰”先执行在线保护，再处理复发条件。面向首次编译造成 TTFT 尖峰的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查状态数的采集完整性。

### 失败模式 2：缓存键忽略 Schema 版本

出现“缓存键忽略 Schema 版本”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿有限状态机 FSM 的事件查看缓存命中率和每 Token 掩码延迟，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

修复“缓存键忽略 Schema 版本”分为影响控制和复验。针对缓存键忽略 Schema 版本可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对合法输出率没有被隐藏。

### 失败模式 3：复杂递归导致状态爆炸

针对“复杂递归导致状态爆炸”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。XGrammar 的时间线配合每 Token 掩码延迟、状态数可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

处理“复杂递归导致状态爆炸”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认 TTFT 没有转移到未计量层。

### 失败模式 4：掩码处理成为 CPU 瓶颈

“掩码处理成为 CPU 瓶颈”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查 Token Mask 的阶段事件，并用状态数及合法输出率缩小故障位置。客户端、服务端、计费数据均需完成对账。

“掩码处理成为 CPU 瓶颈”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验吞吐损失。

### 失败模式 5：Tokenizer 映射错误拒绝合法 Token

记录到“Tokenizer 映射错误拒绝合法 Token”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿 Grammar 编译缓存回放事件，再比较合法输出率与 TTFT。若完成数存在账差，先修复计量链。

对“Tokenizer 映射错误拒绝合法 Token”先执行在线保护，再处理复发条件。面向 Tokenizer 映射错误拒绝合法 Token 的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查重试节省的采集完整性。

### 失败模式 6：只验证 JSON 语法却忽略业务语义

排查“只验证 JSON 语法却忽略业务语义”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看结构合法性的时间线以及 TTFT、吞吐损失。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

修复“只验证 JSON 语法却忽略业务语义”分为影响控制和复验。针对只验证 JSON 语法却忽略业务语义可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对编译延迟没有被隐藏。

```
"""Lesson 12 — constrained JSON output with schema validation."""

from __future__ import annotations

import argparse
import hashlib
import json
import time

from phase3lab.shared.http_client import auth_headers, discover_models, extract_text, metrics_evidence, request_json
from phase3lab.shared.runner import LabSpec, PreconditionError, run_cli
from phase3lab.shared.stats import latency_summary

SPEC = LabSpec(
    lab_id="lesson-12-structured-output",
    title="Grammar：受约束 JSON 输出与逐请求校验",
    goal="向真实端点提交 JSON Schema 约束，并独立解析和校验每条响应。",
    real_evidence=("response_format request", "raw response hash", "validator findings"),
    required_inputs=("JSON-schema capable endpoint", "served model"),
    outputs=("request records", "schema pass rate", "parse failures"),
    acceptance=("schema is sent to backend", "every response is parsed", "invalid output fails acceptance"),
)

SCHEMA = {
    "type": "object",
    "properties": {
        "summary": {"type": "string"},
        "risks": {"type": "array", "items": {"type": "string"}},
        "confidence": {"type": "number", "minimum": 0, "maximum": 1},
    },
    "required": ["summary", "risks", "confidence"],
    "additionalProperties": False,
}

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--strict", action=argparse.BooleanOptionalAction, default=True)

def validate_document(value) -> list[str]:
    findings = []
    if not isinstance(value, dict):
        return ["root_not_object"]
    if set(value) != {"summary", "risks", "confidence"}:
        findings.append("field_set_mismatch")
    if not isinstance(value.get("summary"), str):
        findings.append("summary_not_string")
    if not isinstance(value.get("risks"), list) or not all(isinstance(item, str) for item in value.get("risks", [])):
        findings.append("risks_not_string_array")
    confidence = value.get("confidence")
    if not isinstance(confidence, (int, float)) or isinstance(confidence, bool) or not 0 <= confidence <= 1:
        findings.append("confidence_out_of_range")
    return findings

def fixture(args: argparse.Namespace) -> dict:
    documents = [
        {"summary": "ok", "risks": ["tail latency"], "confidence": 0.8},
        {"summary": "bad", "risks": "not-a-list", "confidence": 2},
    ]
    return {"validation": [{"findings": validate_document(value)} for value in documents], "schema": SCHEMA}

def real(args: argparse.Namespace) -> dict:
    if len(args.base_url) != 1:
        raise PreconditionError("provide exactly one --base-url")
    served = discover_models(args.base_url[0])
    model = served[0] if args.model == "auto" else args.model
    if model not in served:
        raise PreconditionError(f"model {model} is not served")
    records = []
    for index in range(args.requests):
        payload = {
            "model": model,
            "messages": [{"role": "user", "content": f"{args.prompt}\n返回 summary、risks、confidence。case={index}"}],
            "max_tokens": args.max_new_tokens,
            "temperature": 0,
            "response_format": {"type": "json_schema", "json_schema": {"name": "inference_review", "strict": args.strict, "schema": SCHEMA}},
        }
        started = time.perf_counter()
        status, body, _ = request_json("POST", f"{args.base_url[0].rstrip('/')}/v1/chat/completions", payload, timeout=180, headers=auth_headers())
        elapsed_ms = (time.perf_counter() - started) * 1000
        text = extract_text(body) if status == 200 else ""
        try:
            document = json.loads(text)
            findings = validate_document(document)
        except json.JSONDecodeError:
            findings = ["invalid_json"]
        records.append({"request_id": f"grammar-{index}", "status_code": status, "latency_ms": round(elapsed_ms, 4), "response_sha256": hashlib.sha256(text.encode()).hexdigest(), "findings": findings})
    passed = [record for record in records if record["status_code"] == 200 and not record["findings"]]
    if len(passed) != len(records):
        raise RuntimeError(f"structured-output acceptance failed for {len(records) - len(passed)} request(s)")
    return {
        "model": model,
        "schema": SCHEMA,
        "metrics": metrics_evidence((args.evidence_url or args.base_url)[0]),
        "records": records,
        "latency": latency_summary([record["latency_ms"] for record in records]),
        "schema_pass_rate": 1.0,
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

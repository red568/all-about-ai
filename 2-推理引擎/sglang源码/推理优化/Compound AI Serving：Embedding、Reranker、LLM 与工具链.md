## 课程定位

本课把 Compound AI Serving：Embedding、Reranker、LLM 与工具链放回真实请求链路中讨论，中心问题为“如何用关键路径和阶段预算优化多阶段 AI 请求，而非局部跑分？”。Compound AI 请求图和 Embedding 提供分析入口，计算模型负责说明方向，实验和发布门禁负责限定结论。评审时需要同时查看模型版本、负载、调度、显存、并发与服务等级，避免把 Compound AI 请求图的局部理想收益直接当成端到端结果。

本课先用 CPU 模拟控制 Compound AI 请求图和 Embedding，再用真实 CUDA 路径检查这些关系进入实现后增加了哪些成本。每份结果都要标明数据来源、运行环境和适用边界。这样得到的是可复查的工程判断，而非依赖某个框架版本的参数口诀。

## 学习目标

1. 准确解释 Compound AI 请求图、Embedding 和 Reranker 之间的状态与资源关系。
2. 使用“T\_graph = longest\_path(stage durations)；Q\_e2e = f(retrieval, ranking, generation, tools)”建立可计算的收益边界并解释全部变量。
3. 围绕端到端延迟、关键路径长度、阶段成功率和每成功任务成本设计可复现实验。
4. 识别优化非关键路径没有端到端收益、上游质量下降导致 LLM 重试和各阶段独立超时超过总截止时间等典型失败模式。
5. 对“如何用关键路径和阶段预算优化多阶段 AI 请求，而非局部跑分？”给出包含适用条件、证据、风险和回滚的工程答案。

## 工程问题

关于 Compound AI Serving：Embedding、Reranker、LLM 与工具链的性能问题，要从测量条件开始。模型与修订、输入输出分布、请求到达、并发、采样、缓存、端到端延迟统计方式、服务等级和硬件均需保持可追溯。“确定阶段拓扑”和“分配延迟与成本预算”只有在同一证据口径下才可比较。

决策所需的八个观察对象为：Compound AI 请求图、Embedding、Reranker、LLM、外部工具、关键路径、阶段预算、端到端质量。它们横跨算法、运行时和平台，共同作用于降级率与每成功任务成本。以 Compound AI 请求图为例，每个对象都要标出拥有者、状态、计量点和失败边界，局部变化才能与端到端结果对上。

## 知识串讲

### 核心直觉与基础关系

### 核心直觉：Compound AI 的性能由端到端 Critical Path 决定

一个 RAG / Agent / Search + LLM 请求往往包含多个服务阶段。局部优化只有落在关键路径上，才会转化成用户可见收益。

串行链：

$$
T_{e2e}=\sum_i T_i
$$

并行分支：

$$
T_{parallel}=\max_i T_i
$$

复杂 DAG 的用户延迟由最长依赖路径决定。

例如：

```
Embedding 10ms
Vector Search 20ms
Reranker 100ms
LLM 2000ms
Safety 50ms
```

把 Embedding 从 10ms 优化到 2ms，端到端只省 8ms。

如果 Reranker 导致 LLM Prompt 从 8000 token 减到 2000 token，即使 Reranker 自己要 100ms，整体反而可能更快、更省。

这就是 Compound AI 的跨阶段优化。

### 局部成本与下游收益

可以定义第 $i$ 阶段的价值：

$$
Value_i=DownstreamCostSaved_i-Cost_i
$$

例如 Reranker：

- 自己增加 100ms；
- 让 LLM 输入减少 6000 tokens；
- LLM TTFT/成本显著下降。

不能只看 Reranker latency 判断是否值得。

### Stage Budget

全局 Deadline：

$$
D_{global}
$$

给各阶段：

$$
\sum_i B_i\le D_{global}
$$

但静态均分通常不合理。更好的方式根据历史 P95、业务重要性和 fallback 能力分配：

```
Embedding: 50ms
Search: 100ms
Rerank: 200ms
LLM TTFT: 800ms
Safety: 100ms
```

当某阶段超过 budget，可以：

- timeout；
- skip；
- 使用 cache；
- 降级模型；
- 减少候选数。

### Bulkhead：不同阶段不要互相拖死

如果 Embedding、Reranker、LLM 共用同一个无限队列，一个突发 workload 可能传播到所有阶段。

可以使用独立资源池：

```
Embedding Pool
Reranker Pool
LLM Pool
Judge Pool
```

每个 Pool 有自己的：

- concurrency；
- queue；
- circuit breaker；
- SLO；
- autoscaling。

这叫 bulkhead 思想：一个舱室进水，不让整艘船一起沉。

### Fallback 设计

Reranker 挂了怎么办？

方案不是只有“整个 API 500”。

可以：

```
Reranker healthy → rerank top50 → top10 → LLM
Reranker down    → vector top10        → LLM
```

质量略降，但服务仍可用。

类似：

- 大模型超载 → 小模型；
- Deep reasoning 超时 → balanced；
- tool unavailable → cached result；
- image encoder overloaded → lower resolution。

### Retry Budget

Compound system 最怕多层自动重试：

```
Gateway retry 2
 × RAG service retry 2
 × LLM SDK retry 2
 = 最坏 8 次调用
```

因此需要统一 retry budget：

$$
N_{retry,total}\le R_{max}
$$

并用 trace propagation 防止每层独立放大。

### 跨阶段 Observability

必须同时有：

- stage latency；
- queue time；
- cache hit；
- input/output size；
- error/retry；
- downstream saved tokens；
- cost。

比如 Reranker 的 KPI 不只是 rerank QPS，还包括：

$$
TokensSaved_{LLM}
$$

这才是它对整个系统的价值。

### Embedding

对 Embedding 做边界检查，要覆盖输入、输出、状态归属和销毁时点。Compound AI Serving：Embedding、Reranker、LLM 与工具链的等待、计算及复制都能沿这些节点定位。Embedding 传给 Reranker 的数据还应附带模型或策略版本，使测量结果可以对应到唯一配置。

### LLM

解释 LLM 时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Compound AI Serving：Embedding、Reranker、LLM 与工具链的请求可能在这些交界处增加等待、计算或复制。与外部工具交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕 LLM 建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。阶段预算必须服从任务截止时间会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

为外部依赖设置隔离是否合适，取决于 LLM 所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

LLM 带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现优化非关键路径没有端到端收益时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

LLM 的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。每成功任务成本没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何用关键路径和阶段预算优化多阶段 AI 请求，而非局部跑分？”在具体负载下是否成立。

### 端到端质量

解释端到端质量时，先列出它接收什么、产生什么、由谁维护以及状态何时结束。Compound AI Serving：Embedding、Reranker、LLM 与工具链的请求可能在这些交界处增加等待、计算或复制。与 Compound AI 请求图交互的字段必须携带版本身份，便于回放时找到同一配置。

围绕端到端质量建立资源模型，需要把计算量、显存占用、内存流量、主机工作和等待时间单独记账。召回与排序质量决定 LLM 上下文质量会移动关键路径，却很少让所有资源同比例变化。请求事件负责说明顺序，资源曲线负责解释瓶颈转移。

设置缓存与降级是否合适，取决于端到端质量所面对的长度分布、并发、到达过程、采样和任务域。实验在低载、接近饱和、过载三段保留同口径证据。固定长度与固定批量的结果用于解释机制，不承担完整容量结论。

端到端质量带来的速度变化仍需满足模型输出合同，包括 Token 序列、采样分布、结构合法性、结束原因和错误传播。出现缓存内容版本不一致时，质量门禁应停止性能发布；回退目标是已验证配置，并保留问题请求用于复现。

端到端质量的观测记录包含请求身份、模型版本、策略版本、阶段时间、资源状态与失败原因。召回质量没有单位、统计窗口和分母时不参与决策。完整记录用于复查“如何用关键路径和阶段预算优化多阶段 AI 请求，而非局部跑分？”在具体负载下是否成立。

推演重点是判断多阶段 AI 请求由串并行组件组成有向图发生后哪些量应变化，以及局部更快只有位于关键路径才改善完成时间的收益在什么负载下被摊销。实现中的调度、Kernel、内存、网络、客户端和取消成本另行记录。公式与实测产生矛盾时，以检查假设、遗漏项和统计方式为处理顺序。

### 机制 1：多阶段 AI 请求由串并行组件组成有向图

请求执行“多阶段 AI 请求由串并行组件组成有向图”后，阶段边界和依赖关系会发生变化。先记录原路径，再记录候选路径中的串行、并行与合批段；同时保存 Compound AI 请求图状态和端到端延迟，便于把原因与结果关联起来。

容量评估把“多阶段 AI 请求由串并行组件组成有向图”放在三个负载区间中运行。固定开销通常在低载突出，队列和资源争用会在高载显现；上游质量下降导致 LLM 重试意味着候选工作可能消耗了服务正常请求所需的容量。

实现“多阶段 AI 请求由串并行组件组成有向图”时明确数据格式、张量形状、缓存身份、版本兼容和错误回退。执行选择召回和重排规模前冻结接口合同，并加入无效输入、极端长度与资源不足测试。成功样本之外的保护行为也属于验收范围。

“多阶段 AI 请求由串并行组件组成有向图”的 Trace 同时记录决策输入与执行结果：前者含阈值和候选，后者含召回质量、错误、取消和资源变化。这样能判断问题来自机制、选择器、实现成本还是流量变化。

“多阶段 AI 请求由串并行组件组成有向图”的上线合同写明灰度范围、停止条件、开关和暖回滚目标。缓存内容版本不一致发生后，系统恢复相关稳定配置，并持续观察请求排空、缓存切换和资源回收。

### 机制 2：局部更快只有位于关键路径才改善完成时间

理解“局部更快只有位于关键路径才改善完成时间”要从请求关键路径入手。变化前后每个阶段的顺序、并行性和合批条件均需标注，Embedding 作为启用条件，关键路径长度作为端到端结果。

“局部更快只有位于关键路径才改善完成时间”的容量测试覆盖低载、稳定高载和过载。低载显示固定与同步成本，高载显示队列、批处理及共享资源竞争。若出现各阶段独立超时超过总截止时间，说明局部延迟没有变成有效容量，需要核对候选工作占用的公共资源。

“局部更快只有位于关键路径才改善完成时间”的接口合同包括格式、Shape、缓存键、版本与回退语义。设置缓存与降级进入评审前，使用非法输入、边界长度和资源不足场景检验保护路径，确保实现不会只在理想样本上成立。

为“局部更快只有位于关键路径才改善完成时间”采集证据时，把策略输入、阈值、候选集合与重排质量、错误、取消及资源事件放进同一请求链。诊断据此定位选择、执行和负载漂移中的具体环节。

为“局部更快只有位于关键路径才改善完成时间”准备独立发布单元，包含灰度身份、门禁、停止动作和已预热回滚路径。检测到阶段指标无法关联同一任务后执行局部撤回；进程恢复之外，还要确认在途工作、缓存与资源回到稳定状态。

### 机制 3：召回与排序质量决定 LLM 上下文质量

“召回与排序质量决定 LLM 上下文质量”会改写请求的阶段顺序。画出变化前后的关键路径，标明并行、串行和跨请求合批位置；Reranker 给出状态条件，阶段成功率验证结果是否传到请求端。

单请求数据不足以评价“召回与排序质量决定 LLM 上下文质量”。低载用于测量召回与排序质量决定 LLM 上下文质量的固定成本，接近容量时观察批处理与共享资源，过载时确认拒绝和尾延迟。外部工具故障拖垮线程池若只在并发后出现，优先检查候选路径对正常请求资源的挤占。

数据格式、张量形状、缓存身份、版本兼容和错误传播共同构成“召回与排序质量决定 LLM 上下文质量”的实现边界。统一 Trace 与身份需要在合同冻结后测试正常、无效、极端和资源受限输入。

“召回与排序质量决定 LLM 上下文质量”需要成对的原因和结果字段。原因包括决策特征、阈值和候选，结果包括调用放大系数、错误、取消和资源快照；关联后即可判断机制是否有效以及额外成本出现在哪里。

发布“召回与排序质量决定 LLM 上下文质量”时配置独立开关、灰度身份、停止条件和暖回滚目标。优化非关键路径没有端到端收益触发后只撤回相关变化，并继续检查在途请求、缓存和资源释放，直到稳定路径恢复。

### 机制 4：每个阶段的重试会放大下游调用

分析“每个阶段的重试会放大下游调用”时，把前后两条请求时间线对齐，逐段标出可并行、必须串行和允许合批的工作。LLM 说明机制何时生效，召回质量负责确认关键路径是否真的缩短。

对“每个阶段的重试会放大下游调用”分别施加轻载、稳定高载和过载流量，可以分辨同步开销、队列增长、合批变化与资源竞争。检测到缓存内容版本不一致后，沿共享执行资源检查局部收益为何没有进入系统 Goodput。

为“每个阶段的重试会放大下游调用”确定接口时，同时规定数据与 Shape、缓存和版本身份、错误及回退。随后以无效输入、极端长度和资源不足验证为外部依赖设置隔离，使失败路径与成功路径拥有同样清晰的证据。

观测“每个阶段的重试会放大下游调用”时，原因侧保存策略输入、阈值和候选集合，结果侧保存降级率、错误、取消与资源。两侧对齐后，可以区分每个阶段的重试会放大下游调用收益不足、选择错误、实现开销偏大和工作负载漂移。

“每个阶段的重试会放大下游调用”通过独立开关进入灰度，发布记录包含流量身份、停止阈值和可立即启用的回滚修订。出现上游质量下降导致 LLM 重试时撤回本项候选，随后核对在途请求、缓存状态与资源是否释放。

## 工程决策与取舍

### 决策 1：确定阶段拓扑

确定阶段拓扑解决哪项用户问题，需要由端到端延迟、阶段成功率和重排质量共同证明。评审材料同时记录 Compound AI 请求图资源账、“多阶段 AI 请求由串并行组件组成有向图”生效条件和优化非关键路径没有端到端收益的门禁。启用范围与实际证据范围保持一致。

围绕“确定阶段拓扑”运行基线、候选与回退。候选只引入“确定阶段拓扑”研究变量，回退保持已验证制品可立即恢复；每组使用同一请求集合和随机种子。报告分开呈现“确定阶段拓扑”在不同负载及请求形态下的结果，并记录拒绝项、复查触发器和每成功任务成本是否足以支付维护开销。

### 决策 2：分配延迟与成本预算

决定“分配延迟与成本预算”是否上线时，服务承诺是评审起点，关键路径长度、召回质量、调用放大系数构成结果证据。还需解释 Embedding 怎样变化、“局部更快只有位于关键路径才改善完成时间”在哪些负载下有效，以及遇到上游质量下降导致 LLM 重试时如何停止。

“分配延迟与成本预算”比较基线、候选和回退三种配置。基线沿用已验证路径，候选只改变“分配延迟与成本预算”研究因素，回退无需重新下载大制品即可恢复服务。三组使用相同请求集合与随机种子，并按负载区间、请求形态分组。决策记录包含“分配延迟与成本预算”的选择理由、被拒方案、结论到期条件和每成功任务成本对应的维护成本。

### 决策 3：选择召回和重排规模

评审“选择召回和重排规模”时，先写明要改善的用户承诺，以及对应的阶段成功率、重排质量和降级率。候选需说明 Reranker 的资源变化、“召回与排序质量决定 LLM 上下文质量”的适用条件及各阶段独立超时超过总截止时间触发的停止动作。只在极端样本成立的收益应限定启用范围。

实验为“选择召回和重排规模”保留当前基线、单变量候选和暖回退。请求集与随机种子保持一致，结果按负载和请求类型拆开。评审说明“选择召回和重排规模”为何采用当前方案、其他方案为何未采用、什么变化会让结论失效，以及每成功任务成本的改善是否覆盖新增运维成本。

### 决策 4：设置缓存与降级

“设置缓存与降级”进入方案评审前，要绑定具体服务承诺和召回质量、调用放大系数、每成功任务成本。资源侧检查 LLM，机制侧限定“每个阶段的重试会放大下游调用”，故障侧为外部工具故障拖垮线程池准备停止动作。测试样本不代表业务时，结论只覆盖该样本。

验证“设置缓存与降级”需要三条可复现路径：已确认的基线、只改“设置缓存与降级”因素的候选、无需重新取大制品的回退。三者共享请求和随机种子，数据按负载区间与请求形态统计。最终文档保存“设置缓存与降级”的取舍理由、有效期和每成功任务成本相对维护成本的变化。

### 决策 6：为外部依赖设置隔离

决定“为外部依赖设置隔离”是否上线时，服务承诺是评审起点，调用放大系数、每成功任务成本、关键路径长度构成结果证据。还需解释关键路径怎样变化、“缓存和降级能够跳过部分昂贵阶段”在哪些负载下有效，以及遇到阶段指标无法关联同一任务时如何停止。

## 失败模式与故障诊断

### 失败模式 1：优化非关键路径没有端到端收益

针对“优化非关键路径没有端到端收益”，保留失败现场并核验请求身份、模型修订、策略、负载分布与统计窗口。Compound AI 请求图的时间线配合端到端延迟、关键路径长度可区分选择错误、执行异常、验证失败和计量偏差。三方完成数无法对齐时不发布性能判断。

处理“优化非关键路径没有端到端收益”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认召回质量没有转移到未计量层。

### 失败模式 2：上游质量下降导致 LLM 重试

“上游质量下降导致 LLM 重试”的排查从证据一致性开始：请求、模型、策略、输入输出分布和测量窗口必须对应同一次运行。检查 Embedding 的阶段事件，并用关键路径长度及阶段成功率缩小故障位置。客户端、服务端、计费数据均需完成对账。

“上游质量下降导致 LLM 重试”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验重排质量。

### 失败模式 3：各阶段独立超时超过总截止时间

记录到“各阶段独立超时超过总截止时间”时，冻结配置和工作负载，确认请求身份、模型及策略修订、长度分布和时间窗口。沿 Reranker 回放事件，再比较阶段成功率与召回质量。若完成数存在账差，先修复计量链。

对“各阶段独立超时超过总截止时间”先执行在线保护，再处理复发条件。面向各阶段独立超时超过总截止时间的保护从禁用候选、预算收缩、请求隔离、过载拒绝和稳定回退中选择；长期措施落实到校验、迟滞、版本绑定、容量余量或自动门禁。原样本重放时同时检查调用放大系数的采集完整性。

### 失败模式 4：外部工具故障拖垮线程池

排查“外部工具故障拖垮线程池”需要同一版本、同一请求分布和同一统计窗口。先复核请求身份、模型与策略，再查看 LLM 的时间线以及召回质量、重排质量。选择、执行、验证、计量四个环节逐一排除，并核对三方完成数。

修复“外部工具故障拖垮线程池”分为影响控制和复验。针对外部工具故障拖垮线程池可以撤回候选、降低预算、隔离请求、拒绝过载或切换稳定路径；复发预防补齐输入校验、迟滞、版本绑定、容量余量及门禁。重放同一失败样本后，核对降级率没有被隐藏。

### 失败模式 5：缓存内容版本不一致

诊断“缓存内容版本不一致”时，先核对请求身份、模型修订、策略配置、输入输出分布和测量窗口。沿时间线检查外部工具，结合重排质量与调用放大系数定位工作选择、执行、验证或计量环节。客户端、服务端和计费完成数未对账前暂停性能结论。

处理“缓存内容版本不一致”时先保护在线请求，可采用禁用候选、收紧预算、隔离请求、拒绝过载或回退稳定路径。后续通过输入校验、迟滞、版本绑定、容量余量或自动门禁降低复发概率。修复完成后重放原失败样本，并确认每成功任务成本没有转移到未计量层。

### 失败模式 6：阶段指标无法关联同一任务

出现“阶段指标无法关联同一任务”后，固定当前请求集和版本信息，检查模型、策略、输入输出分布及测量窗口是否一致。随后沿关键路径的事件查看调用放大系数和降级率，确定问题落在选择、执行、验证还是计量。完成数对账是继续分析的前提。

“阶段指标无法关联同一任务”的即时动作是限制影响面：撤掉候选、缩小预算、隔离流量、执行过载拒绝或恢复稳定修订。根因修复需补充适用的输入检查、迟滞、版本关系、资源余量和门禁。随后用同一失败输入复验端到端延迟。

```
"""Lesson 14 — sequential Compound AI request graph with data lineage."""

from __future__ import annotations

import argparse
import hashlib
import time

from phase3lab.shared.http_client import auth_headers, discover_models, extract_text, metrics_evidence, request_json
from phase3lab.shared.runner import LabSpec, PreconditionError, run_cli

SPEC = LabSpec(
    lab_id="lesson-14-compound-chain",
    title="Compound AI：分类、证据生成与回答链路",
    goal="让每一阶段的真实输出成为下一阶段输入，并保存可核对的数据血缘。",
    real_evidence=("stage input/output hashes", "per-stage latency", "end-to-end trace"),
    required_inputs=("one OpenAI-compatible endpoint", "served model"),
    outputs=("ordered stage records", "lineage links", "final output hash"),
    acceptance=("three stages execute in order", "downstream input includes upstream output", "failures stop the chain"),
)

def add_arguments(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--stages", type=int, default=3, choices=[3])

def stage_prompts(user_prompt: str, outputs: list[str]) -> list[str]:
    prompts = [f"把问题分类为性能、容量、正确性或其他，只输出分类和一句理由：\n{user_prompt}"]
    if outputs:
        prompts.append(f"根据分类生成三条可验证的工程证据，不要给最终答案：\n分类结果：{outputs[0]}\n问题：{user_prompt}")
    if len(outputs) > 1:
        prompts.append(f"只根据以下问题、分类和证据给出最终回答，并指出证据不足处：\n问题：{user_prompt}\n分类：{outputs[0]}\n证据：{outputs[1]}")
    return prompts

def fixture(args: argparse.Namespace) -> dict:
    outputs = ["性能", "证据 A；证据 B；证据 C"]
    prompts = stage_prompts(args.prompt, outputs)
    return {"stage_count": len(prompts), "lineage": [{"stage": index, "input_contains_previous": index == 0 or outputs[index - 1] in prompt} for index, prompt in enumerate(prompts)]}

def call_stage(base: str, model: str, prompt: str, stage: int, max_tokens: int) -> tuple[dict, str]:
    payload = {"model": model, "messages": [{"role": "user", "content": prompt}], "max_tokens": max_tokens, "temperature": 0}
    started = time.perf_counter()
    status, body, _ = request_json("POST", f"{base.rstrip('/')}/v1/chat/completions", payload, timeout=180, headers=auth_headers())
    elapsed = (time.perf_counter() - started) * 1000
    if status != 200:
        raise RuntimeError(f"compound stage {stage} returned HTTP {status}")
    text = extract_text(body)
    return ({
        "stage": stage,
        "input_sha256": hashlib.sha256(prompt.encode()).hexdigest(),
        "output_sha256": hashlib.sha256(text.encode()).hexdigest(),
        "input_chars": len(prompt),
        "output_chars": len(text),
        "latency_ms": round(elapsed, 4),
    }, text)

def real(args: argparse.Namespace) -> dict:
    if len(args.base_url) != 1:
        raise PreconditionError("provide exactly one --base-url")
    served = discover_models(args.base_url[0])
    model = served[0] if args.model == "auto" else args.model
    if model not in served:
        raise PreconditionError(f"model {model} is not served")
    outputs: list[str] = []
    records = []
    for stage in range(3):
        prompt = stage_prompts(args.prompt, outputs)[stage]
        record, text = call_stage(args.base_url[0], model, prompt, stage, args.max_new_tokens)
        if outputs:
            record["previous_output_sha256"] = hashlib.sha256(outputs[-1].encode()).hexdigest()
            record["previous_output_present"] = outputs[-1] in prompt
        records.append(record)
        outputs.append(text)
    if not all(record.get("previous_output_present", True) for record in records):
        raise RuntimeError("compound chain lineage check failed")
    return {
        "model": model,
        "metrics": metrics_evidence((args.evidence_url or args.base_url)[0]),
        "stages": records,
        "end_to_end_ms": round(sum(record["latency_ms"] for record in records), 4),
        "final_output_sha256": records[-1]["output_sha256"],
    }

def main() -> None:
    run_cli(SPEC, add_arguments, real, fixture)

if __name__ == "__main__":
    main()
```

## 联合推演 1：Compound AI 请求图、多阶段 AI 请求由串并行组件组成有向图与确定阶段拓扑

围绕确定阶段拓扑构造时间线：请求进入时绑定模型、策略和工作负载身份，执行时记录 Compound AI 请求图与“多阶段 AI 请求由串并行组件组成有向图”，结束时汇总端到端延迟。实验保留原始事件和分位数，以便从混合流量中识别优化非关键路径没有端到端收益。

容量部分固定模型与资源，分别运行低载、稳定高载和过载。低载体现“多阶段 AI 请求由串并行组件组成有向图”的固定成本，高载反映批处理及资源共享，过载时 Compound AI 请求图与队列、截止时间共同作用。三个区间的端到端延迟均可解释后，才为确定阶段拓扑划定边界。

注入“优化非关键路径没有端到端收益”后，按检测、隔离、降级、回滚和重新导流记录事件。端到端延迟帮助定位影响，隔离负责停止无效消耗，回滚目标与 Compound AI 请求图保持兼容。缓存、队列与在途请求稳定后，才恢复“多阶段 AI 请求由串并行组件组成有向图”相关流量。

把确定阶段拓扑引入的资源与维护成本加总，再除以符合质量和服务等级的有效完成，得到可比较单位。端到端延迟只是其中一项证据；优化非关键路径没有端到端收益会增加无效成本。最终判断注明 Compound AI 请求图适用的模型、负载范围与到期条件。

## 联合推演 2：Compound AI 请求图、多阶段 AI 请求由串并行组件组成有向图与确定阶段拓扑

确定阶段拓扑的成本分子覆盖计算、显存、训练、加载、监控和日常维护，分母采用有效完成数。结合调用放大系数和阶段指标无法关联同一任务可以判断局部性能是否转化为整体收益。结论仅适用于记录的 Compound AI 请求图、模型与流量，条件变化后重新评估。

## 本课小结

本课从“如何用关键路径和阶段预算优化多阶段 AI 请求，而非局部跑分？”出发，把 Compound AI Serving：Embedding、Reranker、LLM 与工具链拆成可验证决策。理论侧关注 Compound AI 请求图、Embedding 和 Reranker，执行侧检查“多阶段 AI 请求由串并行组件组成有向图”与“缓存和降级能够跳过部分昂贵阶段”，结果侧使用端到端延迟和每成功任务成本。三侧证据一致时，方案才有明确收益边界。

本课用模拟确定机制方向，用 CUDA 实测限定实现成本。优化非关键路径没有端到端收益与上游质量下降导致 LLM 重试通过完整请求链和版本记录定位。上线前还要验证输出合同、服务等级、有效成本、停止条件和恢复行为。
